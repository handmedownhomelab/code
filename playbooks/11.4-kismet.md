# Playbook 11.4 — Kismet

> **For the reader.** Read this whole file, and the files in `11.4/`,
> before you give them to your AI assistant. You need a Linux machine that
> stays on (the book's is the Raspberry Pi 5 from 11.2), a USB Wi-Fi adapter
> that supports **monitor mode**, Uptime Kuma (3.1) for the heartbeat, and
> ideally your reverse proxy (4.3) and private CA (4.4) for TLS. Kismet
> hears your neighbours' devices too: reading that is fine, publishing it is
> not (Appendix B). This playbook is **Not tested** (see the header). Then
> say: *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 11.4 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The adapter's chipset decides the driver,
   the hop rate and the channels that work. Measure them on the reader's
   adapter.
2. **Show each command before you run it**, and say which machine it runs
   on.
3. **CONFIRM** means stop, ask, and wait for a yes. Installing software,
   changing NetworkManager, firewall or service settings, or deleting logs
   is a CONFIRM step even if this file forgot to mark it.
4. **Get install steps from Kismet's own documentation**; they change. Don't
   pipe downloaded scripts into a shell.
5. **Never ask Kismet for the full device list with all its fields.** On a
   busy sensor that stalls Kismet long enough to drop its capture (see
   step 8). Ask for devices seen since a time, or one device by MAC, with
   a short list of fields; for health, use `/system/status.json` and
   `/datasource/all_sources.json`.
6. **Secrets:** the reader sets Kismet's web login and types it into the
   watchdog's env file (mode 600) themselves.
7. **Verify by effect**: the channel the radio is on, measured over time,
   not the config file that says what it should be.
8. If the reader keeps a homelab wiki, record the adapter, its driver,
   the channel list and why, the hop rate as measured, and where the
   config file actually lives.

## Goal: what "done" looks like

- [ ] The adapter in monitor mode, NetworkManager kept off it, and Kismet
      running as a service as the reader's account, not root.
- [ ] `kismet_site.conf` in the directory Kismet actually reads, proved by
      a setting taking effect.
- [ ] The radio hops the chosen channels at the chosen rate, **measured**.
- [ ] The web interface on the LAN only, behind TLS, with a login.
- [ ] Data-packet logging off, devices expiring after 48 hours, and old
      logs pruned by a script, not logrotate.
- [ ] `kismet-hop-watch` running every 5 minutes, and Kuma's push monitor
      going down when the capture stops.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The adapter's chipset and driver | Decides monitor-mode quality and dwell time | `lsusb`; `readlink /sys/class/net/<if>/device/driver` |
| Whether the kernel driver is in-tree | The book's Realtek chips have a kernel driver since Linux 6.14; old out-of-tree drivers are a step back | `uname -r`; `modinfo <driver>` |
| The interface name | Everything below names it | `iw dev` |
| Kismet from packages, or source | Kismet's repository packages can be older than a source build, and the config directory differs | Kismet's install docs; `apt-cache policy kismet` (read **Installed**, not Candidate) |
| The country's Wi-Fi channels | The channel list | The regulatory domain (`iw reg get`) |
| Where the adapter can hear best | Placement mattered more than any setting | Try two spots and compare device counts |
| Kuma's address and a new push monitor | The heartbeat | Kuma (book 3.1) |

## Steps

### 1. The adapter: monitor mode, and NetworkManager off it — CONFIRM

Plug the adapter in, check it in `iw dev`, and check it supports monitor
mode (`iw list` → "Supported interface modes" includes `monitor`).
Install `11.4/99-kismet-unmanaged.conf` in `/etc/NetworkManager/conf.d/`
with the reader's interface name, and apply it at runtime with `nmcli
device set <if> managed no` (don't restart NetworkManager over SSH if it
manages the SSH interface). Left managed, NetworkManager scans the
adapter every few minutes, and each scan retunes the radio out from under
Kismet.

**Verify:** `nmcli device` shows the adapter `unmanaged`.

### 2. Install Kismet — CONFIRM

From Kismet's documentation: its package repository, or a source build
(`make` then `make suidinstall`, which installs the capture helpers setuid
for group `kismet`). Add the reader's account to group `kismet`. The
author builds from source; their repository's package was older than the
build, so "switching to the package" would have been a downgrade.

Install `11.4/kismet.service` (set `User=`), enable it.

**Verify:** `kismet --version`; the service runs as the reader's account;
the web interface answers on port 2501 locally, and the reader creates the
login on first visit.

### 3. The site config, in the right place — CONFIRM

Copy `11.4/kismet_site.conf` into Kismet's own config directory
(`/usr/local/etc/` for a source build, `/etc/kismet/` for a package), set
`httpd_bind_address` to the sensor's LAN address, and put the reader's
interface on the `source=` line. **Not `~/.kismet/`**: Kismet never reads
a site config there, and the author's sat there, ignored, for weeks.

Restart Kismet.

**Verify:** the log at start-up says `Setting default channel hop rate to
1/sec`, and `ss -ltn` shows 2501 on the LAN address only.

### 4. Measure the hop rate

```
for i in $(seq 20); do /usr/sbin/iw dev <if>mon info | grep -oE "channel [0-9]+"; sleep 0.2; done
```

At 1 per second, each channel repeats about five times in a row. All
different means the radio is still hopping at 5 per second, whatever the
config says. The rate **must** be the global `channel_hop_speed`: on the
`source=` line, `hop_rate=` and `channel_hoprate=` both parse without an
error and do nothing.

Kismet's API agrees or disagrees in `/datasource/all_sources.json`
(`kismet.datasource.hop_rate`).

### 5. The channel list, by evidence

Start from the shipped list (every 2.4 and 5 GHz channel except 165) and
the reader's country. Then watch for a day:

- **Kernel warnings and log volume.** `journalctl -k` for driver warnings
  on particular channels, and `journalctl --disk-usage` from day to day. On
  the author's adapter every hop to channel 165 printed warnings, about
  2.8 GB of journal a day, and identified nothing; dropping that one
  channel stopped it.
- **What each channel yields.** Kismet's channel view; a channel with
  traffic and no identified devices is suspect.

**Verify:** `/datasource/all_sources.json` → `kismet.datasource.hop_channels`
lists the expected count (the shipped list: 35).

### 6. Placement

Try the adapter in two places for an hour each and compare new devices
per hour. The author's moved from the basement to the floor above, on a
USB 3 extension (the adapter itself is USB 2), and discovery roughly
tripled. No setting came close.

### 7. Web interface behind TLS, and the firewall — CONFIRM

A proxy host on the reverse proxy (book 4.3) for `kismet.<your domain>`
with a certificate from the private CA (4.4), Force SSL, **WebSockets on**.
On the sensor, allow port 2501 only from the proxy and the machines whose
scripts read the API.

**Verify:** the proxy name loads over HTTPS with the login; port 2501
doesn't answer from another LAN machine that isn't allowed.

### 8. Reading the API safely

Kismet keeps every device in memory, and a request for the whole list with
all its fields made the author's sensor stall long enough for the capture
helpers to exit. So:

- **Health:** `/system/status.json` (device count, memory) and
  `/datasource/all_sources.json` (each source, running, hopping, packets).
- **Recent devices:** `/devices/last-time/<unix-time>/devices.json`, with
  a `fields` list naming only what the report needs.
- **One device:** `/devices/by-mac/<mac>/devices.json`.
- **Alerts:** `/alerts/wrapped/last-time/<seconds>/alerts.json`.

When you ask for a nested field, the reply uses only its **last part** as
the key. Look up the name you actually get back, and make "not found"
different from 0: the book's report read 0 dBm for every device for four
months because of this.

**Verify:** a test query for the last hour's devices with three fields
returns in about a second, and the capture keeps running (packet counter
in `all_sources.json` still rising).

### 9. Logs and memory — CONFIRM

The shipped config already turns off data-frame logging and expires
devices idle for 48 hours (`tracker_device_timeout=172800`; keep it longer
than any report's window). For old logs, install
`11.4/kismet-log-maintenance.sh` with the two root cron lines in its
header: `prune` daily, `rotate` monthly, **after** the reader's daily
report. Don't use logrotate for Kismet: Kismet names its logs per run, so
renaming and counting never expires anything, and on the author's sensor it
failed silently for three months while 105 GB piled up.

**Verify:** after a day, `/system/status.json` shows the device count
levelling rather than climbing for ever. `kismet-log-maintenance.sh prune`
run by hand deletes closed sets older than 7 days and prints each one (on a
new install, nothing yet).

### 10. The hop watchdog and the heartbeat — CONFIRM

When Kismet re-opens a source after an error, it drops the quotes from the
`channels="…"` list and the radio hops channel 1 alone; on the author's
sensor that went unnoticed for 3.5 hours. `kismet-hop-watch` runs every 5
minutes: it reads the expected list and rate from `kismet_site.conf`, puts
them back if they differ (`set_channel.cmd`; `set_hop.cmd` only re-enables
hopping on the collapsed list), and pushes "up" to Kuma only when the
source is running, hopping the expected channels, and its packet counter
moved.

Create a **push monitor** in Kuma (5- to 10-minute heartbeat). Install
`11.4/kismet-hop-watch` in `/usr/local/bin/`, its `.service` and `.timer`
in `/etc/systemd/system/`, and `/etc/kismet-hop-watch.env` (mode 600, the
variables in the script's header, Kuma's **IP address** rather than a
name, so a DNS outage can't fake an alert). Enable the timer.

**Verify:** `journalctl -u kismet-hop-watch` shows "pushed", and Kuma's
monitor is up. Then stop Kismet (CONFIRM): Kuma goes down within a
heartbeat or two. Start it again.

## Gotchas (from the book and the author's sensor)

- **A setting in the wrong file or the wrong place does nothing, silently.**
  The hop rate was believed fixed for two months. Measure (step 4).
- **The channel list collapses on a re-open** (step 10). A Kismet restart
  reads the config correctly again.
- **Don't restart Kismet before the daily report.** A report that reads
  Kismet's memory then sees every device as new and loses the day's
  alerts. That's why the rotation is monthly.
- **"New devices" are mostly phones walking past** with random addresses.
  Filter to devices with a real manufacturer ID or ones that joined your
  network, and drop "devices" Kismet never heard (built from addresses
  inside other radios' traffic): their tell is a signal of exactly 0 dBm.
- **Read `Installed:`, not `Candidate:`.** A configured package repository
  isn't an installed package, and its version may be older than a source
  build.
- **Realtek USB adapters are slow to retune.** At Kismet's default 5 hops a
  second most of each slot goes on retuning. Chipsets made for monitor work
  (MediaTek MT7612U, Atheros AR9271) hop faster, if you're buying.
- **Out-of-tree Realtek drivers are now the old path.** On Linux 6.14 and
  later the in-kernel driver is the maintained one; a DKMS driver that
  fails to build after a kernel update leaves the sensor deaf.

## Rollback

`systemctl disable --now kismet kismet-hop-watch.timer`; remove the units,
the env file, `kismet_site.conf`, the cron lines and the NetworkManager
file (then `nmcli device set <if> managed yes`). Remove the proxy host and
the Kuma monitor. Logs are in `/var/log/kismet/`.
