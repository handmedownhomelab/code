# Playbook 7.1 — The GPU box

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need a desktop with Linux Mint installed (or Ubuntu; Mint is
> Ubuntu underneath), an NVIDIA card in its x16 slot, a power supply with the
> card's connectors, and SSH access from another machine. This playbook is
> **Not tested** (see the header). Then say: *"Follow this playbook. Ask me
> before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 7.1 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's card is a Blackwell (RTX 50-series)
   on driver 580. The reader's card decides the driver series, the CUDA
   version and the test image. Look them up for *their* card.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs or
   removes a driver, reboots, changes the firewall, or deletes anything is a
   CONFIRM step even if this file forgot to mark it.
4. **Get install steps from the upstream docs** (NVIDIA's Container Toolkit
   guide, Docker's Ubuntu guide, the distribution's driver tool). Use the
   distribution's driver packages, not NVIDIA's `.run` installer. Never pipe
   a downloaded script straight into a shell.
5. **Keep an SSH session open from another machine** through every driver
   step. If the desktop doesn't come back after a reboot, that session is
   how you fix it.
6. **Verify by effect**: `nvidia-smi` on the host *and* in a container, not
   "the package installed".
7. If the reader keeps a homelab wiki, record the card, driver version, CUDA
   version, the held packages and the firewall rules.

## Goal: what "done" looks like

- [ ] `nvidia-smi` on the host shows the card, the driver and the CUDA
      version, with persistence mode **Enabled**, and still does after a
      reboot.
- [ ] A CUDA test container prints the same table: containers can use the
      card.
- [ ] SSH is key-only; ufw denies incoming by default and every rule is
      limited to the LAN or one host.
- [ ] Docker's published ports are limited to the LAN too (ufw alone doesn't
      do it; step 7).
- [ ] Security updates install themselves, but never the NVIDIA driver,
      Docker or containerd; the driver packages are held.
- [ ] Every disk is mounted where it should be after a reboot, and the
      reader has a post-update check that tests the *work*, not the service.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The card and its generation | Decides the driver series and whether it needs the **open** kernel modules (Blackwell does) | `lspci -nn \| grep -i nvidia`; look the model up on NVIDIA's site |
| The driver series that supports it | Too old a series won't see a new card | NVIDIA's driver search for the card; on Mint, Driver Manager; `ubuntu-drivers devices` |
| Anything already installed | A leftover `.run` driver or old packages fight the new one | `dpkg -l \| grep -i nvidia`; `nvidia-smi` |
| Secure Boot | If it's on, the driver's kernel module must be signed, which means a password at install and a blue enrollment screen at the next boot | `mokutil --sb-state` |
| Mint/Ubuntu base | Docker's and NVIDIA's repositories want the **Ubuntu** codename, not Mint's | `. /etc/os-release; echo $UBUNTU_CODENAME` |
| Data disks | They must mount at boot, and you'll check them after every reboot | `lsblk -f`, `/etc/fstab` |
| The LAN range, and which machines call which service | The firewall allows only them | Ask; the router's DHCP settings |

## Steps

### 1. Install the driver — CONFIRM

Remove any leftover NVIDIA `.run` install first. Install the series from
*Discover first* with the distribution's packages; for a Blackwell card that
is the **open** variant (the book's is `nvidia-driver-580-open`). Mint's
Driver Manager installs the same packages. If Secure Boot is on, the install
asks for a one-time password; at the next boot, choose **Enroll MOK** and
enter it, or the module won't load.

Reboot (CONFIRM), with the SSH session from rule 5 ready.

**Verify:** `nvidia-smi` shows the card, the driver version and a CUDA
version, and `dpkg -l | grep nvidia-driver` shows exactly one driver series.
If it prints *Driver/library version mismatch*, the reboot hasn't happened or
two series are installed.

### 2. Persistence mode

Without it, the driver unloads when nothing is using the card and the next
job pays the start-up cost. On Mint, `nvidia-persistenced` ships with
`--no-persistence-mode`. Clear that with a systemd drop-in,
`/etc/systemd/system/nvidia-persistenced.service.d/persistence.conf`:

```
[Service]
ExecStart=
ExecStart=/usr/bin/nvidia-persistenced --user nvidia-persistenced --verbose
```

Reload systemd, enable and restart `nvidia-persistenced`.

**Verify:** `nvidia-smi --query-gpu=persistence_mode --format=csv` says
`Enabled`, and still does after the next reboot.

### 3. Docker Engine — CONFIRM

Follow Docker's **Ubuntu** install guide. Before running its repository
step, check the line it writes names the **Ubuntu** codename (`noble` for
Mint 22): `VERSION_CODENAME` on Mint is Mint's own name, which Docker's
repository doesn't have. Use Docker's Ubuntu repository, not its Debian one
(see Gotchas).

**Verify:** `docker run --rm hello-world` works, and `docker-ce` and
`containerd.io` both come from `download.docker.com/linux/ubuntu`
(`apt-cache policy docker-ce containerd.io`).

### 4. NVIDIA Container Toolkit — CONFIRM

Follow NVIDIA's install guide for apt: add its repository and key, install
`nvidia-container-toolkit`, run `nvidia-ctk runtime configure
--runtime=docker`, and restart Docker. That writes the `nvidia` runtime into
`/etc/docker/daemon.json`.

**Verify:** a CUDA base image no newer than the CUDA version `nvidia-smi`
reported prints the same table as the host:

```
docker run --rm --gpus all nvidia/cuda:<version>-base-ubuntu24.04 nvidia-smi
```

The book used `12.8.0`. Check the tag exists on Docker Hub first.

### 5. SSH keys only — CONFIRM

With the reader's key already working, a drop-in in
`/etc/ssh/sshd_config.d/` sets `PasswordAuthentication no` and
`KbdInteractiveAuthentication no`. Check with `sshd -t`, then reload.

**Verify:** from another machine, `ssh -o PubkeyAuthentication=no <host>` is
refused without asking for a password, and a normal key login still works,
**in a new session**, before closing the old one.

### 6. ufw, default deny — CONFIRM

Add the SSH rule **first**, limited to the LAN range, then set default deny
incoming, allow outgoing, and enable ufw. Every later rule names a source:
the LAN range, or one host for a service only one machine uses. No
`Anywhere` rules. Services you reach by SSH tunnel (the book's image and
video tools) get no rule at all.

**Verify:** `ufw status verbose` shows the defaults and only source-limited
rules. From another LAN machine SSH still works; a port with a listener but
no rule doesn't answer.

### 7. Limit Docker's ports too — CONFIRM

**Docker bypasses ufw.** A port published by a container is reachable from
anywhere the machine is, whatever ufw says, because Docker's own firewall
chain comes first. Add a `DOCKER-USER` block at the end of
`/etc/ufw/after.rules` (the "ufw-docker" pattern): return established
traffic, return the LAN range, the tailnet range if the reader uses
Tailscale (`100.64.0.0/10`) and Docker's own networks (`172.16.0.0/12`),
then drop everything else. `ufw reload`.

**Verify:** `iptables -S DOCKER-USER` shows the RETURN rules and a final
DROP. Start a test container publishing a port: it answers from a LAN
machine, and its packets show in the chain's counters (`iptables -L
DOCKER-USER -v -n`). Remove the test container.

### 8. Security updates without the GPU stack — CONFIRM

Install `unattended-upgrades`. In a local file such as
`/etc/apt/apt.conf.d/52unattended-upgrades-local`: security origins only;
a `Package-Blacklist` of `nvidia-`, `libnvidia-`, `docker` and
`containerd`; `Automatic-Reboot "false"`.

Then **hold the driver packages** with `apt-mark hold` (the book's:
`nvidia-driver-580-open`, `nvidia-dkms-580-open`,
`nvidia-kernel-source-580-open`, `nvidia-kernel-common-580`,
`libnvidia-gl-580`; use the reader's series). The blacklist only governs
unattended-upgrades; the hold also stops a hand-run `apt upgrade` from
swapping the driver.

**Verify:** `unattended-upgrade --dry-run --debug` lists no `nvidia`,
`docker` or `containerd` package, and `apt-mark showhold` lists the driver
packages.

### 9. Data disks, and the after-every-update check

Data disks in `/etc/fstab` by UUID with `nofail`, so a bad disk can't stop
the boot. That moves the failure to "boots with a hole in it", so write the
reader a short check to run after any reboot or GPU-stack update:

- `findmnt` shows every data disk at its mount point;
- `nvidia-smi` works on the host and in the test container (step 4);
- the *work* is happening: once the book's apps are installed, Ollama's
  model shows `100% GPU` in `ollama ps` (7.2) and Frigate's `detection_fps`
  is above zero (10.2).

**Verify:** reboot once (CONFIRM) and run the check. Everything passes
without anyone touching the machine.

## Gotchas (from the book and the author's machine)

- **A new GPU generation needs new everything.** For Blackwell: the 580
  open driver, CUDA 12.8 or later, PyTorch cu128 or newer builds, and about
  90 seconds of kernel compilation the first time each app uses the card.
  Check each app's support for the card before blaming the app.
- **A driver update without a reboot breaks containers.** The update swaps
  the libraries while the old kernel module stays loaded; `nvidia-smi` says
  *version mismatch*, and if Docker restarts in the same run, GPU containers
  exit and their restart policy can't recover them. Update the driver on
  purpose, reboot, then restart the GPU containers and run the step 9 check.
  This is the book's 45-hour blind camera story (10.2).
- **The hold doesn't cover a new driver series.** Holding
  `nvidia-driver-580-open` does nothing about `nvidia-driver-595-open`, a
  different package. Driver Manager or `ubuntu-drivers autoinstall` can move
  to a new series straight past the hold. Treat a series change as a planned
  change with the full check.
- **Docker's Debian repository on an Ubuntu base works until it doesn't.**
  The author's machine ran Docker's Debian packages on Ubuntu noble for four
  months, until a containerd build needed a newer `libseccomp2` than noble
  will ever ship, and containerd froze while `docker-ce` (which depends on
  `containerd.io` with no version) could still move. Use the Ubuntu
  repository; the signing key is the same.
- **After a container toolkit or Docker update, restart the GPU containers**
  once the machine is fully up. The restart-on-boot policy alone isn't
  enough for a container that needs the new runtime.
- **"Running" is not "working".** Every status light can be green while the
  GPU does nothing. That is why step 9 tests the work.

## Rollback

Unhold and purge the driver packages (`apt-mark unhold`, then `apt purge
'nvidia-*' 'libnvidia-*'`) and reboot onto the open-source `nouveau` driver.
Remove the toolkit package and the `nvidia` runtime from
`/etc/docker/daemon.json`. Delete the persistence and SSH drop-ins and the
unattended-upgrades local file. `ufw disable` turns the firewall off; remove
the `DOCKER-USER` block from `after.rules` and reload.
