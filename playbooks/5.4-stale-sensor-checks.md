# Playbook 5.4 — Sensors that lie: stale, unreliable and silent

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need Home Assistant from playbook 4.1. The nightly email
> from 5.3 is where these checks end up, and Pi-hole from 6.1 is needed only
> for step 6. Then say: *"Follow this playbook. Ask me before every step
> marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 5.4 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Ask which sensors matter to the reader; a
   freshness check on everything is noise.
2. **CONFIRM** before creating a helper, editing the 5.3 automation, or
   removing anything from the entity registry.
3. **Never remove a Zigbee device to clean up an entity.** Removing a device
   from the Zigbee integration can take the network with it (4.2). Remove
   the leftover *entity*, from the entity registry, only.
4. **If you edit through the Home Assistant MCP server** (playbook 5.5),
   follow its write loop: read fresh, show the change, write, **read it
   back**.

## Goal: what "done" looks like

- [ ] A **"real unavailable"** count that leaves out restored orphans, on a
      dashboard or in the nightly email.
- [ ] For each sensor that matters, a **freshness check** on `last_reported`
      with a sensible age, in the nightly email's banner.
- [ ] Any value the reader has found to be wrong is on a **skip list**, with
      the reason written down.
- [ ] Leftover entities from retired devices removed.
- [ ] Optional: for one device outside Home Assistant, its **heartbeat**
      found (step 6).

## Three kinds of lie

1. **Stale:** the last value, frozen and shown as current.
2. **Unreliable:** it updates, but it's wrong.
3. **Silent:** it isn't in Home Assistant, or it went without anything
   noticing.

"How many entities are unavailable?" catches none of these well: a stale
sensor *has a value*, and the count is padded with leftovers.

## Steps

### 1. Count only the real unavailable

Developer tools → Template:

```
{{ states | selectattr('state','eq','unavailable') | list | count }}
{{ states | selectattr('state','eq','unavailable')
          | rejectattr('attributes.restored','defined') | list | count }}
```

The first is the raw count. The second leaves out **restored orphans**:
entities Home Assistant remembers from an integration or device that no
longer provides them, which carry `restored: true`.

**Verify:** the second number is the smaller one, and listing the
difference (`selectattr('attributes.restored','defined')`) shows only
things the reader recognises as gone.

### 2. A helper for it — CONFIRM

Settings → Helpers → Create helper → **Template** → *Template a sensor*,
named "Unavailable (real)", state:

```
{{ states | selectattr('state','eq','unavailable')
          | rejectattr('attributes.restored','defined') | list | count }}
```

**Verify:** the helper's state equals step 1's second number.

### 3. Which timestamp means "heard from"

| Field | Moves when… | Answers |
|---|---|---|
| `last_changed` | the value changes | "how long has it read this?" |
| `last_updated` | the value or an attribute changes | usually the same |
| `last_reported` | **any** state write, even an unchanged value | "when did we last hear from it?" |

A modem that reads *Connected* all week has a week-old `last_changed` and is
fine. Only `last_reported` tells a quiet sensor from a dead one.

Check it on one of the reader's sensors:

```
{% set s = states.sensor.EDIT %}
changed {{ ((now() - s.last_changed).total_seconds() / 3600) | round(1) }} h ago,
reported {{ ((now() - s.last_reported).total_seconds() / 60) | round(0) }} min ago
```

**Verify:** for a sensor whose value rarely changes, `reported` is minutes
and `changed` is hours or days.

### 4. Freshness checks in the nightly email — CONFIRM

With the reader, list the sensors that matter and how often each should
report (a poller every 5 minutes: 6 hours is generous; a daily job: 30
hours). Add each to the 5.3 automation's `fresh` list as
`('Label', 'sensor.entity', hours)`. The starter already raises
"<label> stale" in the banner when `last_reported` is older than that, or
the sensor is unknown or unavailable.

Without 5.3, make a template binary sensor per check instead:

```
{% set s = states.sensor.EDIT %}
{{ s is none or s.state in ['unknown','unavailable']
   or (now() - s.last_reported).total_seconds() > 6 * 3600 }}
```

**Verify:** temporarily set one check's hours to `0`; it shows as stale
(run the 5.3 automation, or watch the binary sensor turn on). Set it back.

### 5. Values you don't trust — the skip list

When a value updates but is wrong (a battery percentage from a maker's
cloud that disagrees with the maker's own app is the book's example), don't
fix it with arithmetic. Take it out of the checks and read it where it's
right. Add it to 5.3's `batt_skip` (or the relevant list) and write the
reason in the automation's description.

**Verify:** the next rendered email no longer lists it.

### 6. Heartbeat for a device outside Home Assistant (optional)

A device that talks only to its maker's cloud still looks up that cloud's
name, on a timer. If the reader runs Pi-hole (6.1), its **query log** is a
record of when the device was last heard from:

1. Find the device's address in the router or Pi-hole's client list.
2. Pi-hole → **Query log**, filtered to that client, over the last day.
3. Look for the regular lookup: the same domain every few minutes. That
   rhythm is its heartbeat; silence there is a real outage.

**Verify:** the reader can name the domain and the interval. Turning that
into an automatic alert (an Uptime Kuma check, 3.1, or a Pi-hole API poll)
is the reader's choice; the book's lab hasn't built one.

### 7. Clean out retired devices' leftovers — CONFIRM each

From step 1, list the restored orphans. For each one the reader confirms is
really gone: Settings → Entities → the entity → ⚙ → **Delete**. Never
remove the Zigbee *device* for this.

**Verify:** step 1's two counts move closer together.

## Gotchas (from the book and the test)

- **A stale sensor isn't unavailable.** It has a value; only a timestamp
  shows it's old.
- **`last_changed` isn't liveness.** It ages on a healthy sensor whose value
  is steady, and it gave the book's lab a "stale for 29 hours" alarm about a
  monitor that had reported minutes before.
- **Restored orphans pad the unavailable count** (the book's lab once had
  186). Exclude them in every count you look at.
- **A missing entity is `none` in a template**, not an error: the
  freshness check counts it as stale on purpose, so a renamed sensor
  doesn't silently pass.

## Rollback

Delete the "Unavailable (real)" helper and any template binary sensors;
remove the `fresh` and skip-list entries from the 5.3 automation. Deleted
orphan entities don't come back, which is the point; they belonged to
nothing.
