# Playbook 10.1 — Nextcloud with no open ports

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You'll want a Tailscale account (book 3.5) and, ideally, a
> separate drive for the data. Then say: *"Follow this playbook. Ask me
> before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 10.1 describes. Follow the rules below for
> the whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's hosts, drive and paths are the
   author's. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on
   (the Proxmox host or the container).
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs
   software, formats or mounts a drive, or deletes anything is a CONFIRM
   step even if this file forgot to mark it.
4. **Follow Nextcloud's admin manual for the version you install**,
   especially its nginx configuration, which changes between versions.
5. **Secrets:** generate the database and admin passwords on the container
   into root-only files and never print them. The reader stores the admin
   password and changes it after the first login. `occ maintenance:install`
   takes them as arguments, so they're briefly visible in the container's
   process list. A single-purpose container has no other users to see them.
6. **Verify by effect**, and from outside the container where it matters.
7. If the reader keeps a homelab wiki, record the container, the paths, the
   mount and the listener list there.

## Goal: what "done" looks like

- [ ] Nextcloud is installed with its data on the separate drive, from the
      first install (the data directory can't be moved casually later).
- [ ] `occ setupchecks` reports nothing to fix.
- [ ] Inside the container, everything listens on `127.0.0.1` only (web,
      database, Redis). From the LAN, port 80 is refused.
- [ ] Phones and laptops on the tailnet open `https://<name>.<tailnet>.ts.net`
      with a valid certificate. Nothing outside the tailnet can.
- [ ] The data drive has its own backup (the Proxmox backup skips bind
      mounts), and a push monitor watches Nextcloud's health.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The Proxmox host and the data drive | Data on its own drive, bind-mounted in | Ask; `lsblk` on the host |
| The data path inside the container | Fixed at install time | Pick one now; the book uses `/var/nc-data` |
| Whether the drive has arrived | If not, pilot from a folder at the same path (book's war story) | Ask |
| The reader's tailnet | The only way in | Ask; book 3.5 |
| Where backups go | Bind mounts aren't in Proxmox backups | Ask |

## Steps

### 1. The container and the data mount — CONFIRM

An **unprivileged** Debian container with 2 cores and 4 GB, `nesting` on.
On the host, the data folder (on the drive, or a pilot folder) must be owned
by **100033:100033**, mode 770. In an unprivileged container, IDs are
shifted by 100000, so that is `www-data` (33) inside. Bind-mount it at
the chosen path with `pct set <id> -mp0 <host-path>,mp=<container-path>`.

**Verify:** inside the container, `ls -ldn <container-path>` shows owner
`33 33`.

### 2. Packages — CONFIRM

nginx, PostgreSQL, Redis, PHP-FPM and the PHP modules from Nextcloud's
requirements for the version you're installing. With Debian 13 that's
`php-fpm php-pgsql php-curl php-gd php-xml php-mbstring php-zip php-intl
php-bcmath php-gmp php-imagick php-redis` **and `php-apcu`**, which is easy
to leave out and then makes every request warn. Also `unzip` and `curl`.

### 3. Download and verify Nextcloud

Download the release archive and its `.sha256` file from
download.nextcloud.com, and check it with **`sha256sum -c
--ignore-missing`**. The checksum file also lists a metadata file you
didn't download, and without `--ignore-missing` the check "fails" with
the archive marked OK, stopping any `&&` chain. Extract it to
`/var/www/nextcloud`, owned by `www-data`.

### 4. Database and install — CONFIRM

Create a PostgreSQL role and database `nextcloud` with a generated password.
Run `occ maintenance:install` as `www-data` with `--database pgsql`,
`--database-host 127.0.0.1`, the generated passwords, and **`--data-dir`
set to the bind-mounted path**.

**Verify:** `occ status` shows `installed: true`.

### 5. Caching, locking and background jobs

- Redis on a **Unix socket**: enable `unixsocket` and `unixsocketperm 770`
  in Redis's config, add `www-data` to the `redis` group, restart Redis.
- `occ config:system:set`: `memcache.local` = APCu, `memcache.locking` =
  Redis, `redis host` = the socket path, `redis port` = 0 (an integer).
- **`apc.enable_cli=1`** for PHP's command line, or `occ` warns about APCu.
- `occ background:cron`, plus a systemd service (`php -f
  /var/www/nextcloud/cron.php` as `www-data`) and a **5-minute timer**.
  AJAX cron isn't enough.
- Restart PHP-FPM.

### 6. nginx on localhost only — CONFIRM

Use the nginx configuration from Nextcloud's admin manual for your version,
with `listen 127.0.0.1:80;` and `root /var/www/nextcloud;`. Remove the
default site and enable this one.

Then **`systemctl restart nginx`, not `reload`.** In testing, `reload`
after enabling the site reported success while nginx stayed on
`0.0.0.0:80` and `index.php` returned 404 (the same thing happened on the
author's build).

**Verify:**
- `ss -ltn` inside the container: ports 80, 5432 and 6379 on `127.0.0.1`
  (and `::1`) only.
- From another machine, `curl http://<container-lan-ip>/` is **refused**.
- `curl http://127.0.0.1/status.php` in the container shows
  `"installed":true`.
- **SSH:** the Debian template's `sshd` listens on every address. Ask the
  reader whether to remove it (manage with `pct enter` from the host), or
  bind it to the tailnet address only. Either way, nothing should answer on
  the LAN.

### 7. Clean setup checks

Run `occ maintenance:repair --include-expensive` (pending mimetype
migrations) and set `maintenance_window_start` (e.g. 6, meaning 06:00 UTC).
Run the cron service once and wait for it to finish: the first run takes a
while, and checks run during it report "last run 56 years ago".

**Verify:** `occ setupchecks` shows no ✗ and no ⚠. Over HTTPS (step 8) it
may then ask for **HSTS**: add the `Strict-Transport-Security` header in
nginx, because `tailscale serve` hands nginx plain HTTP.

### 8. Publish to the tailnet — CONFIRM

Install Tailscale in the container (its docs), join the reader's tailnet,
and publish nginx with `tailscale serve --bg --https=443
http://127.0.0.1:80`. Add the `*.ts.net` name to Nextcloud's
`trusted_domains`, and set `overwriteprotocol` to `https`.

**Verify:** from a tailnet device, `https://<name>.<tailnet>.ts.net/status.php`
answers with a valid certificate; from a phone **off** the tailnet, it
doesn't resolve or connect.

### 9. Backup and monitoring

- **Backup:** the data drive, a database dump and `config.php`, nightly,
  to another machine. Give it a **zero-file guard**: if the mount is
  missing, the source is an empty folder, and a mirror would delete the
  backup.
- **Monitoring:** Kuma can't reach `127.0.0.1` inside the container, so a
  small timer in the container checks Nextcloud's health (more than
  `status.php`, which stays green when the data mount is gone) and calls a
  Kuma push URL only when healthy (playbook 5.1).

## Gotchas (from the book and the test)

- **The data directory is fixed at install time.** Pilot at the final path.
- **`reload` didn't apply the new site; `restart` did.**
- **`php-apcu` and `apc.enable_cli`** are both needed.
- **A bind mount that comes back empty** (a drive re-enumerated after a
  reconnect) leaves `status.php` green while every read and write fails.
  Check the mount, not just the status page. `pct reboot` re-attaches it.
- **Proxmox's backup skips bind mounts.**

## Rollback

Remove the `tailscale serve` configuration and the machine from the
tailnet, then delete the container. The data folder on the host stays
until the reader deletes it.
