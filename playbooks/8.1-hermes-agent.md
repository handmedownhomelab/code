# Playbook 8.1 — Hermes: a sandboxed agent on your own models

> **For the reader.** Read this whole file, and `8.1/watch_page.py`, before
> you give them to your AI assistant. You need a Proxmox host with room for
> a small VM (4 GB of RAM, 20 GB of disk), and a model server on your
> network: the book's is Ollama on the GPU tower (playbook 7.2). Then say:
> *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 8.1 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **The agent lives in its own box.** Everything here happens inside the
   sandbox VM or on the model server; nothing gives the agent a key, a
   login or a token to any other machine.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before creating the VM, installing software, or changing
   SSH keys or firewall rules.
4. **Read an installer before running it.** Download it to a file, read
   it with the reader, pin it to a release, then run the file.
5. **Secrets stay in `~/.hermes/.env`** (mode 600) and are typed by the
   reader, never echoed.
6. **Verify by effect:** an answer that needed a tool, a message that
   arrived, a refusal that was logged.

## Goal: what "done" looks like

- [ ] A VM that runs only Hermes, as an ordinary user without `sudo`.
- [ ] Hermes answers from your own model server, with a provider that is
      not named `main`, and its log shows no provider warnings.
- [ ] The gateway runs as a service, and the scheduler's heartbeat is fresh.
- [ ] A page watcher stays silent until the page changes, then sends one
      message.
- [ ] (Optional) Your wiki arrives read-only through a key that can only
      push into one folder.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The Proxmox host for the sandbox | It holds the VM | The book uses the second host (1.3) |
| A fixed address for the VM | The jail's `from=` and your firewall rules | A DHCP reservation (book 1.5) |
| The model server's address, and its OpenAI-compatible URL | Hermes's provider | Ollama: `http://<host>:11434/v1` (playbook 7.2) |
| A model with tool calling, and the context it's served with | Hermes needs tools and at least 64K tokens | `curl http://<host>:11434/api/show -d '{"model":"<name>"}'`: `capabilities` must include `tools` |
| Whether a wiki copy is wanted, and from which machine | The rrsync jail | The machine that holds the wiki (book 2.2) |

## Steps

### 1. The sandbox VM — CONFIRM

Create a small Debian VM (2 cores, 4 GB, 20 GB: the install alone is about
2.5 GB). Give it a fixed address. Create an ordinary user for the agent
(the steps use `hermes`) **without** `sudo`. On the model server's side,
allow this VM to reach the model port; nothing else needs to reach the VM
except SSH.

**Verify:** `ssh hermes@<vm>` works, and `sudo -v` as that user is refused.

### 2. Prerequisites — as root, CONFIRM

`apt install git curl rsync libatomic1`. The installer's bundled Node.js
needs `libatomic1`; without it the install fails, because an agent user
without `sudo` can't install it ("pm install failed", after "sudo: a
password is required").

### 3. Install Hermes — as the agent user, CONFIRM

Download the installer from the project's site
(hermes-agent.nousresearch.com, Quick Install) to a file. **Don't pipe it
into a shell.** Read it with the reader: it installs into `~/.hermes` and
`~/.local/bin`, adds `~/.local/bin` to the shell's PATH, downloads a pinned
and checksummed `uv`, and installs dependencies hash-verified. By default it
installs the **tip of the main branch**, so pin a release: look up the
latest release tag on GitHub (NousResearch/hermes-agent) and its commit,
then run:

```
bash install.sh --commit <release commit> --non-interactive --skip-browser --skip-computer-use
```

The two `--skip` flags leave out a browser and a desktop-control driver
that a sandboxed home agent doesn't need; `hermes pm install` adds them
later.

**Verify:** `hermes --version` names the release you pinned, and
`stat -c %a ~/.hermes/.env` is `600`.

### 4. The model, and the provider name — CONFIRM

On the model server, make sure the model is served with **at least 64K
tokens of context** (Hermes's minimum for tool work). With Ollama, either
set the server's context length (the book's tower serves 81,920, 7.7) or
create a variant with `num_ctx 65536`, as Hermes's Ollama guide shows.

Then, on the VM, define the model server as a **named provider** and make
it the default. **Don't name it `main`**: `main` is also a keyword in
Hermes's auxiliary settings. The book's agent spent a month with every
background task failing silently because of that name.

```
hermes config set providers.local-ollama.api http://<model host>:11434/v1
hermes config set providers.local-ollama.default_model <model>
hermes config set providers.local-ollama.context_length <served context>
hermes config set model.provider local-ollama
hermes config set model.default <model>
```

The generated `config.yaml` starts with a cloud model as its default.
These commands replace it; don't add cloud keys unless you mean to.

**Verify:** ask something that needs a tool and has a known answer, e.g.
put a file with a known line in the agent's home folder and run `hermes
chat -Q -q "Use your file tools to read ~/<file> and tell me what it
says."` It answers with the line (about 90 seconds on the test's small
model, first call included). Then
`grep -E "custom/main|Nous Portal not configured" ~/.hermes/logs/agent.log`
finds nothing from this run. In the test, a provider named `main` produced
exactly those lines.

### 5. The gateway and its scheduler — CONFIRM

Scheduled jobs run only while the **gateway** runs. Without it, `hermes
cron create` warns "Scheduler is not ready … no gateway serves it", and
nothing ever fires. As root, `loginctl enable-linger hermes` (so the
service survives logout); then as the agent user, `hermes gateway install`.

**Verify:** `systemctl --user is-active hermes-gateway` says `active`, and
`hermes cron status` shows a ticker heartbeat a few seconds old. `ss -tlnp`
shows no new listening port: the gateway talks outward only.

### 6. A page watcher

Copy `8.1/watch_page.py` to `~/.hermes/scripts/`, set `URL` and `NAME`, and
cut the fetched page down to the part you care about (a price, a status
line), because most pages change on every load. Scripts must live in
`~/.hermes/scripts/`. Then:

```
hermes cron create "every 30m" --no-agent --script watch_page.py --deliver local --name <name>
```

`--no-agent` means no model is involved: the script's output **is** the
message. `--deliver local` writes each run to
`~/.hermes/cron/output/<job id>/`; switch to a messaging channel once one
is set up (book 8.2).

**Verify:** `hermes cron run <job id>` twice: both runs are recorded as
"silent (empty output)" (the first one records the baseline). Change what
the script watches (or point it at a page you control), run it again: one
record with the "Page watcher" line. Then leave it alone and confirm the
scheduler fires it on its own.

### 7. Read-only wiki copies through an rrsync jail (optional) — CONFIRM

The agent may read your wiki; it must never be able to change it or reach
the original. So the wiki machine **pushes** a copy, with a key that can
only write into one folder on the VM.

On the wiki machine, make a dedicated key (`ssh-keygen -t ed25519 -f
~/.ssh/wiki_push`). On the VM, create `~/wiki-mirror` and add one line to
the agent user's `~/.ssh/authorized_keys`:

```
command="/usr/bin/rrsync -wo /home/hermes/wiki-mirror",restrict,from="<wiki machine's address>" ssh-ed25519 AAAA… wiki-push
```

`-wo` makes the jail write-only (the book's runs read-write; write-only is
stricter, and `--delete` still works through it), `restrict` turns off
shells, port forwarding and the rest, and `from=` limits the key to one
machine. Schedule the push on the wiki machine (cron or launchd, hourly),
for only the wikis the agent may read:

```
rsync -a --delete -e "ssh -i ~/.ssh/wiki_push -o IdentitiesOnly=yes" <wiki>/ "hermes@<vm>:<name>/"
```

Keep the quotes round `"hermes@<vm>:<name>/"`. In zsh, an unquoted
`$HOST:homelab/` is read as `$HOST` with the `:h` modifier, and becomes a
**local** copy that reports success. That happened during the test.

**Verify, from the wiki machine:**
- the push works, and a file deleted at the source disappears from the VM
  on the next push;
- `ssh -i ~/.ssh/wiki_push hermes@<vm> id` is refused ("does not run
  rsync");
- pulling back (`rsync … "hermes@<vm>:<name>/" /tmp/x`) is refused
  ("reading from write-only server is not allowed");
- a destination with `..` is refused;
- `ssh -i … -N -L 18022:localhost:22 hermes@<vm>` gives "administratively
  prohibited" when used.

Point the agent at the copy (a plugin or the file tools) only after this
passes.

### 8. Write it down

On the VM's wiki page: the release, the provider name and model, the
served context, what the gateway runs, each watcher (job id, schedule,
script), and the jail line with its source machine.

## Updates

`hermes update` follows the branch it installed from; with a pinned
install, re-run the downloaded installer with the new release's commit
(read what changed first). After an update, repeat the step 4 and 5
checks.

## Gotchas (from the book and the test)

- **The provider name `main`.** It collides with a keyword. Name it after
  the server.
- **The context number that looks wrong may be right.** Hermes compresses a
  conversation at half its context limit (`compression.threshold: 0.5` by
  default). The book's agent believes 128K and the server serves 80K,
  which is safe because compression happens at 64K. Read the mechanism
  before "fixing" a number. Hermes logs a warning when your pinned
  `context_length` is below what the server advertises; that one is
  expected.
- **No gateway, no schedule.** A job that never fires looks just like a
  page that never changed. Check `hermes cron status`.
- **A watcher must be silent when nothing changed.** Diagnostics go to
  stderr; anything on stdout becomes a message.
- **A one-shot `hermes chat -Q` exits as soon as it answers**, cancelling
  its own background title request. The model server logs a 500 for it.
  It's harmless.
- **The installer tracks `main` unless pinned.**

## Rollback

Destroy the VM. On the wiki machine, remove the push job and the
`wiki_push` key. On the model server, remove the VM's firewall allowance.
Nothing else depends on the agent.
