# Playbook 4.2 — Zigbee, buttons and a door chime

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need Home Assistant from playbook 4.1, a Zigbee
> coordinator (a USB stick; the book's is based on the TI CC2652 chip), a
> USB extension cable, and some Zigbee devices. For the chime: door
> sensors and a speaker Home Assistant can play to. Pairing means pressing
> buttons on devices, so you do that part. Then say: *"Follow this
> playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 4.2 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's VM ID, coordinator, Wi-Fi
   channels, devices and speakers.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before changing the VM, picking the Zigbee channel, and
   removing any device.
4. **Never remove a Zigbee device with a generic "remove device" call.** In
   ZHA every Zigbee device hangs off one integration entry; a generic
   removal deletes that entry, and with it the whole Zigbee network. Use
   ZHA's own remove, keyed on the IEEE address (step 8).
5. **Never use a Device trigger for a button.** Use `zha_event` and the
   IEEE address (step 4).
6. **Home Assistant changes go through its web interface or its API**,
   never by editing files under `.storage`.
7. **Verify by effect**: a press that toggles a light, a door that speaks.

## Goal: what "done" looks like

- [ ] The coordinator is on a USB extension cable, away from USB 3 ports,
      passed through to the Home Assistant VM, and ZHA drives it.
- [ ] The Zigbee channel is chosen away from the reader's 2.4 GHz Wi-Fi
      channels, before anything is paired.
- [ ] Each button's automation triggers on `zha_event` with its IEEE
      address and the command that button actually sends.
- [ ] Opening any chime door makes the chosen speakers say which door, with
      Piper, locally.
- [ ] Light schedules are one automation with two triggers chosen by id.
- [ ] The reader knows how to retire a Zigbee device (ZHA's remove, then
      dashboards checked).

## Discover first

| What | Why | How to find it |
|---|---|---|
| The Home Assistant VM's ID and Proxmox host | USB passthrough | `qm list` on the host |
| The coordinator's USB ID | Passthrough | `lsusb` on the Proxmox host with it plugged in |
| Other USB serial devices on that host | Many sticks share one USB ID (`10c4:ea60` is a common USB-serial chip) | `lsusb` |
| The 2.4 GHz Wi-Fi channels in use | The Zigbee channel | The access points' settings (the book's: 1 and 11) |
| The devices to pair, and where | Mains-powered ones repeat; pair those first | Ask |
| The speakers for the chime, and which to leave out | The chime's targets | Settings → Devices & services → the media player entities |

## Steps

### 1. Place the coordinator, and pass it through — CONFIRM

Plug the coordinator into the Proxmox host **through a USB extension
cable**, away from USB 3 ports and the case: both radiate interference in
Zigbee's band. Then, on the host:

```
lsusb                                   # find the stick's ID, e.g. 10c4:ea60
qm set <vmid> -usb0 host=<vendor:product>
```

If another device on the host has the same ID, pass the stick by port
instead (`host=<bus>-<port>`, from `lsusb -t`), so the right one goes to
the VM.

**Verify:** `qm config <vmid> | grep usb0` shows it, and inside Home
Assistant, Settings → System → Hardware → *All hardware* lists a serial
device for the stick (`/dev/serial/by-id/...`).

### 2. ZHA, and the channel — CONFIRM the channel

Settings → Devices & services → Add integration → **Zigbee Home
Automation**, and pick the stick's `/dev/serial/by-id/` path. Then, in
ZHA's network settings, set the channel **before pairing anything**.

Zigbee and 2.4 GHz Wi-Fi share the band. Wi-Fi channels 1, 6 and 11 cover
most of it; Zigbee channels run 11–26, 5 MHz apart from 2405 MHz. Choose
one in a gap the reader's Wi-Fi leaves open: the book's Wi-Fi uses 1 and
11, and Zigbee sits on **20**, between them (17 or 18 would be dead
centre of that gap). Changing the channel later can mean re-pairing
everything.

**Verify:** ZHA's configuration page shows the chosen channel.

### 3. Pair — the reader presses the buttons

Add device in ZHA, then put each device in pairing mode. **Mains-powered
devices first** (plugs, bulbs): they're routers and extend the mesh for
the battery ones. Name each device well now (the room and what it is, no
people's names): the chime reads the name out, and renaming later ripples
through automations and dashboards.

**Verify:** each device shows in ZHA with its entities updating (press a
button, open a sensor, and watch its state change).

### 4. Buttons, the durable way

First find out what the button sends. **Developer Tools → Events**, listen
for `zha_event`, press the button once. Note `device_ieee` and `command`.
**Different buttons send different command names for the same gesture**:
the book's Aqara button sends `single` for a short press; its eWeLink
button sends `toggle`.

Then the automation, keyed on that IEEE address and that command:

```
alias: Button - Basement Sofa Lights
mode: single
triggers:
  - trigger: event
    event_type: zha_event
    event_data:
      device_ieee: "<the button's full IEEE address>"
      command: single          # what YOUR button sent
actions:
  - action: switch.toggle
    target:
      entity_id: switch.basement_sofa_lights
```

A *Device* trigger from the automation editor keys on an internal
`device_id`, which changes if the button is re-paired; the automation then
stops, silently. The IEEE address is printed on the hardware and never
changes.

**Verify:** a short press toggles the light; the automation's trace
(Settings → Automations → the automation → Traces) shows the event. Other
gestures (double press, hold) do nothing, unless you add them.

### 5. Piper — the reader, in Settings → Add-ons

Install the **Piper** add-on (local text-to-speech) and start it, then
accept the **Wyoming** integration Home Assistant discovers. To slow the
voice so it carries across a room, set Piper's `length_scale` option above
1 (the book uses **1.5**) and restart the add-on.

**Verify:** Developer Tools → Actions → `tts.speak` with entity `tts.piper`,
a `media_player_entity_id` of one speaker and a message: the speaker says
it.

### 6. The door chime

One automation: a `state` trigger per door sensor, `to: "on"` (open), and a
`tts.speak` per fixed speaker. The sentence is built from the sensor that
fired, so each door's friendly name ("Front door") is what's spoken:

```
alias: Door Open - Chime
mode: parallel
max: 5
triggers:
  - trigger: state
    entity_id: binary_sensor.front_door_opening
    to: "on"
  # one trigger per door sensor
actions:
  - action: tts.speak
    target:
      entity_id: tts.piper
    data:
      media_player_entity_id: media_player.living_room
      message: "{{ trigger.to_state.attributes.friendly_name ~ ' opened' }}"
  # repeat for each fixed speaker
```

Leave portable speakers out on purpose, so the chime doesn't follow
someone onto the patio. `mode: parallel` lets two doors opening together
both speak.

**Verify:** open each door in turn; the chosen speakers say that door's
name, and the left-out speaker stays quiet. Pull the internet connection
(or block the Home Assistant VM's outbound traffic) and try again: it
still speaks, because nothing leaves the house.

### 7. Light schedules, the tidy way

"On at sunset, off at 11 pm" is one automation, not two: two triggers, each
with an id, and a `choose` on the id:

```
alias: Bedroom LED - Sunset On, 11pm Off
mode: single
triggers:
  - trigger: sun
    event: sunset
    id: sunset
  - trigger: time
    at: "23:00:00"
    id: bedtime
actions:
  - choose:
      - conditions: [ { condition: trigger, id: sunset } ]
        sequence: [ { action: light.turn_on, target: { entity_id: light.bedroom_led } } ]
      - conditions: [ { condition: trigger, id: bedtime } ]
        sequence: [ { action: light.turn_off, target: { entity_id: light.bedroom_led } } ]
```

**Verify:** after the next sunset and the next 23:00, the light followed,
and each trace shows the branch that ran. (*Run actions* in the editor
fires no trigger, so neither branch runs: that isn't a fault.)

### 8. Retiring a Zigbee device — CONFIRM each one

When a device leaves the house, remove it the same day, with ZHA's own
remove, keyed by its IEEE address: the device's page → ⋮ → *Remove*, or the
action `zha.remove` with `ieee: "<address>"`. This works even if the
device is already in a drawer. **Never** a generic "remove device" (rule 4).

Then search every dashboard and automation for its entities. A Zigbee
device that simply disappears doesn't go *unavailable*: its entities keep
their last value, which reads exactly like live data.

**Verify:** the device is gone from ZHA's device list, every other Zigbee
device still reports, and no dashboard card shows its old entities.

## Gotchas (from the book and the author's lab)

- **The plug that kept reporting after it was gone.** A retired plug's
  power reading looked normal for weeks on a dashboard. Remove retired
  devices in ZHA, then check dashboards, not just automations.
- **Command names differ per device**, and come from the device's quirk,
  not ZHA. Never copy one button's `command` to another's automation.
- **A trigger with `device_id` breaks on re-pair.** IEEE address only.
- **Bursts of `zigpy` "Data is too short" errors** in the log are usually
  devices declining ZHA's routing-table scan, and cosmetic. Worry if
  they're continuous or devices actually drop.
- **If devices drop, move the channel toward the middle of the Wi-Fi gap**,
  not pre-emptively: re-channelling an established network can force
  re-pairing.

## Rollback

Disable or delete the automations. To remove Zigbee entirely: delete the
ZHA integration (this time deleting the whole entry is the intent), then
`qm set <vmid> -delete usb0` on the Proxmox host.
