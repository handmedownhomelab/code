# Playbook 4.4 — Your own certificate authority

> **For the reader.** Read this whole file before you give it to your AI
> assistant. Then say: *"Follow this playbook. Ask me before every step
> marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 4.4 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's names, addresses and CA name are
   the author's. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs
   software, changes trust on a device, or deletes anything is a CONFIRM
   step even if this file forgot to mark it.
4. **Get install steps from Smallstep's docs**
   (https://smallstep.com/docs/step-ca/) and acme.sh's
   (https://github.com/acmesh-official/acme.sh), not from memory.
5. **Secrets:** the CA's key password is generated on the CA machine into a
   root-only file and never printed. Never copy a private key off the
   machine it was made on.
6. **Verify by effect**: a certificate is good when a client that trusts
   only your root connects with no error, not when a command says "ok".
7. If the reader keeps a homelab wiki, record the CA's name, URL, root
   fingerprint and lifetimes there (never the password).

## Goal: what "done" looks like

- [ ] A CA answers `ok` at `https://<ca-name>:8443/health`, running as its
      own service user and starting at boot.
- [ ] The root fingerprint is written down in two places the reader controls.
- [ ] One service has a certificate from the CA that lasts **90 days** and
      renews itself, and a client that trusts the root reaches it with
      `ssl_verify_result` `0`.
- [ ] The reader's own computer and phone trust the root (step 9).
- [ ] The CA's directory, including its database, is in a backup.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Where the CA will run | Its own small container or machine; it does one job | Ask; the book uses a 1-core, 512 MB container |
| The CA's name and address | Every client uses it, e.g. `ca.home.arpa` | Ask; give it a local DNS record (book 4.1) and a reservation (1.5) |
| A display name for the CA | Shown in certificate details | Ask, e.g. "Home Lab CA" |
| The first service to get a certificate | Something with a web interface | Ask; the second Pi-hole or the first one is a good start |
| Whether that service already uses port 80 | The simple ACME method needs port 80 free during issuing | Check with `ss -ltn` on that machine |
| Where the reader keeps passwords | The CA password needs a second copy off the machine | Ask |

## Steps

### 1. Install from Smallstep's repository — CONFIRM

On the CA machine, add Smallstep's apt repository as their docs describe and
install `step-ca` and `step-cli` from it. **Use the repository, not
downloaded `.deb` files.** Without the repository apt can never tell you a
newer version exists (the book's 4.4 story).

**Verify:** `step-ca version` and `step version` print versions, and
`apt-cache policy step-ca` shows the Smallstep repository as the source.

The package installs the programs only: no service user, no service. Steps
2 and 4 add those.

### 2. A service user and the key password

Following Smallstep's *Running step-ca as a daemon* guide: create a system
user `step` with home `/etc/step-ca`. Then generate a long random password
into `/etc/step-ca/password.txt`, mode 600. Do not print it.

**Ask the reader to store a second copy** in their password manager. They
can read it themselves with `ssh -t` and `cat`. Without it, a lost
container and a lost backup mean a new CA and re-trusting every device.

### 3. Create the CA — CONFIRM

Run `step ca init` with `STEPPATH=/etc/step-ca`, non-interactively, with:
the reader's display name, the CA's DNS name, address `:8443`, a JWK
provisioner (the book calls it `admin`), the password file, and the
**`--acme`** flag to add the ACME provisioner. Initializing straight into
`/etc/step-ca` avoids the docs' move-and-edit step. Then make the `step`
user own `/etc/step-ca`.

Why port 8443: the book explains. If the reader wants 443, the docs'
service file already grants the capability.

**Verify:** `/etc/step-ca/config/ca.json` exists, lists a JWK and an ACME
provisioner, and its database path is `/etc/step-ca/db`.

### 4. Run it as a service — CONFIRM

Install the systemd unit from Smallstep's daemon guide as-is (it runs as
`step`, reads `password.txt`, and is heavily sandboxed). It works unchanged
in an unprivileged Proxmox container with `nesting=1`. Enable and start it.

**Verify:**
- `systemctl is-active step-ca` is `active`, and it's enabled.
- `step ca health --ca-url https://<ca-name>:8443 --root /etc/step-ca/certs/root_ca.crt` prints `ok`.
- `step certificate fingerprint /etc/step-ca/certs/root_ca.crt`: show it to
  the reader and have them record it with the password.

### 5. Set the certificate lifetimes — CONFIRM

**This is the step the defaults get wrong for a home lab.** A new
provisioner issues certificates valid for **24 hours**. Set:

- the **ACME** provisioner to 90 days (`--x509-default-dur=2160h
  --x509-max-dur=2160h` with `step ca provisioner update`);
- the **JWK** (`admin`) provisioner, used for hand-issued certificates, to
  one year (`8760h` for both).

Make sure `step` still owns `/etc/step-ca`, then reload the service (it
re-reads its config on `systemctl reload`).

**Verify:** the two provisioners' `claims` in `ca.json` show the new
durations, and the service is still active.

### 6. Trust the root on the service machine

Fetch the root from `https://<ca-name>:8443/roots.pem`. Fetching it skips
verification, since nothing trusts it yet, so **check its SHA-256
fingerprint against the one from step 4** before trusting it. Then add it to
the system store (`/usr/local/share/ca-certificates/`, then
`update-ca-certificates`).

**Verify:** `curl -s -o /dev/null -w '%{ssl_verify_result}'
https://<ca-name>:8443/health` prints `0` on the service machine.

### 7. A self-renewing certificate for the service — CONFIRM

1. Install acme.sh from its official installer. Download it to a file and
   show the reader before running it. It adds its own renewal cron job.
2. **Free port 80 if the service uses it.** A fresh Pi-hole (playbook 4.1)
   serves its web interface on 80 and 443, and acme.sh's standalone mode
   then fails with "port 80 … Please stop it first". (It still exits 0, so
   read its output.) On Pi-hole, make the web interface HTTPS-only:
   `pihole-FTL --config webserver.port "443os,[::]:443os"`. Pi-hole keeps
   serving on 443 with its own certificate until step 3 replaces it. The
   admin page is then `https://<name>/admin` only.
3. Issue: `acme.sh --issue -d <service-name> --standalone --server
   https://<ca-name>:8443/acme/acme/directory`, with a **reload command**
   that puts the certificate where the service expects it and restarts the
   service. For Pi-hole the reload command is a small script that writes
   `fullchain.cer` followed by the key into `/etc/pihole/tls.pem` (owned by
   `pihole`, not world-readable), then restarts `pihole-FTL`. Write the new
   file first and move it into place, so Pi-hole never reads half a file.

**Verify:**
- `openssl x509 -noout -dates` on the deployed certificate shows about **90
  days** (if it shows one day, step 5 didn't take).
- From **another** machine that trusts the root:
  `curl -s -o /dev/null -w '%{ssl_verify_result}' https://<service-name>/`
  prints `0`.
- `openssl s_client -showcerts` against the service shows the leaf issued
  by your intermediate, and the intermediate by your root.
- `crontab -l` shows acme.sh's cron entry. Its domain config shows the next
  renewal **30 days after issue** (`Le_NextRenewTimeStr`): it renews with
  about 60 days to spare.
- Force one renewal (`acme.sh --renew … --force`) and check the reload
  command ran and the service still verifies.

### 8. A certificate by hand, for things that can't run ACME

On the CA machine: `step ca certificate <name> <name>.crt <name>.key
--provisioner admin --provisioner-password-file /etc/step-ca/password.txt`.

**Verify:** `step certificate verify <name>.crt --roots
/etc/step-ca/certs/root_ca.crt` succeeds and the certificate lasts a year.
Tell the reader to put the renewal date in their calendar. Move the key to
its service securely and delete the CA's copy of it.

### 9. Trust the root on the reader's devices — the reader does this

Give the reader the steps for each device. The book's table lists macOS,
Linux, the browsers that keep their own store, and iPhone/iPad. **On iPhone
it's two steps:** install the profile, *then* Settings → General → About →
Certificate Trust Settings → enable full trust. Have them check each device
with the `curl` test above or a page that loads with no warning.

## Gotchas (from the book and the test)

- **Defaults are 24-hour certificates.** Fine for Smallstep's intended use,
  surprising at home (step 5).
- **acme.sh standalone needs port 80 free**, and reports failure while
  exiting 0.
- **"It still says Not Secure" is almost always the device**, not the
  certificate: the root isn't trusted there yet, or on iPhone full trust
  isn't turned on.
- **Two roots with similar names?** Ask a live connection which root it
  chains to (`openssl s_client -showcerts`, the last `i:` line), not the
  label.
- **`openssl s_server -cert` sends only the leaf.** If you test with it,
  add `-cert_chain`, or clients report "unable to get local issuer
  certificate" (`ssl_verify_result` 20) for a perfectly good certificate.
- **The database is in `/etc/step-ca/db`**, not `/var/lib`: make sure the
  backup covers `/etc/step-ca` whole.
- **Upgrading later:** read the changelogs, record both fingerprints,
  snapshot, upgrade, then issue a ten-minute test certificate and verify it
  against the root (book 4.4 has the routine).

## Rollback

Before any device trusts the root: delete the container. After: also remove
the root from each device's trust store, or it stays trusted.
