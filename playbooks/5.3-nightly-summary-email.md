# Playbook 5.3 — The nightly house-summary email

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need Home Assistant from playbook 4.1 and a way to send
> mail: your provider's SMTP login, or the relay from playbook 3.3. The
> dashboards from 5.1 and 5.2 help (daily energy meters, host sensors) but
> aren't required: a section with nothing to show is left out. The starter
> automation is `5.3/nightly-summary.yaml` in this repository. Then say:
> *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 5.3 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's own entities. The starter
   finds batteries, leak sensors and daily energy meters by device class;
   only the four lists marked `EDIT` need names.
2. **Never put a password in the automation or in chat.** The SMTP login
   lives in the SMTP integration's own configuration.
3. **CONFIRM** before adding the SMTP integration, creating the automation,
   and before every test that changes a device's state.
4. **If you edit through the Home Assistant MCP server** (playbook 5.5),
   follow its write loop: read fresh, show the change, write, **read it
   back**.
5. **Verify by effect**: a mail in the reader's inbox, not the action's
   "success".

## Goal: what "done" looks like

- [ ] An SMTP notify entity that delivers mail to the reader.
- [ ] One automation, a **time trigger at 23:50**, one `smtp.send_message`
      action whose `html:` is a Jinja template.
- [ ] A banner at the top: red with a count and a list when anything needs
      the reader, green "All systems normal" otherwise.
- [ ] **Every alert in the banner has fired once on purpose** and been seen
      in a real mail.
- [ ] Batteries listed from `device_class: battery`, with a skip list, and a
      battery that stops reporting **flagged**, not dropped.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Home Assistant version | `last_reported` in templates needs 2024.3 or later | Settings → About |
| Mail account | The SMTP integration | Ask the reader: host, port, encryption, sender, recipient. The password is typed by the reader into Home Assistant, never into chat |
| Battery sensors | The battery section and its skip list | `{{ states.sensor | selectattr('attributes.device_class','defined') | selectattr('attributes.device_class','eq','battery') | map(attribute='entity_id') | list }}`; ask which to skip (phones, watches, any value the reader doesn't trust) |
| Daily energy meters | The ranked energy list | 5.1's utility meters: energy sensors with a `next_reset` attribute |
| Host sensors | The systems lines | 5.2's Glances or Proxmox CPU, RAM and disk sensors, one triple per host |
| Other things to watch | The `checks` list | A garage door, a backup-problem sensor, a recording drive: ask the reader |

## Steps

### 1. Mail: the SMTP integration — CONFIRM

Add the **SMTP** integration with the reader's mail details (or the 3.3
relay: its address, port 25, no encryption, no login). Name it for the
recipient ("email tom").

Since 2026, SMTP is set up in the UI: Settings → Devices & services → **Add
integration → SMTP**: sender, server, port, encryption (`starttls`, `tls`
or `none`), and the login if the server needs one. Then, on the new entry,
**Add recipient**: each recipient is its own notify entity, named from the
sender and the recipient's name (sender `ha@example.com` with recipient
"email tom" gives `notify.ha_example_com_email_tom`). Read the entity ID
from Settings → Entities rather than guessing it.

**Verify:** a notify entity for it exists (Settings → Entities, domain
`notify`). Developer tools → Actions → `notify.send_message` with that
entity and a one-line message: the mail arrives.

### 2. Why `smtp.send_message`, not `notify`

The generic `notify.send_message` takes only a title and a message. HTML and
attachments need **`smtp.send_message`**, with fields `title`, `message`,
`html` and `attachments`. (The old per-integration `notify.<name>` actions
are deprecated and stop working in 2027.3.)

### 3. The automation — CONFIRM

Create a new automation, *Edit in YAML*, and paste
`5.3/nightly-summary.yaml`. Set `target.entity_id` to step 1's notify entity
and fill the four `EDIT` lists from *Discover first*. Leave a list empty
(`[]`) if it doesn't apply. Save.

The design: **every alert is computed once, at the top**, into a Jinja
`namespace`, and the banner, the sections and the counts all read from it.
Add a new alert by appending to `ns.alerts` in that block; nowhere else.

**Verify:** the automation shows in the list with its trigger at 23:50.

### 4. Watch it render — no mail needed

Developer tools → **Template**: paste the `html:` value (everything after
`html: >-`, unindented). The right side renders it live with today's
values; every edit re-renders.

**Verify:** the rendered output has no `Error` and the batteries count
matches *Discover first* minus the skip list.

### 5. Send one now

Open the automation → ⋮ → **Run actions**.

**Verify:** the mail arrives, renders as HTML (not raw tags), and the
banner is green or lists only real problems.

### 6. Make every alert fire once — CONFIRM each

An alert that can't fire is worse than none, because you stop looking. For
each alert type, cause it on purpose, run the automation, and see it in the
mail:

| Alert | How to make it fire |
|---|---|
| Water leak | A damp cloth across a leak sensor's contacts |
| Battery low | Temporarily change the low threshold in the template from `10` to `101`, run, change it back |
| Battery not reporting | Take the battery out of one device, wait until it shows unavailable |
| A `checks` entry | Open the garage door (or the thing it watches) |
| Freshness (`fresh`) | Temporarily set its hours to `0` |
| Host offline | Temporarily point one host's CPU sensor at a name that doesn't exist |
| Update pending | Usually true sometime; otherwise skip and say so |

**Verify:** each alert appeared in a real mail, then the banner went green
again once it was undone. Note any you couldn't fire.

## Gotchas (from the book and the test)

- **An undefined variable in Jinja is empty, not an error.** A banner that
  tests a misspelled list says "all normal" forever. That's why every alert
  goes through `ns.alerts` and why step 6 exists.
- **A hand-typed battery list rots.** Devices get replaced and renamed; a
  missing entity reads `unknown` and silently drops out. Select by
  `device_class`, skip by name.
- **A battery that dies hard goes unavailable.** Skipping unavailable
  batteries hides exactly the failure you want; flag them.
- **Freshness uses `last_reported`**, not `last_changed`: a value that
  hasn't changed in a week can be perfectly healthy (5.4).
- **Home Assistant is the wrong place to alert about Home Assistant.** If
  it is down, there is no mail. Its own outage is the independent monitor's
  job (3.1).
- **A wrong notify entity "succeeds".** `notify.send_message` aimed at an
  entity that doesn't exist returns success and sends nothing; only a
  warning in the log says so. Check the inbox, not the action's result.
- **Name the daily meters.** The energy list shows each meter's name, so a
  meter left as `plug_7_today` reads that way in the mail.

## Rollback

Delete the automation and, if it was added only for this, the SMTP
integration. Nothing here changes a device.
