# Playbook 2.1 — The LLM wiki

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need a workstation with an AI assistant that can read and
> write files and run commands (the book uses Claude Code, set up in 2.3;
> any capable assistant works), git, and SSH to at least one host. Then
> say: *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 2.1 describes. You will also be the wiki's
> maintainer afterwards. Follow the rules below for the whole session.

## Rules for the assistant

1. **Discover, don't assume.** Every fact in a page comes from the reader or
   from a host, never from what a typical homelab looks like. Mark anything
   unverified as unverified.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** the schema with the reader before writing pages from it, and
   before restructuring or deleting anything in an existing notes folder.
4. **Read-only on the hosts.** Filling in pages means reading (`lsblk`,
   `ss -tlnp`, `systemctl list-units`), never changing.
5. **No secrets in any page**: no passwords, tokens, keys, or the contents of
   files that hold them. The path to a secret is fine.
6. **Verify by effect**: the checks in step 6 run against the files, not
   against your memory of what you wrote.

## Goal: what "done" looks like

- [ ] A wiki folder with `raw/`, `wiki/` (with `system/`, `concept/`,
      `runbook/`, `incident/`), `wiki/index.md`, `wiki/todo.md` and
      `log.md`, in git.
- [ ] A `CLAUDE.md` schema at its root that the reader has read and agreed.
- [ ] A system page for each host, filled from the host itself, each with a
      Gotchas section.
- [ ] Every page has `type:` and `last_updated:`, is listed in the index,
      and every change has a log entry.
- [ ] One query answered from the pages, with links, and one lint pass.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Where the wiki will live | The book uses `~/wiki/homelab-wiki`; 2.2's sync scripts look under `~/wiki/` | Ask |
| Existing notes | Raw material for the first ingest; never deleted | Ask; a notes app export, a README, a text file of IPs |
| The hosts, and how to reach each | The first system pages | Ask; the host list in `~/.claude/CLAUDE.md` (2.3) |
| The reader's editor or reader app | Obsidian reads the folder as is; any editor works | Ask |
| Whether the AI loads `CLAUDE.md` from the folder it starts in | The schema only works if it's read | Claude Code does; for other assistants, find their equivalent and tell the reader |

## Steps

### 1. The folder

Create the layout and make it a git repository (book 2.2 adds a hub and
clones; for now it's local):

```
<wiki>/
├── CLAUDE.md        the schema (step 2)
├── log.md           append-only history, newest at the bottom
├── raw/             sources: articles, exports, notes (never edited)
├── scripts/         canonical copy of every script, mirroring its host path
└── wiki/
    ├── index.md     every page, one line each
    ├── todo.md      open items only, each linking to its page
    ├── archive.md   resolved to-do items
    ├── system/      one page per host or major service
    ├── concept/     cross-cutting topics
    ├── runbook/     how-to procedures
    └── incident/    what broke
```

Put an empty `.gitkeep` file in every folder that has nothing in it yet:
git doesn't track empty folders, so without one a clone (book 2.2) arrives
without `raw/` or `incident/`. Add `.gitattributes` with the single line
`log.md merge=union` now; 2.2 explains why. Copy any existing notes into
`raw/` unchanged.

**Verify:** `git -C <wiki> status` works, and after the first commit (end
of step 2) `git clone -q <wiki> /tmp/wiki-check && find /tmp/wiki-check -type d -not -path '*/.git*'`
lists the root and all seven folders. Delete `/tmp/wiki-check`.

### 2. The schema — CONFIRM

Write `<wiki>/CLAUDE.md` from this template (Appendix C.1). Walk the reader
through it and change what they want changed. **This file is the product:**
without it, an AI in a folder of markdown is still just a chatbot.

```
# CLAUDE.md — Homelab wiki schema

This file tells the AI how this wiki works. It maintains the pages; I read
them. We change this file together as the lab grows.

## Layout
homelab-wiki/
├── CLAUDE.md        this file
├── log.md           append-only history, newest at the bottom
├── raw/             sources: articles, exports, notes (never edited)
├── scripts/         canonical copy of every script, mirroring its host path
└── wiki/
    ├── index.md     every page, one line each
    ├── todo.md      open items only, each linking to its page
    ├── archive.md   resolved to-do items
    ├── system/      one page per host or major service
    ├── concept/     cross-cutting topics
    ├── runbook/     how-to procedures
    └── incident/    what broke

## Page types
Every page has frontmatter: `type:` and `last_updated:` (YYYY-MM-DD).
- system/<host>.md: Hardware · OS and access · Services (with ports) ·
  Network · Storage · Recent changes (5 bullets max) · Gotchas · Related
- concept/<topic>.md: What it is · How it works here · Configuration ·
  Gotchas · Related
- runbook/<verb-object>.md: When to use · Prerequisites · Steps (exact
  commands) · Verification · Rollback
- incident/<YYYY-MM-DD>-<slug>.md: Summary · Symptoms · Root cause · Fix ·
  Prevention

## Rules
- Session start: read this file, wiki/index.md, wiki/todo.md, and the last
  20 lines of log.md. Then read only the pages the index points to.
- Every change: update the page, bump last_updated, add a log.md entry
  (`## [YYYY-MM-DD] <op> | <title>`), commit, push. Same commit.
- One home per volatile fact (IPs, ports, versions, model names). Other
  pages link to it instead of retyping it.
- History is frozen: never edit log.md entries, incidents, or dated bullets.
- No secrets in any page. Paths to secrets are fine.
- Commands must survive a copy-paste: no placeholders in runnable lines,
  no trailing comments, quote paths with spaces. Say which host to run on.
- Before deploying a script from scripts/, diff it against the live copy.
- Verify changes by reading their effect. Record how you verified.

## Operations
- Ingest: read the source in raw/, summarize what matters, update every
  affected page, log it.
- Query: answer from the pages, with links. Offer to file a valuable answer
  as a new page.
- Lint: find contradictions, stale claims, orphan pages, todos that are
  done. Log it.
```

Then create `wiki/index.md` (a heading per page type, empty lists),
`wiki/todo.md`, `wiki/archive.md`, and `log.md` with its first entry:

```
## [YYYY-MM-DD] schema | wiki created
```

Commit.

**Verify:** start a new session **in the wiki folder** and ask *"What do
you do at the start of every session here, and what goes in a log entry?"*
It answers from `CLAUDE.md` (the four files it reads; the
`## [date] op | title` format). If it doesn't, the assistant isn't loading
the schema; fix that before going on.

### 3. The first ingest: one system page per host

In that session, give the AI the book's first prompt:

*"Read CLAUDE.md and create a system page for each host in my global
rules. SSH to each one and fill in hardware, OS, services with ports, and
disks. Put anything surprising under Gotchas. Log it."*

If the reader has notes in `raw/`, add: *"Then ingest everything in raw/:
tell me what matters before you change pages."*

**Verify:**
- One `wiki/system/<host>.md` per host, each with frontmatter and every
  section the schema names, Gotchas included (it may say "none yet").
- Each page's facts came from the host: pick two values (a disk size, a
  listening port) and check them by hand on the host.
- `wiki/index.md` lists every new page with a one-line description.
- `log.md` has a new entry in the schema's format, in the same commit as
  the pages (`git show --stat HEAD`).
- `grep -rniE 'password|token|secret|BEGIN .*PRIVATE' <wiki>/wiki` finds
  nothing that is an actual secret.

### 4. The first query

Ask the book's question: *"Read the index and tell me which host runs my
DNS, which runs the reverse proxy, and what breaks if the first Proxmox
host reboots."* (Adjust to the reader's lab.)

**Verify:** watch what the AI does before it answers. It opens
`wiki/index.md`, then the pages it points to, and its answer links them. If
it answers from general knowledge instead, the session-start rule isn't
being followed: fix the schema, not the answer. If the answer is worth
keeping, it offers to file it as a page.

### 5. Lint

Ask: *"Lint the wiki."* The AI looks for contradictions, stale claims,
pages nothing links to, and to-do items that are actually done, and logs
the pass.

Then run the mechanical half yourself, from the wiki folder, so the result
doesn't depend on the AI:

```
for f in wiki/*/*.md; do head -6 "$f" | grep -q '^type:' || echo "no type: $f"; head -6 "$f" | grep -qE '^last_updated: [0-9]{4}-[0-9]{2}-[0-9]{2}' || echo "no last_updated: $f"; grep -qF "$(basename "$f" .md)" wiki/index.md || echo "not in index: $f"; done
```

```
grep -rhoE '\[\[[^]|#]+' wiki CLAUDE.md | sed 's/^\[\[//' | sort -u | while read -r l; do [ -e "$l.md" ] || [ -e "wiki/$l.md" ] || find wiki -mindepth 2 -maxdepth 2 -name "$l.md" | grep -q . || echo "dangling: [[$l]]"; done
```

Both work in bash and zsh. The first catches pages missing `type:` or
`last_updated:` and pages the index doesn't list; the second, wikilinks to
pages that don't exist.

**Verify:** both print nothing. Then break it on purpose: remove one page's
`last_updated:` line, add `[[no-such-page]]` to the index, and create an
unlisted page; the commands report all three. Put things back
(`git checkout -- wiki`, and delete the extra page).

### 6. A reader (optional)

Open the folder as an Obsidian vault, or in any editor. In Obsidian the
graph view shows pages nothing links to as isolated dots: usually a page the
AI created and never wired in.

**Verify:** the wikilinks between pages are clickable, and the graph has no
isolated dots, or the reader knows why each one is there.

## Gotchas (from the book and the test)

- **The schema is the product.** Most problems with an LLM wiki are schema
  problems: if the AI keeps doing something wrong, add a rule; don't keep
  correcting the output.
- **Read before acting.** The session-start rule (schema, index, to-dos,
  last 20 log lines) is cheap, and it's the difference between an assistant
  that knows what happened yesterday and one that doesn't.
- **One home per volatile fact.** An address typed on ten pages is nine
  future contradictions. Pages link to the one page that holds it.
- **History is frozen.** A version named in an incident write-up is correct
  forever. Lint must not "fix" it.
- **The Gotchas sections are the most valuable text in the wiki.** "Don't
  SSH to the proxy's name for the Proxmox host" lives there, and it's what
  stops the AI repeating a mistake.
- **A script has two copies, and they drift.** The book's war story: a
  model name was changed on a host, the wiki copy wasn't, and the next
  deploy from the wiki put the old name back. Copy host edits back to
  `scripts/` in the same session, and diff before deploying.
- **The AI fills in what it can read, and says what it couldn't.** In the
  test, a host where sudo needs a password got a page whose Gotchas listed
  what wasn't checked (firewall, cron) and why. That's the behaviour to
  ask for; a page that guesses is worse than a short one.
- **Old is worse than broken.** A copy of the wiki nobody pulled answers
  confidently from yesterday. Book 2.2 keeps every machine current.

## Rollback

The wiki is a folder of markdown in git. Delete the folder to remove it;
nothing outside it was changed (step 3 only reads the hosts).
