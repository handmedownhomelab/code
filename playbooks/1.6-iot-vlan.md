# Playbook 1.6 — An IoT VLAN

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need a gateway and access points that support VLANs and
> zone or inter-network firewall rules (the book uses UniFi), and, for a
> wired device, a managed switch. If you keep reservations as code (1.5),
> have the table and loader handy. Then say: *"Follow this playbook. Ask
> me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 1.6 describes. Most changes happen in the
> gateway's interface, so you will plan, tell the reader what to set, and
> check the results from real devices. Follow the rules below for the whole
> session.

## Rules for the assistant

1. **Discover, don't assume.** Every network, address and device here is
   the book's example. Build the device list from the reader's gateway, not
   from what a typical house has.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before every change to the gateway, the Wi-Fi, a switch
   port, or the reservation table's `--apply`.
4. **Test from the right place.** Containment is tested from a device *on*
   the IoT network; reachability from the main side is tested from a
   **wired** host. Never conclude "blocked" from a laptop on Wi-Fi.
5. **No Wi-Fi passwords, keys or controller credentials** in commands,
   pages or the chat.
6. **Verify by effect**: device addresses, Home Assistant's entities, and a
   probe matrix with an expected answer on every row.

## Goal: what "done" looks like

- [ ] An IoT network (VLAN) exists, with its own subnet and DHCP.
- [ ] The house's existing Wi-Fi name is bound to it, and a new Wi-Fi name
      on the main network carries the few devices that need full access.
- [ ] Firewall: IoT reaches the internet, the DNS servers, and Home
      Assistant's MQTT broker, and nothing else on the main network; the
      main network reaches IoT; IoT can't reach the gateway's management.
- [ ] Every IoT device with a reservation holds its new address; Home
      Assistant shows them available.
- [ ] A containment test, run from a device on the IoT network, matches the
      expected answer on every row.
- [ ] A written decision about cameras (the book's: no camera VLAN, an
      internet block instead).

## Discover first

| What | Why | How to find it |
|---|---|---|
| Every client, and how it connects (wired port or Wi-Fi name) | A Wi-Fi device takes its VLAN from the Wi-Fi name; a wired one from its switch port | The gateway's client list; export it |
| Which devices need full access (laptops, phones, a TV that casts to phones) | They move to the new trusted Wi-Fi name | Ask; group the list with the reader |
| What talks to the gadgets, and how | Home Assistant, a video recorder, casting | HA's integrations; which ones are configured by IP |
| The DNS servers and the MQTT broker's address and port | The allow rules | Book 6.1, 4.x; the gateway's DHCP settings |
| Cameras: wired or Wi-Fi, and where they record | Decides whether a camera network is worth it (step 1) | Client list; the recorder's channel list |
| A device that can join the IoT network and has a shell | The containment test (step 7) | Ask: a Raspberry Pi is ideal; a laptop on the IoT Wi-Fi works if nothing else does |
| A wired host on the main network with a shell | The reachability test | Ask |

## Steps

### 1. Decide what moves, and write down what doesn't — CONFIRM

Sort every client into: **stays on the main network** (servers, network
gear, laptops, phones), **IoT** (plugs, bulbs, appliances, sensors, cloud
speakers), and anything with its own reason. Then decide cameras on
evidence, as the book did: how many are actually wired, what the goal is
(usually "no internet"), and how much traffic flows between cameras and the
recorder (all of it would be routed through the gateway if they were split).
**Cameras and their recorder stay on the same network**, whatever you
decide.

**Verify:** the reader has a written list (a wiki page, book 2.1) with each
device's group and the reason for any exception, and a sentence saying why
any canceled network was canceled.

### 2. Create the IoT network — CONFIRM

In the gateway: a new network, its own VLAN ID and subnet (the book:
`10.20.50.0/24`, VLAN 50), DHCP on, DNS servers the same as the main
network's. Don't bind any Wi-Fi to it yet. If you keep reservations as
code, add the subnet to `MANAGED_CIDRS` in the loader (1.5).

**Verify:** the gateway lists the network; `./ux7_load_reservations.py
--list` accepts a row in the new subnet without the "OUTSIDE every managed
network" warning.

### 3. The trusted Wi-Fi name first — additive

Create a **new** Wi-Fi name on the **main** network, with the same radio
and security settings as the existing one, and a fresh password. Move the
full-access devices to it by hand, one at a time. Nothing else changes yet,
so this step can sit for days.

**Verify:** each moved device is on the new name, on its old address (its
reservation is per MAC, so it follows), and reaches everything it did.

### 4. The firewall, before anything moves — CONFIRM

Create rules **in this order** (UniFi orders custom rules by creation, not
by the index you type):

1. IoT → the DNS servers: allow (DNS, and ping for health checks).
2. IoT → the MQTT broker's address, its port: allow.
3. IoT → anything else on the main network: block.
4. Main network → IoT: allow (so Home Assistant can reach the devices).
5. IoT → the gateway itself: allow DHCP, DNS, NTP, ping and mDNS, then
   block the rest. A new zone's default often allows everything to the
   gateway, management interface included.

IoT → internet stays allowed. For cameras that must not reach the internet,
add an address group and one block rule (the book's answer instead of a
camera VLAN).

**Verify:** read the rules back from the gateway, not from memory: each
exists, in this order, with the block rules last within their zone pair.
Hit counters can read zero for several minutes after a change; don't take
a fresh zero as proof of anything.

### 5. The reservation rows — table only

For every IoT device that needs a stable address (anything Home Assistant
or another host reaches by IP), write its new row in the table, in the IoT
subnet. **Don't `--apply` yet:** a reservation belongs to one network, so
applying it now would remove the reservation the device relies on today.

**Verify:** `./ux7_load_reservations.py --list` shows the new rows with no
preflight problems. Write down each row's old address too (for rollback).

### 6. The move: rebind the Wi-Fi name — CONFIRM

Change the house's **existing** Wi-Fi name from the main network to the
IoT network. That one setting moves every device on it, with no password
re-entry. Then load the reservations:

```
./ux7_load_reservations.py --username <local-admin>
./ux7_load_reservations.py --username <local-admin> --apply
```

**Verify:**
- The client list shows the devices on the IoT network with IoT addresses.
  Check **addresses**, not reachability: a device holding a stale lease
  keeps working on its old address and is not moved yet. Power-cycle the
  stragglers.
- `--apply` may report `FixedIpAlreadyUsedByClient`: while devices flooded
  in, some took pool addresses reserved for others. Turn the Wi-Fi name off
  and on (every device re-requests), and run `--apply` again. Two or three
  passes converge; the loader is idempotent.
- A final dry run reports `CREATE=0, UPDATE=0, ERROR=0`.
- Home Assistant: the moved devices' entities are available. (In the
  book's lab, integrations that track devices by MAC re-pointed themselves.
  Any that use a fixed IP need reconfiguring.)

### 7. Containment, from a device on the IoT network

On the test device joined to the IoT network, with a shell (it needs `nc`
from netcat-openbsd, `nslookup` from dnsutils, and `curl`), check every
row and compare with the expected answer. Replace each `<…>:port` with the
reader's address and port; the loops work in bash and zsh:

```
for t in <proxmox>:8006 <gpu-tower>:22 <home-assistant>:8123 <gateway>:443; do nc -z -w 3 ${t%:*} ${t#*:} 2>/dev/null && echo "OPEN    $t (expected: blocked)" || echo "blocked $t"; done
```

```
for t in <dns-1>:53 <mqtt>:1883; do nc -z -w 3 ${t%:*} ${t#*:} 2>/dev/null && echo "open    $t" || echo "BLOCKED $t (expected: open)"; done
```

```
nslookup example.com <dns-1>
```

```
curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
```

**Verify:** every "expected: blocked" row prints `blocked`, DNS and MQTT
print `open`, the lookup answers, and the internet request returns 200.
Then, from a **wired** host on the main network, `nc -z -w 3` to a moved
device's open port succeeds (main → IoT is allowed).

### 8. A wired device — plan a cable pull

To move a wired device, change its switch port's VLAN, then unplug its
cable for ten seconds. Changing the port doesn't drop the link, so the
device keeps its old address and is unreachable from both networks until
it asks again.

**Verify:** the device appears on an IoT address in the client list.

## Gotchas (from the book and the test)

- **Enforcement needs a routed boundary.** Devices on the same network talk
  to each other directly; no firewall rule touches that traffic. A
  separate network is the only way to put the firewall between them.
- **Move the name, not the devices.** Rebinding the existing Wi-Fi name
  moved about 40 devices with one setting. The earlier plan, a new name for
  70 devices one by one, died of its own cost.
- **The restricted side renumbers.** If the trusted devices moved to the
  new network instead, the gadgets would still share a network with the
  servers. And a device that falls back to the old Wi-Fi name lands in the
  restricted network: the safe direction.
- **Reservations go inert off-network.** Apply the IoT rows only after the
  move, or you strip the reservations the devices depend on until then.
- **Test from the right vantage point.** On cutover night every TCP port on
  the IoT network looked closed from a Wi-Fi laptop, and open from two wired
  servers. The rule was fine; the probe's path wasn't.
- **A new zone's default may allow all traffic to the gateway**, management
  interface included. Step 4.5 closes it.
- **Creation order is the only ordering control** for custom rules on
  UniFi; a requested index can be ignored. Allows first, the block last.
- **A design can be right and not worth building.** Write down why you
  declined it, so nobody reopens it next year.

## Rollback

Bind the house's Wi-Fi name back to the main network: devices re-request
addresses on the main network within minutes (power-cycle the stubborn
ones). Restore their old reservation rows and `--apply`. The trusted Wi-Fi
name and the firewall rules can stay; they're harmless without devices on
the IoT network.
