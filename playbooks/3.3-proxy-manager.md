# Playbook 3.3 — NGINX Proxy Manager: one front door

> **For the reader.** Read this whole file, and `3.3/server_proxy.conf`,
> before you give them to your AI assistant. Build your CA first
> (playbook 3.4); this playbook gets its certificates from it. Then say:
> *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 3.3 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's names and addresses are the
   author's. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs
   software, changes DNS for the house, or deletes anything is a CONFIRM
   step even if this file forgot to mark it.
4. **Get install steps from the upstream docs**: Docker
   (https://docs.docker.com/engine/install/), NGINX Proxy Manager
   (https://nginxproxymanager.com/setup/), acme.sh.
5. **Secrets:** the reader creates the NPM admin account themselves. Private
   keys stay on the NPM machine. If you upload a certificate through NPM's
   API, do it from that machine.
6. **Verify by effect**: through the proxy, from another machine.
7. If the reader keeps a homelab wiki, record each proxy host (name,
   backend, scheme, WebSockets) there.

## Goal: what "done" looks like

- [ ] NPM runs and starts at boot, and its admin account belongs to the
      reader.
- [ ] One service is reached at `https://<name>` through the proxy: a
      client that trusts your root gets `ssl_verify_result` `0`, and
      `http://` redirects to `https://`.
- [ ] WebSockets pass through: the HTTP/1.1 upgrade test returns
      `101 Switching Protocols`.
- [ ] The certificate comes from your CA, lasts 90 days, and a forced
      renewal reaches NPM by itself.
- [ ] The service's local DNS name points at **the proxy**, not the
      service.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Where NPM will run | A small VM or container with Docker; it holds every certificate | Ask; the book uses a small VM |
| The proxy's fixed address | Every proxied name will point at it | Ask; book 1.4 |
| The CA's name and root fingerprint | Certificates come from it | From playbook 3.4 |
| The first service | Its address, port, and whether it speaks HTTPS itself | Ask; check with `curl` from the proxy machine |
| Whether it uses WebSockets | Most modern web apps do (Home Assistant, cameras, Proxmox console) | Assume yes |

## Steps

### 1. Docker — CONFIRM

Install Docker Engine from Docker's own repository, as its docs describe
for the reader's distribution. In a **Proxmox container**, enable the
`nesting` and `keyctl` features first; Docker then works in an unprivileged
container. **Verify:** `docker run --rm hello-world` prints its greeting.

### 2. NGINX Proxy Manager — CONFIRM

Use the `docker-compose.yml` from NPM's setup page, in a folder of its own
(the book uses `/srv/npm`). Pin the image to the current version tag rather
than `latest`, so an update is a decision. Start it with `docker compose up -d`.

**Verify:** `curl -s http://<proxy-ip>:81/api/` answers
`{"status":"OK","setup":false,…}` within a minute or two.

### 3. Claim the admin account now — the reader does this

**Current NPM has no default login.** Until someone creates the admin
account, NPM's API accepts an unauthenticated request to create one, from
anyone who can reach port 81. Ask the reader to open
`http://<proxy-ip>:81` straight away and create their account. Don't do it
for them: it's their password.

**Verify:** `curl -s http://<proxy-ip>:81/api/` now shows `"setup":true`.

### 4. The first proxy host — CONFIRM

The reader adds it in the web interface (**Hosts → Proxy Hosts → Add**), or
you use NPM's API with a token the reader gives you:

| Field | Value |
|---|---|
| Domain name | the service's name, e.g. `ha.home.arpa` |
| Scheme | `http`, unless the service itself speaks HTTPS |
| Forward host / IP | the service's **IP address** (never `localhost`: that's the proxy) |
| Forward port | the service's port |
| WebSockets support | **On** |

Then point the name at the **proxy's** address in Pi-hole (book 3.1), and
remove any record that pointed it at the service.

**Verify** from another machine: `curl -s -o /dev/null -w '%{http_code}'
http://<name>/` gets the service's normal answer.

### 5. Serve the ACME challenge on every host — CONFIRM

Install `3.3/server_proxy.conf` from this repository as
`data/nginx/custom/server_proxy.conf` under NPM's folder, and create the
folder `data/letsencrypt-acme-challenge/`. Test and reload NGINX inside the
container (`docker exec <container> nginx -t`, then `nginx -s reload`).
Use the reader's actual container name, from `docker compose ps`. With the
compose file from the docs it's `<folder>-app-1`, not the book's
`npm-npm-1`.

**Verify:** put a file at
`data/letsencrypt-acme-challenge/.well-known/acme-challenge/probe`, fetch
`http://<name>/.well-known/acme-challenge/probe` from another machine and
get its contents. Then fetch `http://<name>/` and get the service, not the
file. Delete the probe.

### 6. A certificate from your CA — CONFIRM

On the NPM machine:

1. Fetch your CA's root, **check its fingerprint** against the one recorded
   in playbook 3.4, and trust it system-wide.
2. Install acme.sh from its official installer (download, show, run), as
   root from a real root shell: it refuses to run under `sudo`.
3. Issue with `--webroot <npm-folder>/data/letsencrypt-acme-challenge` and
   `--server https://<ca-name>:8443/acme/acme/directory`.
4. In NPM, add the certificate as a **Custom** certificate (SSL
   Certificates → Add → Custom), uploading the full chain and the key. The
   reader can do this in the browser. If you use the API instead, run it
   on the NPM machine, so the key never leaves it. Note the number NPM
   gives it: the files land in `data/custom_ssl/npm-<id>/`.
5. Register the deploy hook once: `acme.sh --install-cert -d <name> --ecc`
   with `--fullchain-file …/custom_ssl/npm-<id>/fullchain.pem`,
   `--key-file …/custom_ssl/npm-<id>/privkey.pem` and `--reloadcmd "docker
   exec <container> nginx -s reload"`.
6. On the proxy host, choose that certificate and turn on **Force SSL**.

**Verify**, from another machine that trusts the root:
- `curl -s -o /dev/null -w '%{ssl_verify_result} %{http_code}'
  https://<name>/` prints `0 200` (or the service's normal code).
- `http://<name>/` answers `301` to the `https://` address.
- The proxy host's **scheme is still what you set**. Assigning a
  certificate in the web interface has been seen to flip it to `https`,
  which gives a 502 from a backend that only speaks HTTP.
- `openssl x509 -noout -enddate` on `custom_ssl/npm-<id>/fullchain.pem`
  shows about 90 days.

### 7. Prove WebSockets and renewal

- The HTTP/1.1 upgrade test from book 3.3 (`curl --http1.1 … -H "Upgrade:
  websocket"` against a WebSocket path of the service) returns `HTTP/1.1
  101 Switching Protocols`. Without `--http1.1`, curl may use HTTP/2 and
  report a meaningless 400. Run the same test straight against the backend
  if it fails, before blaming the proxy.
- `acme.sh --renew -d <name> --ecc --force` succeeds **with Force SSL on**,
  and its reload command runs. Afterwards the `https://` check still prints
  `0`.

### 8. More hosts

Repeat steps 4 and 6 for each service: name → proxy, proxy host, its own
certificate, deploy hook. Give NPM's own admin page a proxy host too
(`npm.<domain>` → the proxy's IP, port 81), so even that is HTTPS.

## Gotchas (from the book and the test)

- **WebSockets off** gives a page that loads and never updates. Check the
  toggle before debugging anything upstream.
- **Wrong scheme** gives a redirect loop or a 502, never a clear error.
- **No default login in current NPM**: claim the admin account before
  anything else (step 3).
- **Container name:** the reload command must name the reader's container.
  A wrong name makes every renewal "succeed" without NGINX ever loading the
  new certificate.
- **Delete `server_proxy.conf` and renewals stop quietly.** It's the only
  thing that answers the challenge once Force SSL is on.
- **acme.sh refuses `sudo` and `sudo -i`**, and inside a `cmd && next`
  chain the refusal is easy to miss. Use `su -`.

## Rollback

Point each name back at its service in Pi-hole first, then `docker compose
down` in NPM's folder. Removing the acme.sh cron entry stops renewals.
