# Playbook 3.1 — Pi-hole: ad blocking and local names

> **For the reader.** Read this whole file before you give it to your AI
> assistant. Then start a session and say: *"Follow this playbook. Ask me
> before every step marked CONFIRM."* It works as a checklist for a human, too.
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 3.1 describes. The book explains why; this file
> says what to do. Follow the rules below for the whole session.

## Rules for the assistant

1. **Discover, don't assume.** Every address, host name and domain in the
   book is the author's, not the reader's. Ask for, or look up, the reader's
   own values in *Discover first* below.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop and ask the reader, and wait for a yes. Treat
   anything that installs software, changes DNS or DHCP for the house, or
   deletes anything as a CONFIRM step even if this file forgot to mark it.
4. **Get current install commands from the upstream docs**
   (https://docs.pi-hole.net/), not from memory or from this file. Projects
   change their installers; the docs are current and this file may not be.
5. **Secrets never go on a command line or into a file you write.** The
   Pi-hole admin password is set by the reader at an interactive prompt, or
   in the web interface.
6. **Verify by effect.** A step is done when you have read back the state it
   should have changed (a `dig` answer, a file listing), not when a command
   exits 0.
7. If the reader keeps a homelab wiki (book Chapter 2), record what you built
   there when you finish, with the exact verification results.

## Goal: what "done" looks like

- [ ] Pi-hole v6 runs on a machine with a fixed address on the home LAN.
- [ ] The reader can log in to its web interface with a password only they
      know.
- [ ] `dig +short <a-local-name> @<pihole-ip>` returns the address the reader
      chose, for at least one local record under `home.arpa`.
- [ ] `dig +short doubleclick.net @<pihole-ip>` returns `0.0.0.0`.
- [ ] `/etc/pihole/hosts/` contains exactly one file, `custom.list`.
- [ ] Either the gateway hands Pi-hole out as the DNS server (step 6), or the
      reader has decided to do that later. Write down which.

## Discover first

Ask the reader, or find out with read-only commands, and write the answers
down before step 1:

| What | Why | How to find it |
|---|---|---|
| Where Pi-hole will run | A Proxmox container (the book's way), another Debian or Ubuntu machine, or a Raspberry Pi | Ask |
| Its LAN address | Pi-hole needs one that never changes | Ask; book section 1.4 covers DHCP reservations on the gateway |
| The gateway / router model | It decides how clients learn their DNS server (step 6) and whether it intercepts DNS | Ask |
| Local domain | The book uses `home.arpa` (RFC 8375). Keep it unless the reader has a reason | Ask |
| Local names to create | Host name and address pairs, e.g. `nas.home.arpa` | Ask; start with two or three |
| Upstream resolvers | Where Pi-hole forwards everything else | Ask; any two well-known public resolvers are fine |
| Does the house use Plex? | Decides whether the `plex.direct` gotcha applies | Ask |

## Steps

### 1. A small machine with a fixed address — CONFIRM

Pi-hole needs very little: one CPU core, 512 MB of RAM and about 4 GB of disk.

- **On Proxmox (the book's way):** an *unprivileged* LXC container from the
  current Debian template, 1 core, 512 MB, 4 GB disk, on the LAN bridge.
  Check the Proxmox docs for the current `pct create` syntax or use the web
  UI's *Create CT* wizard. Enable `nesting` (current Debian templates expect it).
- **On anything else:** a current Debian or Ubuntu install, or Raspberry Pi
  OS Lite.

Then make its address fixed: a DHCP reservation on the gateway (book 1.4) or
a static address. **Verify:** from another machine, `ping` the address, and
on the machine `ip -4 addr` shows it.

### 2. Install Pi-hole — CONFIRM

1. Open https://docs.pi-hole.net/ and follow the current *Basic install* (or
   *Unattended install*) instructions.
2. **Download the installer to a file and let the reader read it before it
   runs.** Never pipe it straight into a shell. The book says why in one line:
   it's widely used and readable, and that's still no reason to skip the look.
3. The installer is an interactive text menu. An AI assistant can't drive it
   over a plain SSH session, so either:
   - **the reader runs it** in their own terminal and answers the menus with
     the values from *Discover first*, or
   - **you run it unattended** (CONFIRM). If the current docs describe an
     unattended install, follow them. If they don't (they didn't when this
     was tested), this works: the installer skips its menus only when
     `/etc/pihole/pihole.toml` **already exists**, so write a minimal one
     first, with the reader's upstreams and the machine's LAN interface name:

     ```toml
     [dns]
       upstreams = ["<resolver-1>", "<resolver-2>"]
       interface = "<lan-interface>"
     ```

     Then run the downloaded installer with `--unattended`. It finishes with
     **"Update complete!"** rather than "Installation complete". That's
     expected: the pre-written file makes it think Pi-hole was already there.
     It still installs the default blocklist. Run `pihole reloadlists`
     straight afterwards: in both test installs, FTL kept the empty
     pre-install database open and blocked nothing until it was told to
     reload (step 4 shows how to spot it).
4. **Set the admin password now, before anything else.** An unattended
   install sets **no password at all**, so until this step anyone on the LAN
   can use the web interface and the API. **The reader types it** at the
   prompt that `pihole setpassword` opens (run it over `ssh -t`, so there is
   a terminal), or sets it in the web interface. Never put it on a command
   line yourself.

**Verify:**
- `pihole status` reports it is listening on port 53. (It also says
  blocking is enabled. Don't believe that yet; step 4 checks it.)
- `dig +short pi-hole.net @<pihole-ip>` from *another* machine returns an
  address. That proves the DNS service answers on the LAN, not just on
  localhost.
- A few seconds after the password is set, an unauthenticated API request
  is refused: `curl -s -o /dev/null -w '%{http_code}'
  http://<pihole-ip>/api/dns/blocking` prints `401`. With no password it
  prints `200`, and anyone on the LAN can change Pi-hole's settings.
- **In a container:** turn off Pi-hole's own time service
  (`ntp.sync.active`, `ntp.ipv4.active` and `ntp.ipv6.active` set to
  `false` with `pihole-FTL --config`). An unprivileged container can't set
  the clock, so it only logs "Insufficient permissions" every ten minutes;
  the host keeps the time.

### 3. Local names — CONFIRM

In Pi-hole v6 local records live in **one** place: the `hosts` array under
`[dns]` in `/etc/pihole/pihole.toml`. Add the reader's records with the web
UI (*Settings → Local DNS Records*), the `pihole-FTL --config dns.hosts`
command, or a careful edit of the toml. Pi-hole reloads by itself within
seconds. There is no restart command to run.

**Verify**, from another machine, for every record:
`dig +short <name> @<pihole-ip>` returns the address, and
`dig +short -x <address> @<pihole-ip>` returns the name.

### 4. Blocking works

**Verify:** `dig +short doubleclick.net @<pihole-ip>` returns `0.0.0.0`.
Then `ls -l /etc/pihole/hosts/` shows exactly one file, `custom.list`.

**If the name resolves to a real address**, check
`/var/log/pihole/FTL.log` for `no such table: main.gravity`. Both test
installs left FTL holding the empty database from before the blocklist
download. It blocked nothing while `pihole status` said "blocking is
enabled". `pihole reloadlists` fixed it, and the `dig` above then returned
`0.0.0.0`. This is the book's refrain in miniature: read the effect, not
the status line.

### 5. Optional: one regex deny and one allow — CONFIRM

Only if the reader wants them. The book's examples: a regex deny for an
abuse-heavy top-level domain (`\.top$`) and an exact allow for one domain an
app needs. Use the `pihole` command or the web UI. Keep the comment to plain
words: the comment validator rejects punctuation such as `:`, `(`, `)` and
`.`, and when it does it adds nothing. **Verify** the deny with `dig` (a
blocked name answers `0.0.0.0`), not with the command's reply.

### 6. Hand Pi-hole to every client — CONFIRM, and usually the reader's job

This changes DNS for the whole house, so it is the riskiest step.

- Set the gateway's DHCP server to hand out the Pi-hole address as DNS
  server 1 on every network, including any IoT VLAN. Leave Pi-hole's own
  DHCP off; the gateway keeps that job.
- Unless you have a tool for the reader's gateway and they ask you to use it,
  **give the reader the steps for their gateway model and let them do it.**
- Clients pick it up when their lease renews. Toggling Wi-Fi on one device is
  the quick test.

**Verify:** on a client, its DNS server is the Pi-hole address, and that
client appears in Pi-hole's query log within a minute.

## Gotchas (from the book's war stories)

- **Never back a file up inside `/etc/pihole/hosts/`.** Pi-hole serves every
  file in that directory. A `custom.list.bak` there keeps answering live
  DNS, and changed names start returning two addresses. Back up to
  `/etc/pihole/` instead.
- **`custom.list` is generated from `pihole.toml`.** Read it, never edit it;
  your edits get overwritten.
- **`pihole restartdns` is gone in v6.** It just prints usage text, which
  looks like a broken PATH. Nothing needs restarting after a record change.
- **Test from a client with `dig @<pihole-ip>`, not `getent` on the Pi-hole
  box**: on the box, `/etc/hosts` is read first and can disagree.
- **One IP reverses to one name.** If many names share one address (a
  reverse proxy, book 3.3), only one wins the reverse lookup.
- **Gateways can intercept DNS.** UniFi's content filter, and similar
  features on other gateways, answers *all* DNS on a network itself, even
  queries sent to Pi-hole's address. The tell is a blocked name answering
  something other than `0.0.0.0` (UniFi: `203.0.113.250`). Check the reader's
  gateway for such a feature before step 6.
- **Plex households:** some upstream resolvers return SERVFAIL for
  `*.plex.direct`, and Plex apps stall for 30 seconds before falling back. If
  that happens, send just that zone to a different upstream
  (`misc.dnsmasq_lines` with `server=/plex.direct/<resolver>`). Test the fix
  with a name that has **never** resolved; a cached one proves nothing.
- **Client groups keyed by MAC address don't follow a replaced device.** If
  the reader uses groups, key them by IP address (the DHCP reservation
  moves with the device).

## Rollback

- Before step 6: delete the container or run Pi-hole's uninstaller. Nothing
  else in the house has changed.
- After step 6: set the gateway's DHCP DNS back to its previous value first
  (write that value down before changing it), let clients renew, then
  remove Pi-hole.
