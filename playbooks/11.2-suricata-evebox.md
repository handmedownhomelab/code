# Playbook 11.2 — Suricata and EveBox

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need a small Linux machine with two network ports (the
> book's is a Raspberry Pi 5 with a USB Ethernet adapter), and a managed
> switch that can mirror a port; you set up the mirror. Then say: *"Follow
> this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 11.2 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Passive only.** The capture port gets no IP address and nothing is
   ever sent on it.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before installing software or changing a network interface.
4. **"Active" proves nothing.** Every step is verified by packets counted
   or alerts seen.

## Goal: what "done" looks like

- [ ] A mirror of the gateway's **LAN-side** uplink arrives on the sensor's
      capture port, whose packet counters climb by thousands a second.
- [ ] Suricata runs with ET Open rules updated nightly, `HOME_NET` set to
      the reader's private ranges.
- [ ] A test alert appears in `eve.json` and in EveBox.
- [ ] EveBox requires a login.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The switch and the gateway's uplink port | Where to mirror | The switch's web interface |
| The sensor's two interfaces | Capture vs management | `ip -br link` |
| The reader's private ranges | `HOME_NET` | From book 1.5/1.6 |
| CPU architecture | The EveBox `.deb` to download | `dpkg --print-architecture` |

## Steps

### 1. The mirror — the reader, on the switch

Mirror the port that connects to the **gateway's LAN side** to the port
the sensor's capture interface is plugged into. (The LAN side shows real
device addresses; the internet side shows only the router's.)

### 2. The capture port — CONFIRM

Bring the capture interface up with **no address**, in promiscuous mode, at
boot, using the system's network configuration.

**Verify:** `ip -s link show <capture>` twice, ten seconds apart: the RX
packet count climbs by thousands a second. If it climbs by one a second,
the mirror isn't arriving. Stop and fix that first.

### 3. Suricata — CONFIRM

Install `suricata` from Debian. In `/etc/suricata/suricata.yaml`, set the
af-packet `interface` to the capture port and `HOME_NET` to the reader's
ranges. Keep the file otherwise close to the default. Run `suricata-update`
for the ET Open rules, and schedule it nightly (a timer or cron, then reload
Suricata). Check the config with `suricata -T`, then restart.

**Verify:** `/var/log/suricata/suricata.log` reports tens of thousands of
signatures loaded, and `eve.json` fills with `flow`, `dns` and `tls`
events.

### 4. Prove it alerts

Rule 2100498 fires on the text `uid=0(root)` in a TCP response. From a
machine on the far side of the mirror, serve a file containing `uid=0(root)
gid=0(root)` over plain HTTP (for example `python3 -m http.server`) and
fetch it from a machine whose traffic crosses the mirror. (The old
testmynids.org page didn't answer when this was tested.)

**Verify:** `eve.json` gets an `alert` event, "GPL ATTACK_RESPONSE id check
returned root".

### 5. EveBox — CONFIRM

**Install from the release `.deb`**, from evebox.org's releases page for
the sensor's architecture. EveBox also has an apt repository, but its
signing key uses SHA-1, which Debian 13's apt has rejected since February
2026 ("The repository … is not signed"). Don't weaken apt's policy to get
around it. No checksum is published for the `.deb`, so download it over
HTTPS from evebox.org only.

The packaged service expects Elasticsearch. For a single sensor, use its
built-in SQLite store: in `/etc/default/evebox`, set `EVEBOX_OPTS="--sqlite
--input /var/log/suricata/eve.json"`. EveBox loads `/etc/evebox/evebox.yaml`
by itself, so don't add a second `-c`: it fails with "cannot be used
multiple times".

**Turn authentication on.** The packaged `evebox.yaml` ships with
`authentication: false`, which means anyone on the network can read every
alert. Set it to `true`, add a user (`evebox config -D /var/lib/evebox
users add`, with the reader typing the password), and restart.

**Verify:** the test alert from step 4 is in EveBox, and an anonymous
request to `http://<sensor>:5636/api/alerts` gets `401`.

### 6. Write down how each piece updates

Suricata updates with `apt`. EveBox is a hand-installed `.deb`, so check
its releases page on a schedule. Rules update nightly. Put this list on the
host's wiki page.

## Gotchas (from the book and the test)

- **Active and blind:** `systemctl is-active suricata` says `active` with
  no traffic arriving. Check the counters.
- **After moving a cable, the alert log's tail is old.** Check alert
  timestamps, not just that alerts exist.
- **What doesn't cross the uplink isn't seen**, and a 1 Gb capture port on a
  faster uplink drops packets at peak.
- **EveBox ships open.** Authentication is off until you turn it on.

## Rollback

Remove the switch mirror, then the packages. Nothing on the network depends
on a passive sensor.
