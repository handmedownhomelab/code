# Playbook 5.1 — Home Assistant in a Proxmox VM

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need the Proxmox host from book 1.2 and about 4 GB of RAM
> free. Onboarding happens in your browser, and only you do it. Then say:
> *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 5.1 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's Proxmox host, storage names
   and network.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before creating the VM, and before anything that changes
   another machine (the proxy, Pi-hole).
4. **The reader onboards Home Assistant in the browser.** Never create its
   accounts yourself.
5. **Get the image from Home Assistant's own release page**, and verify the
   download as the release page describes.
6. **Verify by effect**, from another machine.

## Goal: what "done" looks like

- [ ] A Home Assistant OS VM on Proxmox: UEFI, 2 cores, 4 GB, 32 GB disk,
      starting at boot, with a DHCP reservation.
- [ ] The reader owns the only account, created at first boot.
- [ ] Mosquitto is installed and running, so other machines can publish to
      Home Assistant.
- [ ] Through the reverse proxy, `https://<ha-name>` loads (no 400).
- [ ] Home Assistant's daily backup is on, and the VM is in the Proxmox
      backup job.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Proxmox storage for VM disks | Where the disk is imported | `pvesm status` |
| Free RAM on the host | Home Assistant uses close to all of what it's given | `free -g` |
| The next free VM ID | For the commands | `pvesh get /cluster/nextid` |
| The reverse proxy's address | The trusted-proxy setting | From playbook 4.3 |
| The name for Home Assistant | e.g. `ha.home.arpa` | Ask |

## Steps

### 1. Get the image

From Home Assistant's "alternative installation" page, download the current
**KVM/Proxmox** image (`haos_ova-<version>.qcow2.xz`) onto the Proxmox host,
into a temporary folder, and decompress it.

### 2. Create the VM — CONFIRM

On the Proxmox host (or with Proxmox's own wizard; the community helper
scripts are another route the book mentions):
- machine type **q35**, firmware **OVMF (UEFI)** with an EFI disk, **with
  pre-enrolled keys off** (Home Assistant's guide says to turn Secure Boot
  off; the test VM booted this way);
- 2 cores, 4096 MB, a virtio network card on the LAN bridge;
- import the qcow2 as the VM's disk (`qm importdisk`), attach it as `scsi0`
  and make it the boot disk, then **grow it to 32 GB** (`qm resize`). HAOS
  expands into the space by itself;
- start at boot (`onboot 1`).

Delete the downloaded image afterwards.

**Verify:** the VM is running, and within a minute its address answers.
Give that address a DHCP reservation (book 1.5).

### 3. First boot, and claim it now — the reader does this

The first boot downloads Home Assistant itself: allow 10–20 minutes.

**Watch the port.** Since Home Assistant 2026.8, a **fresh** Home Assistant
OS install serves its web interface on **port 80**:
`http://<address>/` or `http://homeassistant.local/`. Port 8123 only
redirects there. (Older guides, and installs from before 2026.8, use
`:8123`.) If you're checking progress with a script, check port 80. A
check on 8123 never sees anything but the redirect.

As soon as the onboarding page appears, ask the reader to open it and create
their account. **Until they do, anyone who can reach it can.** In testing,
an unauthenticated request created the owner account; after that, a second
attempt was refused (403).

**Verify:** the onboarding page now asks for a login instead.

### 4. Name it, and point the proxy at it — CONFIRM

In NGINX Proxy Manager (playbook 4.3), the proxy host for `<ha-name>`
forwards to `http://<address>:80` on a fresh install (`:8123` on older
ones), **WebSockets on**. Point the name at the proxy in Pi-hole.

Then the reader adds the proxy in Home Assistant: **Settings → System →
Network**, add the proxy's address as a `/32` and turn on *use
X-Forwarded-For*. Until then, Home Assistant answers proxied requests with
**400 Bad Request** (confirmed in testing: any request carrying
`X-Forwarded-For` from an untrusted address got 400).

**Verify:** `https://<ha-name>` loads from another machine, with no 400.

### 5. Add-ons — the reader, in Settings → Add-ons

Install **Mosquitto broker** and start it (enable *Start on boot* and
*Watchdog*). Then Settings → Devices & services should offer the MQTT
integration. Accept it. Other add-ons from the book (Piper, Whisper,
ESPHome, Tailscale) as needed.

**Verify:** from another machine with `mosquitto_pub` and a Home Assistant
user, publish to a test topic. In Home Assistant, Settings → MQTT →
*Listen to a topic* shows it.

### 6. Backups

Home Assistant's own backups: on, daily, kept a few days. Add the VM's ID
to the Proxmox backup job (playbook 1.4), because the job names its guests
explicitly.

**Verify:** after the next nights, both backups exist.

## Gotchas (from the book and the test)

- **Port 80 on fresh installs, 8123 on older ones.** Tutorials, proxy
  configs and monitors written for 8123 need the right port.
- **Claim it first.** Same pattern as NPM, Kuma and Open WebUI.
- **400 Bad Request through the proxy** means the proxy isn't trusted yet.
  The setting lives in the web interface now; older guides show YAML.
- **Configuration moves.** Since 2026.8 the proxy and port settings live in
  Home Assistant's internal storage, not `configuration.yaml`. Back up
  `.storage/` along with the YAML, or use Home Assistant's own backups.
- **Close to 100% RAM use is normal** for Home Assistant, not a leak.
- **Name devices well from the start.** Renaming later ripples through every
  automation and dashboard.

## Rollback

Stop and destroy the VM in Proxmox; remove its proxy host and DNS name.
