# Playbook 1.5 — Cutover day, and reservations as code

> **For the reader.** Read this whole file and `1.5/ux7_load_reservations.py`
> before you give them to your AI assistant. The loader is written for a
> UniFi gateway (UniFi OS: an Express, Cloud Gateway or Dream Machine); the
> cutover order and the table-as-code idea work with any gateway. You need
> the new gateway, a laptop, Python 3, and an afternoon when the house can
> be offline for half an hour. Then say: *"Follow this playbook. Ask me
> before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* replace their router as section 1.5 describes. Much of it
> happens in the gateway's own interface and with cables, so you will be
> telling the reader what to do and checking the results. Follow the rules
> below for the whole session.

## Rules for the assistant

1. **Discover, don't assume.** Every address, range and device in this
   playbook is the book's example. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before every step that changes the live network, and before
   every `--apply`. Read each dry run to the reader first.
4. **Credentials never go on a command line**, in a file in the repository,
   or in a wiki page. The loader reads the gateway password from an
   environment variable, the macOS Keychain or a prompt.
5. **Every subcommand is a dry run until `--apply`.** That includes
   `--prune`. Say so each time.
6. **Verify by effect**: a device on its reserved address, the gateway's
   own read-back (`--verify`), not the loader's summary line.

## Goal: what "done" looks like

- [ ] The new gateway routes the house, on the old router's LAN address,
      and the internet works.
- [ ] Every fixed address lives in one Markdown table, and the gateway
      matches it: a dry run reports `CREATE=0, UPDATE=0, ERROR=0`.
- [ ] `--verify` passes: subnet, gateway address, lease, pool, DNS.
- [ ] DHCP hands out the reader's own DNS servers (the Pi-holes, if they
      have them), switched over last.
- [ ] The old router is out of the routing path (bridged or retired), and
      the reader has written down the public IP address.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The old router's LAN address, subnet and DHCP range | The new gateway keeps the address; every hand-set device points at it | The old router's app or page; `ip route` or `netstat -rn` on a client |
| Every fixed address today (device, IP, MAC) | The reservation table | The old router's export, if it has one. If it doesn't (the book's didn't), build it from its app, `arp -a`, and each host's `ip link` |
| Devices with hand-set addresses | They must keep working with no change | Ask; check each server's network config |
| Whether the old router can be bridged, and whether that needs its cloud | The ordering trap (step 4) | Its documentation |
| The internet provider's MAC binding | Cloning the old WAN MAC can keep the same public IP | The provider; or just clone it |
| The public IP address now | To check it afterwards (the book forgot) | `curl -s https://ifconfig.me` |
| A local admin account on the new gateway | The local API refuses cloud accounts with two-factor | Created in step 2 |

## Steps

### 1. The table — no network needed

Copy `1.5/reservations.example.md` to the reader's wiki (or anywhere they
keep notes) as `reservations.md`, and fill the table under
`## Reservations` with every device that needs a fixed address: one row,
`Device | IP | MAC`. Leave out the gateway's own switches and access
points: the controller owns their addresses and refuses reservations for
them. Copy `1.5/ux7_load_reservations.py` next to it and edit the block
marked **YOUR NETWORK**: the table's path, the gateway's address, the LAN
(`PRIMARY_LAN_CIDR`), every network the table may use (`MANAGED_CIDRS`),
and what `--verify` expects (`EXPECTED`: subnet, gateway, DNS servers in
order, lease, the cloned WAN MAC if any).

**Verify:** `./ux7_load_reservations.py --list` prints `Parsed N
reservations` with N equal to the table's rows, lists them in address
order, and prints **no** lines starting with `!` (duplicate IPs or MACs,
addresses outside every managed network). Read the output: `--list` exits 0
even when it finds problems. To see the guard work, add a row with a
duplicate address to a copy of the table and run the loader without flags
against it (`--inventory <copy>`): it stops with `Refusing to continue: 1
preflight problem(s) above.` and exit status 2, before it asks for a
password. Fix the real table until `--list` is clean.

### 2. The bench session — zero downtime

The new gateway stays off the house network. Set it up with its app or a
laptop on its LAN port, in this order:

1. **Adopt and update the firmware first.** For internet during this
   stage, its WAN may go to a free port on the current network, as long as
   its own LAN is still on its default subnet (not the house's).
   A firmware update can change the API the loader uses; let it land before
   anything is tested.
2. **Everything that doesn't touch the house's subnet:** a **local** admin
   account for the loader, the Wi-Fi name and password, a **public** DNS
   resolver for DHCP for now (the Pi-holes are on the old network and
   unreachable from the bench), and any switch you're adding (adopt it; set
   up a port mirror if you'll run an IDS, Chapter 11).
3. **Clone the old router's WAN MAC** onto the new gateway's WAN, so the
   provider keeps the same public IP.

**Verify:** the gateway's interface shows the new firmware, the local
account logs in at the gateway's own address in a browser, and the Wi-Fi
name is up.

### 3. Renumber and load, still on the bench — CONFIRM

Set the gateway's LAN to the house's subnet and **the old router's
address** (the book: `10.20.0.0/22`, gateway `10.20.0.1`), and define the
DHCP pool explicitly (the book: `10.20.0.16`–`10.20.3.254`, a 4-hour
lease). UniFi won't auto-size a large subnet's pool.

**One rule while you do it: the gateway's WAN must never hold an address
inside the house's subnet.** If its WAN still borrows a lease from the
house network (stage 1 of step 2), the same subnet would sit on both sides
of the router. Unplug the WAN before renumbering; the loader only needs
the laptop to reach the gateway, not the internet. (The book's lab moved
the WAN to the modem at this point instead, which works because a modem
hands out a public address; it also means the house is already offline.)

Join the laptop to the new Wi-Fi name, then, with the reader's go-ahead
for each:

```
./ux7_load_reservations.py --username <local-admin>
./ux7_load_reservations.py --username <local-admin> --apply
./ux7_load_reservations.py --username <local-admin>
```

**Verify:**
- The first dry run lists every row as CREATE (or UPDATE/SKIP) and ends
  `Nothing was written. Re-run with --apply to commit.`
- The `--apply` run ends `ERROR=0`.
- The second dry run reports every row as SKIP: `CREATE=0, UPDATE=0`.
  That's the idempotency check; the loader's own summary isn't proof, this
  read-back is.
- `./ux7_load_reservations.py --username <local-admin> --verify` prints
  `ok` for the LAN subnet, gateway IP, DHCP lease, DHCP pool, IDS/IPS and
  reservation count, and ends `N pass, 0 fail, 0 unknown`. DNS shows
  `FAIL` for now if `EXPECTED` lists the Pi-holes; that's step 6.
- If the laptop can't reach the gateway, every online command stops with
  `POST /api/auth/login -> timed out`. Check the laptop is on the new
  Wi-Fi name and that `--host` is the gateway's new address.

### 4. The cutover — CONFIRM, house offline 15–30 minutes

Tell the household first. Then, **in this order**:

1. **Put the old router into bridge mode, or switch its DHCP off, while it
   still has internet.** Some (the book's mesh) can only be changed through
   their cloud, and once the modem cable moves they can't be changed at all.
2. Move the modem cable to the new gateway's WAN.
3. Connect the new gateway's LAN (through its switch) to where the old
   router's LAN went.
4. Power-cycle the modem if the gateway doesn't get a WAN address within a
   few minutes.

Never leave two routers handing out addresses on one network: that's what
step 1 prevents.

**Verify:**
- The gateway has a WAN address, and `curl -s https://ifconfig.me` from a
  client matches the public IP written down earlier (if the MAC clone
  worked).
- A client gets an address in the pool, and the gateway at the old address
  answers.
- Spot-check five hosts on their documented addresses, including at least
  one with a hand-set address and one reserved device:
  `ping -c 2 <address>` and log in to each server.
- A speed test from one machine: about 940 Mb/s is the most a 1 Gb port
  can do. That is correct, not a fault.

### 5. The fallout check

Devices that hold a lease until it expires keep their old address for up
to a lease period. Run the dry run again an hour later.

**Verify:** the dry run is still all SKIP, and the gateway's client list
shows each reserved device on its reserved address. Two kinds of rows
silently miss: a MAC that is a phone's or laptop's **private (randomized)
Wi-Fi address**, which changes per network name, and a device that hasn't
renewed yet. Find the first kind by its new MAC in the client list, update
the row, and re-run with `--apply`.

### 6. DNS last — CONFIRM

When everything above is green, switch DHCP's DNS servers from the public
resolver to the reader's own (the Pi-holes, book 6.1–6.2). Clients pick it
up on lease renewal, or when they rejoin Wi-Fi.

**Verify:** `--verify` now ends `0 fail`, DNS included. A client resolves a local name
(`nslookup <host>.home.arpa`) and an internet name. If local names fail,
put DNS back to the public resolver (one field) and fix the resolvers
another day: the house keeps its internet either way.

### 7. Keep it as code

From now on, a fixed address is a row in the table, then a dry run, then
`--apply`. Run `--verify` after every gateway firmware update: an update
can reset a setting silently. To remove a reservation, delete its row and
run `--prune` (dry run), then `--prune --apply`.

**Verify:** add one test row for a spare device, dry run (one CREATE),
apply, dry run (SKIP); then remove the row, `--prune` (one orphan listed,
`Nothing was written`), `--prune --apply`, and `--prune` again (no
orphans).

## Gotchas (from the book and the test)

- **Bridge before you move the cable.** The book's cutover did it the
  other way round and needed a round trip: modem back to the old router,
  bridge it in the app, modem back to the new gateway. The old router
  *looked* fine in the phone app over cellular; seeing it isn't the same as
  being able to change it.
- **Keep the old router's LAN address.** It's what lets every hand-set
  device survive the swap untouched.
- **Public DNS on the bench, your own DNS last.** On the bench the Pi-holes
  are unreachable, and pointing DHCP at them breaks DNS confusingly. But
  public DNS is a fallback, not a resting state: no public resolver answers
  for `home.arpa` names.
- **Every subcommand needs its own `--apply`.** The book's war story:
  `--prune` then `--apply` ran a prune *dry run* and then a load, which
  failed with `DuplicateFixedIP` because the old reservation was still
  there. The report said "Nothing was written" at the bottom.
- **The gateway refuses a second reservation on an address.** Clear the old
  one first (`--prune --apply`), then load.
- **Reservations are scoped to a network.** A row is routed by its address;
  a row for a network the gateway doesn't have yet stops the whole run
  before anything is written (1.6 adds the IoT network).
- **The gateway's own switches and access points can't be reserved**
  (`FixedIpAlreadyUsedByDevice`). Leave them out of the table.
- **Write down the public IP before you start.** The book didn't, so "same
  public IP after the swap" could never be checked.
- **A 4-hour lease, not 24.** Short leases make a DNS or address change
  reach clients quickly.

## Rollback

Until the old router is retired, the swap reverses in minutes: modem cable
back to the old router's WAN, turn its bridge mode off (or DHCP back on),
and its LAN back where it was. The cloned WAN MAC means the modem doesn't
need re-provisioning either way. The reservations on the new gateway do
no harm while it's unplugged; to remove them, delete them in its interface
or reset it. (`--prune` refuses to run against an empty table, on
purpose: a table that fails to parse would otherwise look like "remove
everything".)
