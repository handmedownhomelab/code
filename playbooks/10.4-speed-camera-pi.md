# Playbook 10.4 — the portable speed camera

> **For the reader.** Read this whole file, and `10.4/README.md`, before you
> give them to your AI assistant. You need a Raspberry Pi 3B (or newer), a
> Sony PlayStation 3 Eye, a DS3231 real-time clock module for the Pi, a
> microSD card, a power bank or outdoor power, a tripod and a weatherproof
> box, and a car you can drive past at a known speed. Check what your state
> and community allow before you record a street or share the data. This
> playbook is **Not tested** (see the header). Then say: *"Follow this
> playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 10.4 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The Pi, the camera's controls, the street's
   geometry and the reader's time zone are theirs, not the book's.
2. **Show each command before you run it**, and say which machine it runs
   on: the Pi or the reader's computer.
3. **CONFIRM** means stop, ask, and wait for a yes. Writing an SD card,
   installing software, changing SSH or the boot configuration, or deleting
   anything is a CONFIRM step even if this file forgot to mark it.
4. **Never pipe the project's installer into a shell.** This playbook
   installs from apt and the project's repository instead (step 3 says why).
5. **Secrets:** the reader types the Pi's password and the Wi-Fi password
   themselves.
6. **Verify by effect**: the setting sshd actually uses, the clock the
   tracker actually sees, a speed measured against a known one.
7. **Never call it calibrated until step 8 passes in both directions.** A
   bad calibration raises no error; it produces believable wrong speeds.
8. If the reader keeps a homelab wiki, record the unit, the RTC module and
   when it was fitted, each deployment's calibration numbers and direction
   mapping, and a photo of the camera's view.

## Goal: what "done" looks like

- [ ] The Pi has its own name, key-only SSH (checked from another machine),
      and the right time zone.
- [ ] The DS3231 is fitted and registered, `fake-hwclock` is off, and the
      tracker refuses to start unless the clock is synchronized or agrees
      with the module.
- [ ] Exposure and gain are locked, at the shortest exposure that still
      gives a usable picture in the deployment light.
- [ ] The camera is aimed through the preview, square on to traffic, with a
      narrow crop band.
- [ ] Each direction calibrated separately, validated at a known speed, and
      calibration mode off.
- [ ] Rows appear in the CSV with the right directions, and the fixed
      camera's report script reads the file unchanged.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Pi model | A Pi 3B shares one USB 2 bus between the camera and the network | The board; `cat /proc/device-tree/model` |
| The DS3231 module's pinout | The compact "for Pi" modules press onto pins 1–9; others need wiring | The module's silkscreen; its square pad is pin 1 |
| The reader's time zone | Every CSV row is stamped in the Pi's zone | Ask |
| The fixed camera's CSV columns (10.3) | The exporter writes the same four | The fixed camera's logger |
| Where the unit will go, and its power | Power decides the deployment length (step 9) | Ask |
| A reference car, and its real length | Calibration is a length in pixels against a length in millimetres | A tape measure, not a spec sheet |

## Steps

### 1. Write the card — CONFIRM (erases it)

**Raspberry Pi OS Lite** (64-bit) with Raspberry Pi Imager. In its
customisation screen: a hostname, the reader's user, their SSH public key,
Wi-Fi, and **the time zone**. (Imager may copy the time zone from the
computer it runs on; check it anyway in step 2.)

**Verify:** the Pi boots and `ssh <user>@<pi>.local` works by key.

### 2. Base settings and key-only SSH — CONFIRM

Copy the companion `10.4/` folder to the Pi as `~/speedcam-stage/`. Set
`SPEEDCAM_TZ` (and the locale, keymap and Wi-Fi country if they differ)
at the top of `usr/local/bin/speedcam-apply-firstboot-settings.sh`, then:

```
sudo ~/speedcam-stage/usr/local/bin/speedcam-apply-firstboot-settings.sh
```

It writes `/etc/ssh/sshd_config.d/01-speedcam.conf`. **The `01-` matters:**
Raspberry Pi OS ships `50-cloud-init.conf` with `PasswordAuthentication
yes`, sshd keeps the *first* value it reads, and the files are read in name
order. A `99-` file installs cleanly, reloads without an error, and does
nothing. The script checks the effective value and says so if it didn't
take.

**Verify,** in a new session before closing the old one:
`sudo sshd -T | grep -i '^passwordauthentication'` says `no`, and from
another machine

```
ssh -o PubkeyAuthentication=no -o BatchMode=yes <user>@<pi> true
```

answers `Permission denied (publickey)`. If the list reads
`(publickey,password)`, passwords are still on. (Don't check by grepping the
cloud-init file as a normal user: only root can read it, so the grep finds
nothing, which looks like "nothing to worry about".) `timedatectl` shows
the reader's zone.

### 3. Provision — CONFIRM

```
sudo ~/speedcam-stage/usr/local/bin/speedcam-provision.sh
```

Run with `sudo` from the reader's account, it runs the tracker as that
account (`RUN_USER`). It:

- installs OpenCV, NumPy, `v4l-utils`, `sqlite3` and `i2c-tools` **from
  apt**. Not the project's `curl | bash` installer, which pulls a desktop
  dependency set and can try to build OpenCV from source: hours on a 1 GB
  Pi, and it can run out of memory;
- copies speed-camera's code from the latest `main` of its repository into
  `/opt/speed-camera` (each re-run takes the latest again; note the date);
- installs the plugin, exporter, tools and systemd units, and patches the
  two lines of `config.py` that turn the plugin on, then reads them back
  and **fails loudly** if either is missing, rather than running the
  project's defaults;
- adds the DS3231 overlay to the boot config and disables `fake-hwclock`;
- enables the exporter timer, and **refuses to enable the tracker** until
  the plugin says `SPEEDCAM_CALIBRATED = True`.

It is safe to re-run after editing the plugin or exporter, and it never
overwrites a plugin marked calibrated or an existing `speedcam.conf`.

**Verify:** it ends with "installed but NOT enabled: the camera is
uncalibrated", and `systemctl list-timers speedcam-export.timer` shows the
timer.

### 4. The clock — CONFIRM (power off to fit the module)

Shut down, fit the DS3231 (square pad on the Pi's pin 1), boot **on the
network**, and re-run the provisioner if it said the overlay was added this
run.

**Verify:**
- `cat /sys/class/rtc/rtc0/name` says `rtc-ds1307 1-0068` (the DS3231's
  driver). Don't use `i2cdetect`: it needs the `i2c-dev` module, which this
  build doesn't load, and reports nothing with the module working.
- `timedatectl` says `synchronized: yes`. Within a minute or two of that
  the module holds the right time (`sudo hwclock -r`); write it by hand
  (`sudo hwclock -w`) only while synchronized, or you store a wrong clock.
- The gate works: `sudo /usr/local/bin/speedcam-clock-check.sh` exits 0
  now. Then shut down, take the Pi **off the network**, boot, and run it
  again: still 0, because the clock agrees with the module.

### 5. See what the camera sees, and lock exposure

```
python3 /usr/local/bin/speedcam-snapshot.py -o /tmp/snap.jpg
```

draws the crop band in green and a **10-pixel ruler** along its bottom
edge, read from the plugin, so it shows exactly what the tracker measures.
Copy it to the reader's computer to look at.

Then, **at the deployment site, in the real light**:

```
python3 /usr/local/bin/speedcam-tune-exposure.py
```

It picks the **shortest exposure with a usable picture**, not the
best-looking frame: exposure is shutter time, and blur is what ruins pixel
tracking, while noise from more gain costs little. (The author's unit: 20
exposure / 40 gain matched 60 / 20 for brightness at a third of the
shutter time.) Keep the result as the defaults in
`/usr/local/bin/speedcam-camera-init.sh` (or as `SPEEDCAM_EXPOSURE` /
`SPEEDCAM_GAIN` in an `Environment=` line of a drop-in for
`speed-camera.service`). That script locks exposure, gain and white balance
before every start and reads each value back.

**Verify:** a snapshot of a passing car shows it sharp, not smeared.

### 6. Aim, through a tunnel

```
sudo systemctl start speedcam-preview
```

on the Pi, then from the reader's computer:

```
ssh -N -L 8081:127.0.0.1:8081 <user>@<pi>
```

and open `http://localhost:8081/`: a live view with the crop band and ruler,
about 18–20 frames a second. The preview has no login, never starts at
boot, and stops the tracker while it runs (they share the camera). Stop it
when done: `sudo systemctl stop speedcam-preview`.

Aim **square on to traffic** (across the road, not along it), and keep the
crop band (`MO_CROP_Y_UPPER` / `MO_CROP_Y_LOWER` in the plugin) a **narrow
horizontal strip across the lane**: one pixels-to-millimetres constant is
only true at one distance.

**Verify:** a photo of the aimed view, kept with the deployment's notes.

### 7. Calibrate, each direction separately — the reader does the driving

1. Park the reference car in the near lane, inside the band. Measure it.
2. With `CALIBRATE_ON = True` (the shipped default), saved images carry
   tick marks every 10 px. Read the car's length in pixels.
3. In `/opt/speed-camera/plugins/ps3eye.py`, set `CAL_OBJ_MM_L2R` (the
   true length in mm) and `CAL_OBJ_PX_L2R` (pixels).
4. Repeat in the far lane for `CAL_OBJ_*_R2L`.
5. Set **both** `SPEEDCAM_CALIBRATED = True` and `CALIBRATE_ON = False`
   (calibration mode logs every track and stops pruning saved images, which
   fills the card in a week).
6. `sudo systemctl enable --now speed-camera.service`.

Never use 0 as "not calibrated yet": the program divides by `CAL_OBJ_PX` at
start-up, so a zero crashes it before the camera opens, and you can't run it
to calibrate. The shipped placeholders are non-zero for that reason, and the
`SPEEDCAM_CALIBRATED` flag is the real gate.

### 8. Validate, and set the directions

**Validate:** drive past several times in **each** direction at a steady
known speed (cruise control, a passenger reading the speedometer), and
compare the logged speeds (`journalctl -u speed-camera`). Adjust a
direction's pixel count until it matches. A one-direction check passes
even when the other lane's constant is wrong.

**Directions:** walk past the lens, read which of L2R and R2L was logged,
and set `L2R_DIRECTION` / `R2L_DIRECTION` in
`/opt/speed-camera/speedcam.conf` to the real compass directions. They are
camera-relative; turn the unit around and they swap, and backwards values
look completely normal in the data.

**Verify:** `python3 /opt/speed-camera/speedcam_export.py --dry-run`
shows the test passes with the right speeds and directions, stamped in the
reader's time zone.

### 9. Deploy, collect, report

Before it goes out and again when it comes back: `timedatectl`, and the
clock against a phone. Power: a Pi 3B with the camera draws 4–5 W; a
20,000 mAh bank lasts about 13–15 hours. For days, use mains power.

The exporter appends to `/var/lib/speedcam/speedcam_traffic.csv` every 10
minutes and never duplicates a row. Copy the CSV off and put it next to the
fixed camera's data; the same report script reads it.

**Verify:** the report shows the new street, and the hourly counts match
when the unit was actually out.

## Gotchas (from the book and the author's unit)

- **No clock, no data, and a wrong clock looks right.** On the author's
  first boot with an unset module, the clock went 2000-01-01 → the time the
  Pi was last running (systemd's saved clock) → the right time once the
  network answered. Offline there's no third step: every row is shifted
  back by however long the unit sat unpowered, in the current year, and a
  "reject rows before this year" check passes all of them. The clock check
  is the guard; it refuses to start unless the clock is synchronized or
  agrees with a working module within 10 minutes.
- **Treat the module as a consumable.** Its cell is soldered on, and when
  it dies there is no error: the module resets and systemd's saved clock
  makes everything look normal. Buy a spare, and check `timedatectl` before
  and after each deployment. The kernel's `SET TIME!` warning on this
  module appeared after harmless outages too (about 6 seconds lost), so the
  check deliberately doesn't refuse on it.
- **640×480 at 30 fps, not 60.** The Eye only sends uncompressed video: 60
  fps is 36.9 MB/s, past what a Pi 3B's shared USB 2 bus carries. For more
  frames, drop to 320×240 first.
- **`MO_MAX_X_DIFF_PX` must clear the fastest car.** At 30 fps a 60 mph car
  moves about 54 px a frame; the project's default of 20 would silently
  discard every car. Shipped at 70.
- **Leave `MO_MAX_SPEED_OVER = 0`.** Logging only fast cars inflates every
  "percent over the limit", which needs every car in the denominator.
- **Auto-exposure must stay off.** When it re-meters on a car entering the
  frame, the whole image changes brightness and the tracker reads it as
  motion.
- **The preview from a laptop on Wi-Fi may not connect** when the Pi is on
  another network segment, while SSH does. The tunnel works from anywhere.
- **The PS3 Eye can't read a plate and does poorly after dusk.** That's the
  price of 60 fps and a short exposure.

## Rollback

`sudo systemctl disable --now speed-camera speedcam-export.timer`, remove
the units from `/etc/systemd/system/`, `/opt/speed-camera`,
`/var/lib/speedcam` (copy the CSV off first), the tools in
`/usr/local/bin/speedcam-*`, the DS3231 lines from the boot config, and
`01-speedcam.conf` (then reload sshd). Or reflash the card.
