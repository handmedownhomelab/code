# Playbook 2.5 — The Homelab Menu and `audit.sh`

> **For the reader.** Read this whole file and the three files in `2.5/`
> before you give them to your AI assistant. You need a workstation (Mac or
> Linux) with zsh or bash, and SSH keys from it to your hosts (book 2.3).
> Then say: *"Follow this playbook. Ask me before every step marked
> CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 2.5 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's hosts, user names and
   addresses. The scripts' arrays hold the book's examples, not theirs.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before editing the reader's shell startup file (`~/.zshrc` or
   `~/.bashrc`): show the lines you will add, and add, never replace.
4. **Read-only on the hosts.** Nothing in this playbook changes a host. The
   only commands you run there are the reachability check and the read-only
   examples below.
5. **Verify by effect**: run the menu and the report, and read what they
   print.

## Goal: what "done" looks like

- [ ] `~/bin/ssh-menu.sh` and `~/bin/audit.sh` exist, are executable, and
      list the reader's own hosts.
- [ ] Typing `m` draws the menu; `m <number>` and `m <name>` connect;
      `m <letter>` runs that command without drawing the menu.
- [ ] `audit.sh` with no arguments prints one report covering this machine
      and every host, and marks each host that can't be reached **NO KEY**
      or **UNREACHABLE**.
- [ ] A failing command shows a non-zero `[exit: N]` in the report.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The reader's shell | Decides where `m()` goes, and which variant | `echo $SHELL` |
| Each host's name and `user@address` | The arrays at the top of both scripts | Ask; the host list in `~/.claude/CLAUDE.md` (book 2.3) if there is one. Some hosts log in as a different user (Home Assistant's SSH add-on is `root`) |
| Which hosts already accept this machine's key | So the first report holds no surprises | `ssh -o BatchMode=yes -o ConnectTimeout=5 <user>@<host> true` for each; exit 0 means yes |
| Three or four commands the reader runs every week | The menu's letter entries | Ask. Shell functions are allowed: see step 3 |

## Steps

### 1. Install the two scripts

Copy `2.5/ssh-menu.sh` and `2.5/audit.sh` to `~/bin/` and `chmod +x` both.
`~/bin` doesn't need to be on `PATH`: everything calls them by full path.

**Verify:** `~/bin/ssh-menu.sh --help` and `~/bin/audit.sh --help` each
print their usage block.

### 2. Put the reader's hosts in both arrays

Edit `NAMES` and `TARGETS` at the top of `ssh-menu.sh`, and `LABELS` and
`TARGETS` at the top of `audit.sh`. The arrays are **parallel**: the third
name goes with the third target, so both arrays in a file must be the same
length. Keep the two files in the same order. Show the reader both blocks
before saving.

**Verify:** `bash -n ~/bin/ssh-menu.sh && bash -n ~/bin/audit.sh` prints
nothing, and the menu in step 4 shows every host with the right target
beside it.

### 3. Put the reader's commands in the menu

Edit `CKEYS`, `CLABELS` and `CCMDS` in `ssh-menu.sh`, one entry per weekly
command (again parallel arrays). Keys are single letters, so they never
collide with a host number; case matters, `p` and `P` differ. Keep the `a`
entry, which runs `audit.sh`. An entry can be a shell function from the
reader's startup file, such as a tunnel that cleans up on Ctrl-C; that is
why the menu prints the command instead of running it.

**Verify:** `~/bin/ssh-menu.sh a` prints exactly `~/bin/audit.sh` on
stdout, and `~/bin/ssh-menu.sh 1 2>/dev/null` prints exactly
`ssh <first target>`. Nothing else may reach stdout: the `m` function runs
whatever does.

### 4. Add `m` to the shell — CONFIRM

zsh: append the function from `2.5/m.zsh` to `~/.zshrc`. bash: append the
same function to `~/.bashrc` with the two `print` lines replaced by
`printf '%s\n' "> $cmd"` and `history -s "$cmd"` (the comment at the top of
`m.zsh` shows it). Then open a new terminal.

**Verify**, in the new terminal:
- `type m` says it is a shell function.
- `m` draws the menu (hosts numbered on top, letters below, `q Quit`).
  Type `q`: it prints `Bye.` and returns to the prompt.
- `m 1` prints `> ssh <first target>` and connects. Log out.
- `m <name of host 2>` does the same for host 2.
- `m nosuchhost` prints `m: no host or command matching 'nosuchhost'`, and
  `echo $?` then prints 1.
- `history | tail -3` shows the `ssh` command `m` ran.

### 5. The first report

Run `~/bin/audit.sh` (no arguments: `uptime` and `uname -a` everywhere).

**Verify:**
- One header, then a section for this machine marked `(local)`, then one per
  host, then `END OF REPORT`.
- Every host the reader expects to reach shows `uptime` output and
  `[exit: 0]`. Any other host shows **NO KEY** (it answered but refused
  this machine's key) or **UNREACHABLE** (with the first line of SSH's
  error). Go through each one with the reader: is that expected?
- The run never stops to ask for a password. If one does, `BatchMode=yes`
  has been removed from `SSH_OPTS`; put it back.
- An unreachable host costs its `ConnectTimeout` (10 seconds) per run, so a
  run with one dead host takes about ten seconds longer. That's expected.

### 6. Prove the exit codes are real

Run `~/bin/audit.sh "false" "df -h /"`.

**Verify:** every reachable section shows `$ false` followed by
`[exit: 1]`, and `df` followed by `[exit: 0]`. If `false` shows
`[exit: 0]`, the script is reading `$?` (the status of the `sed` at the end
of the pipe) instead of `${PIPESTATUS[0]}`.

### 7. A command file

Write three read-only checks to `~/checks.txt`, one per line (blank lines
and lines starting with `#` are skipped), for example `df -h /`, `free -h`
and `test -f /var/run/reboot-required && echo REBOOT NEEDED || echo ok`.
Run `~/bin/audit.sh -f ~/checks.txt > ~/audit-report.txt`.

**Verify:** the saved file lists all three under `Commands:` and has a
section per host. `~/bin/audit.sh -f nosuchfile` exits 2 and says
`-f needs a readable file`.

## Gotchas (from the book and the test)

- **stdout is a contract.** The menu, colors and messages go to stderr;
  exactly one command goes to stdout, and `m` evals it. A debugging `echo`
  added to `ssh-menu.sh` without `>&2` becomes a command `m` tries to run.
- **Why the indirection.** A script can't see the shell's functions, and a
  function's Ctrl-C trap only fires in the shell that owns it. Printing the
  command and letting the shell run it fixes both, and puts the command in
  history.
- **NO KEY is not UNREACHABLE.** With `BatchMode=yes` a missing key and a
  dead host both just fail. The script reads SSH's error text to tell them
  apart. In the book's lab one Pi-hole showed as unreachable for seven weeks
  because its `authorized_keys` had been emptied on purpose. When you remove
  access somewhere, list what else relied on it.
- **`$?` after a pipe is the last command's status.** `cmd | sed` always
  looks successful. That's what `PIPESTATUS` is for.
- **Keep labels under about 21 characters.** The command columns are
  padded to that width; a longer label pushes the next column out of line.
  Cosmetic, but it's the first thing you'll notice.
- **Different users on different hosts.** Each target carries its own user.
  A host that logs in as `root` into a minimal shell (Home Assistant's SSH
  add-on) may lack commands the others have; expect a non-zero exit there,
  not a broken script.
- **`StrictHostKeyChecking=accept-new`** trusts a host the first time it is
  seen and refuses if its key later changes. If a host was rebuilt, find
  out why its key changed, then remove the old line with `ssh-keygen -R`.
- **A fan-out you run is a deliberate choice.** For anything broad or
  sensitive, the book keeps a human between the AI and the fleet: you run
  `audit.sh`, you paste the report back. Don't give an AI an unattended
  shell on every host instead (book 2.5, "Two ways to give an AI reach").

## Rollback

Delete the `m()` function from the shell startup file, and remove
`~/bin/ssh-menu.sh`, `~/bin/audit.sh`, `~/checks.txt` and any saved
reports. Nothing was changed on any host.
