# Playbook 2.2 — One wiki on every machine

> **For the reader.** Read this whole file and the files in `2.2/` before you
> give them to your AI assistant. You need a wiki folder (book 2.1), an
> always-on machine for the hub, and SSH keys from each workstation to it.
> Then say: *"Follow this playbook. Ask me before every step marked
> CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 2.2 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's hub, user name, wiki names
   and workstations.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before moving or deleting any existing wiki folder, and
   before editing `~/.claude/settings.json` (merge into it; never replace
   it).
4. **Nothing is deleted until a restore has been proven** (step 7).
5. **Verify by effect**, on a second machine.

## Goal: what "done" looks like

- [ ] Each wiki is a bare repository on the hub, `~/git/<wiki>.git`.
- [ ] Every workstation has a clone at `~/wiki/<wiki>`, and a push from one
      reaches the others at their next session start.
- [ ] If programs on the hub read the wiki, the hub's own copy updates on
      every push.
- [ ] Claude Code pulls at session start and pushes at the end, never
      blocks a session, and warns about uncommitted work and missing
      `log.md` entries.
- [ ] `log.md` has `merge=union`, and nothing else does.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The hub | Always on, reachable by SSH from every workstation | Ask; the book uses the GPU tower |
| The user@host for the hub | Clone URLs and `WIKI_HUB` | Ask; test `ssh user@hub true` from each workstation |
| The wikis, and where they live now | What to migrate | Ask; check for a cloud-drive folder (step 7) |
| Each workstation | Each needs a clone and the hooks | Ask |
| Whether programs on the hub read the wiki | Decides the post-receive hook | Ask |

## Steps

### 1. The hub — CONFIRM

Install git on the hub. For each wiki: `git init --bare ~/git/<wiki>.git`
(set `main` as the default branch).

### 2. The first push

From the workstation that has the wiki: make it a git repository if it
isn't one, add `.gitattributes` containing **`log.md merge=union`**, commit,
add the hub as `origin` (`<user>@<hub>:git/<wiki>.git`) and push `main`.

### 3. The hub's own copy — only if programs on the hub read the wiki

Install `2.2/post-receive` as `~/git/<wiki>.git/hooks/post-receive` (mode
755), then clone the bare repository to `~/wiki/<wiki>` **on the hub**. Tell
the reader that this copy is disposable: it's reset on every push, so nobody
edits there.

**Verify:** the next push from a workstation prints `post-receive: <wiki>
checkout updated to <commit>`. (Before the hub's clone exists, it prints
"no checkout … skipping", and that's fine.)

### 4. A clone on every workstation

`git clone <user>@<hub>:git/<wiki>.git ~/wiki/<wiki>` on each. Every wiki
lives directly under `~/wiki/`: the scripts look there.

### 5. The hooks — CONFIRM per workstation

Copy `2.2/wiki-sync.sh` and `2.2/check-wiki-log.sh` to `~/.claude/hooks/`,
set `WIKI_HUB` at the top of `wiki-sync.sh`, and **merge** the `hooks`
section from `2.2/settings-hooks.json` into `~/.claude/settings.json`.
Show the reader the merged file before saving it.

**Verify**, using two workstations:
- Commit a small change (page plus `log.md` entry) on A and run
  `wiki-sync.sh push`. `~/.claude/wiki-sync.log` says `push <wiki>`.
- Run `wiki-sync.sh` on B. Its log says `pull <wiki> <old> -> <new>`, and
  the change is there.
- Leave an uncommitted edit on B. The pull logs `skip <wiki> (dirty)`, and
  the push run prints the UNCOMMITTED warning.
- `check-wiki-log.sh` on B warns "modified wiki/ pages but no log.md
  change". Then undo the edit.

### 6. The failure paths

- **Hub unreachable:** set `WIKI_HUB` to an address that doesn't answer, in
  a copy of the script. A run exits 0 in about 3 seconds and logs `SKIP`.
- **Two machines, one log:** append to `log.md` on A and on B, commit both,
  push A. B's push hook reports `push FAILED — push by hand`. On B, `git
  pull --rebase` combines both entries with no conflict, then push. (In
  testing, the same thing without the `merge=union` line gave `CONFLICT in
  log.md`.)

### 7. Moving out of a cloud folder — CONFIRM, only if that's where it lives

As book 2.2 describes:
1. Back up three ways: a copy of the folder, a `git bundle`, and a tarball
   of the hub.
2. **Prove one restores:** clone the bundle to a temporary folder and
   compare its `HEAD` with the commit written down beforehand.
3. Copy out of the cloud folder; don't move. Delete the originals only at
   the very end, with the reader's yes.

## Gotchas (from the book and the test)

- **Old is worse than broken.** A clone that wasn't pulled answers
  confidently from yesterday. That's why the pull runs at every session
  start.
- **The push hook never commits.** Uncommitted work stays local until
  someone commits it with a log entry.
- **`merge=union` only for `log.md`.** It keeps both sides' lines, which is
  right for an append-only log and wrong for anything else.
- **A check that can't find its target must say so.** Test each hook once by
  breaking what it guards (step 5's dirty edit does that).
- **Cloud folders and background tools on macOS:** a program started over
  SSH or by another program can hang, not fail, opening files there. Git
  clones avoid it.
- **Several AI sessions on one machine share one clone.** The book's
  optional `wiki-lock` gives each wiki one writer at a time; the sync script
  respects it if present.

## Rollback

Remove the hooks from `~/.claude/settings.json`. The clones and the hub stay
as plain git repositories.
