# Playbook 2.4 — Teaching the AI from its mistakes

> **For the reader.** Read this whole file and the two scripts in `2.4/`
> before you give them to your AI assistant. You need Claude Code on your
> workstation (book 2.3). Steps 5 and 6 also need the git hub from book 2.2
> and SSH keys to it. Then say: *"Follow this playbook. Ask me before every
> step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* set up what section 2.4 describes: the memory folder you write
> to yourself. Follow the rules below for the whole session.

## Rules for the assistant

1. **Discover, don't assume.** The memory folder's path depends on where
   sessions start; find it, don't guess it.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before editing `~/.claude/settings.json` or
   `~/.claude/CLAUDE.md` (merge into them, never replace them), and before
   moving or deleting an existing memory folder.
4. **No secrets in memory, ever.** Memory files are plain text, loaded into
   every session and, after step 5, copied to other machines. A path to a
   secret is fine; the secret is not.
5. **The reader decides what is true.** Propose lessons; save one only when
   the reader agrees it is right.
6. **Verify by effect**: open a new session and check that the memory is
   there and used.

## Goal: what "done" looks like

- [ ] Auto memory is on, and the reader knows where the folder is.
- [ ] One memory folder serves the reader's homelab sessions, not one per
      directory they happen to start in.
- [ ] At least one feedback memory exists, written as a rule with **Why**
      and **How to apply**, and indexed in `MEMORY.md` by the moment it
      matters ("Before …").
- [ ] `~/.claude/CLAUDE.md` tells the AI how to write lessons.
- [ ] Optional: the folder is a git clone on every workstation, pulled at
      session start and pushed at the end.
- [ ] A weekly read-only report checks the folder and changes nothing.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Claude Code version | Settings and behavior below are current Claude Code | `claude --version`; update if it's old |
| Whether auto memory is on | It is on by default; someone may have turned it off | In a session, `/memory` shows the auto memory toggle. Also check `~/.claude/settings.json` for `"autoMemoryEnabled": false` and the shell for `CLAUDE_CODE_DISABLE_AUTO_MEMORY` |
| Where the reader starts sessions | The folder is `~/.claude/projects/<project>/memory/`, and `<project>` comes from the git repository, or the directory, a session starts in | Ask; then `ls -d ~/.claude/projects/*/memory` |
| Memories that already exist | Don't overwrite a store that has history | `ls` each folder found above; `wc -l` its `MEMORY.md` |
| The git hub and user (steps 5–6) | Where the memory repository lives | Book 2.2; test `ssh <user>@<hub> true` |
| Every workstation | Each needs the clone and the hooks | Ask |

## Steps

### 1. Choose one memory folder — CONFIRM

Auto memory is per project: a session started in `~/projects/foo` and one
started in `~` use different folders. For a homelab that splits the
lessons. Two ways to keep one store, and the reader picks:

- **Start every homelab session in the same folder** (the book's lab starts
  them in one working folder). Nothing to configure.
- **Or set the folder explicitly** in `~/.claude/settings.json`:
  `"autoMemoryDirectory": "~/.claude/memory"`. Every project then shares it.

If more than one folder already holds memories, list them for the reader
and merge the ones they want to keep into the chosen folder, by hand, before
going on. Leave the old folders where they are until step 7 passes.

**Verify:** in a new session, `/memory` lists the auto memory folder the
reader chose.

### 2. The first memory, by hand

Write one feedback memory the reader agrees with, in the folder, as its own
file. The book's example is a good first one:

```
---
name: feedback-verify-effect-not-exit-code
description: Before reporting a change as done, read the state it should
  have changed
metadata:
  type: feedback
---
A command's exit status answers the question the command was asked, not the
one we meant. `mount` with `nofail` returns 0 when nothing was mounted.

**Why:** backups filled a system disk because a script trusted mount's
exit code.

**How to apply:** after any mount, write or restart, do one independent
read of the effect (mountpoint -q, read the file back, query the service).
```

Save it as `feedback-verify-effect-not-exit-code.md` (the filename matches
`name:`). Then add one line to `MEMORY.md` in that folder, creating it if
needed, that starts with the **moment** the lesson matters:

```
- [Before trusting a mount, write or restart](feedback-verify-effect-not-exit-code.md) — read the effect, not the exit code
```

**Verify:** start a new session in the usual folder and ask *"What do you
do before reporting a mount as done, and where did you learn it?"* The
answer names the rule and the memory file. If it answers from general
knowledge, the session is using a different folder: back to step 1.

### 3. Tell the AI how to write lessons — CONFIRM

Merge a short section into `~/.claude/CLAUDE.md` (book 2.3):

```
## Memory
- When I correct you, or confirm an approach that wasn't obvious, offer to
  save it as a feedback memory: the rule, then **Why:** and **How to apply:**.
- One fact per file. Its MEMORY.md line starts with the moment it matters
  ("Before calling a disk healthy…"), not the topic.
- Before saving, check for an existing memory that covers it; update that one.
- Never put secrets, tokens or passwords in a memory.
```

**Verify:** in a new session, correct the AI on something small and true
(for example: *"On my hosts, use `systemctl status`, never `service`"*).
It offers to save a memory, or says it saved one. Open the new file: it has
a `name:` matching its filename, the rule, **Why** and **How to apply**,
and `MEMORY.md` gained a line that starts with "Before" or "When".

### 4. The weekly check

Copy `2.4/memory-check.sh` to `~/bin/` and `chmod +x` it. If the reader has
more than one folder under `~/.claude/projects/*/memory`, pass the chosen
one as the argument (or set `MEM_DIR` at the top).

**Verify:**
- `~/bin/memory-check.sh --no-ai` writes `~/memory-reports/latest.md`, and
  on the new store it says `Clean.`
- **Break it on purpose**, on a copy: `cp -R <folder> /tmp/memtest`, change
  one file's `name:`, add `[[no-such-memory]]` to another, and add an index
  line to a missing file. `~/bin/memory-check.sh --no-ai /tmp/memtest`
  reports all three. Delete `/tmp/memtest`.
- `ls -l --time-style=full-iso <folder>` (on a Mac, `ls -lT`) before and
  after a full run (without `--no-ai`): nothing in the folder changed. The
  report has a `## Judgment pass` section ending in `## To apply`.
- If Claude Code isn't logged in for that user, the full run exits 3, and
  the report keeps the mechanical half and says the judgment pass failed.

Schedule it weekly, at a time the machine is awake: a cron line on Linux;
on a Mac, a launchd agent with `StartCalendarInterval` (cron doesn't run
while a Mac sleeps, and doesn't catch up). The judgment half calls
`claude -p`, so it needs Claude Code logged in for the user it runs as.

### 5. One memory on every workstation (optional) — CONFIRM

Only with the git hub from book 2.2.

1. On the hub: `git init --bare ~/git/claude-memory.git` and
   `git -C ~/git/claude-memory.git symbolic-ref HEAD refs/heads/main`.
2. On the workstation that has the memories: in the memory folder,
   `git init -b main`, and add `.gitattributes` with the single line
   **`MEMORY.md merge=union`**. Then `git add -A`, commit, add the hub as
   `origin` (`<user>@<hub>:git/claude-memory.git`), and
   `git push -u origin main`.
3. On each other workstation: find (or create, step 1) its memory folder,
   **move it aside** (`mv memory memory.pre-git`), and
   `git clone <user>@<hub>:git/claude-memory.git memory` in its place. Then
   compare the old folder with the clone, and copy across any memory that
   only the old one had. This is the step that costs something if skipped.
4. On every workstation: `git config --global user.name` and `user.email`
   must be set (the hook commits), and SSH to the hub must work with no
   prompt.

**Verify:** `git -C <folder> log --oneline -1` shows the same commit on
every workstation.

### 6. The hooks — CONFIRM per workstation

Copy `2.4/claude-memory-sync.sh` to `~/.claude/hooks/` and `chmod +x`. If
step 1 used `autoMemoryDirectory`, add that folder to `EXTRA_STORES` at the
top. Merge into `~/.claude/settings.json`: `claude-memory-sync.sh pull` as
a **SessionStart** hook and `claude-memory-sync.sh push` as a **Stop**
hook, beside any wiki hooks from 2.2. With both, the `hooks` section reads:

```
{
  "hooks": {
    "SessionStart": [ { "hooks": [
      { "type": "command", "command": "bash \"$HOME/.claude/hooks/wiki-sync.sh\"" },
      { "type": "command", "command": "bash \"$HOME/.claude/hooks/claude-memory-sync.sh\" pull" } ] } ],
    "Stop": [ { "hooks": [
      { "type": "command", "command": "bash \"$HOME/.claude/hooks/check-wiki-log.sh\"" },
      { "type": "command", "command": "bash \"$HOME/.claude/hooks/wiki-sync.sh\" push" },
      { "type": "command", "command": "bash \"$HOME/.claude/hooks/claude-memory-sync.sh\" push" } ] } ]
  }
}
```

Show the reader the merged file before saving it, and check that it parses
(`python3 -m json.tool ~/.claude/settings.json`).

**Verify**, with workstations A and B:
- On A, create `test-sync.md` in the memory folder and run
  `~/.claude/hooks/claude-memory-sync.sh push`.
  `~/.claude/memory-sync.log` says `committed 1 change(s)` and `pushed ok`.
- On B, run `… pull`. The log says `pulled ok, now at <commit>`, and the
  file is there.
- On B, delete it and `push`; on A, `pull`. It's gone on A too, and still
  in `git log` on the hub.
- A `push` with nothing changed returns in well under a second and writes
  nothing to the log (it runs at the end of every turn).
- **Two machines at once:** save a different memory on A and on B (each
  adds a line to `MEMORY.md`), then `push` on A, then on B. Both push, and
  `MEMORY.md` on both ends up with both lines. (In the test, without the
  `merge=union` line from step 5, B's push logged `pre-push rebase failed`
  and B's commits stayed local until merged by hand.)
- **Hub unreachable:** on B,
  `git -C <folder> remote set-url origin <user>@192.0.2.1:git/claude-memory.git`
  (an address that never answers), then `pull`. It exits 0 within about
  five seconds and logs `pull failed (local memory unchanged)`. Set the URL
  back.
- Start a real session on B: its first turn knows the lesson from step 3.

### 7. Clean up

Once step 6 passes on every workstation, the reader decides about the
`memory.pre-git` folders and any old per-project folders from step 1.
CONFIRM before deleting anything.

## Gotchas (from the book and the test)

- **Index the moment, not the topic.** "Before calling a disk healthy from
  SMART" fires when the AI is about to do exactly that. "SMART notes" never
  fires. This is the decision that made memory work in the book's lab.
- **Only the start of `MEMORY.md` is loaded:** the first 200 lines or
  25 KB, whichever comes first. Topic files are read on demand. Keep one
  short line per memory; `memory-check.sh` warns at the limits.
- **Memory is per project and per machine** until you make it otherwise
  (steps 1 and 5). A session started in another folder, or on another
  machine, doesn't know what this one learned.
- **Feedback memories compound; the others mostly don't.** The book's lab
  has about 90 of them. Write one the first time the AI gets something
  wrong, while the details are fresh.
- **`MEMORY.md` is the file two machines both change.** Every new memory
  adds a line to it, so two machines that each learn something conflict on
  it. `merge=union` keeps both lines; it's right for this one index file
  and wrong for anything else in the folder.
- **Deletions propagate.** Pruning a memory on one machine removes it
  everywhere at the next pull. That's intended; the hub's history keeps it.
- **The check reports; you decide.** `memory-check.sh` gives the judgment
  pass read-only tools, so it can't edit the store even by mistake. Apply
  findings in a normal session. "Clean" is the usual result.
- **Show a secrets file's shape, never its lines.** Cutting each line at
  `=` still prints any line without one, value and all (the book's war
  story). If a memory needs to mention a secret, it names where the secret
  lives.
- **A link inside a code example counts as a link** to the mechanical
  check. If a memory quotes `[[example]]` syntax, expect a finding for it;
  that's the parser, not a broken store.

## Rollback

Remove the two hooks from `~/.claude/settings.json`, the `## Memory`
section from `~/.claude/CLAUDE.md`, the `autoMemoryDirectory` line if step 1
added it, and the scheduled check. The memory folder stays: plain markdown
files, with `.git` inside if step 5 ran. To stop memory altogether, set
`"autoMemoryEnabled": false`.
