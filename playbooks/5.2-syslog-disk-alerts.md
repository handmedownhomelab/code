# Playbook 5.2 — Syslog, disk-health alerts, and email that arrives

> **For the reader.** Read this whole file and the files in `5.2/` before
> you give them to your AI assistant. Alert mail needs a working relay on
> each host (book 1.2). Then say: *"Follow this playbook. Ask me before
> every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 5.2 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's hosts and addresses are the
   author's. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs
   software, changes a service's configuration, or deletes anything is a
   CONFIRM step even if this file forgot to mark it.
4. **Validate before restarting:** `rsyslogd -N1` must pass before any
   `systemctl restart rsyslog`.
5. **An alert isn't done until it's in the inbox.** "The daemon is active"
   and "Postfix can send" are not proof. Fire each alert through its own
   mechanism and have the reader confirm it arrived.
6. If the reader keeps a homelab wiki, record which hosts forward, which run
   smartd, and the date each alert path was proven.

## Goal: what "done" looks like

- [ ] A collector writes `/var/log/remote/<host>/<date>.log` for every
      sender, compresses after a day, and deletes after 90.
- [ ] Every Linux host forwards to it over TCP, and the gateway and Home
      Assistant send to it too.
- [ ] Every host with disks runs smartd, and smartd's **own** test message
      has reached the reader's inbox from each one.
- [ ] Each cron job and timer whose failure matters has a mail or push path,
      checked against the four ways cron output dies.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Where the collector will run | A small container; give its log tree its own disk if you can | Ask; the book uses the second Proxmox host |
| The collector's **IP address** | Clients use the address, not a name, so logging doesn't depend on DNS | Ask; fixed by DHCP reservation (book 1.4) |
| Which hosts forward | Every Linux host, plus the gateway and Home Assistant | List them |
| Which hosts have disks to watch | smartd needs real disks, so not containers | `lsblk` on each physical host and VM |
| Whether each host's mail relay works | smartd and cron mail use it | Book 1.2; `echo test \| mail -s test root` |

## Steps

### 1. The collector — CONFIRM

A small Debian container. **Debian 13 doesn't install rsyslog by default**
(it relies on the journal), so install `rsyslog`. Copy
`5.2/10-remote-collector.conf` to `/etc/rsyslog.d/`. If the gateway isn't
UniFi, delete the firewall block (the file says which). Then `rsyslogd -N1`
and restart rsyslog.

**Verify:** `ss -lntu` shows port 514 on UDP and TCP.

### 2. Retention

Install `5.2/prune-remote-logs.sh` as `/usr/local/sbin/prune-remote-logs.sh`
(mode 755), with `prune-remote-logs.service` and `.timer`. Enable the timer.
It compresses day files after one day and deletes after 90.

**Verify:** create a back-dated test file in a host folder (`touch -d "100
days ago"`), plus one `-d "3 days ago"`, and start the service once: the old
one is gone, the 3-day one is `.gz`. Remove the test folder.

### 3. Forward every Linux host — CONFIRM per host

On each host: install `rsyslog` if missing, copy
`5.2/60-forward-to-syslog.conf` to `/etc/rsyslog.d/` with the collector's
**IP address** as `target`, `rsyslogd -N1`, restart rsyslog. It forwards a
copy over TCP with a disk queue. Local logs are untouched.

**Verify:** `logger -t playbooktest "hello"` on the host, then on the
collector the line appears in `/var/log/remote/<host>/<today>.log`.

### 4. The gateway and Home Assistant — the reader, in their settings

Give the reader the steps for their gateway model (UniFi: remote syslog
server in the controller's settings) and for Home Assistant (its syslog
integration). **Verify** each appears as a folder on the collector.

### 5. Prove the collector's safety rules

Once, from any host, send three raw lines to the collector's TCP 514 (bash
`/dev/tcp` works): one claiming the host name `../../etc/cron.d`, one with
`[CUSTOM1_LAN-D-1]` in it (only if the gateway block is kept), and one
normal line.

**Verify:** nothing new appears under `/etc` on the collector (the test
filed the path-like name under the sender's IP address). The `CUSTOM1` line
is only in `<date>-firewall.log`. The collector's own `/var/log/syslog`
contains none of the three. Delete the test folders.

### 6. SMART alerts that reach the inbox — CONFIRM per host

On each host with real disks (a container has none to check):

1. Install `smartmontools` **and `bsd-mailx`**. smartd's mail hook stops
   with "Your system does not have /usr/bin/mail" when `mail` is missing,
   and nothing installs it for you: not smartmontools, not Postfix. That
   message goes to smartd's log, not to an inbox.
2. Configure smartd to mail `root` (and make sure `/etc/aliases` sends
   `root` to the reader's address, then `newaliases`).
3. Fire smartd's own test: `smartd -q onecheck -M test`.

**Verify:** the reader confirms the test message arrived, from each host.
Record the date per host.

Reading SMART later: "PASSED" can't express wear. Read the attributes
(reallocated and pending sectors, an SSD's percentage used). Don't poll a
running long self-test often: that can restart it.

### 7. The four ways cron output dies

For each scheduled job that matters, check:

1. Does it redirect its own output (`> /dev/null`, `>> file`)? Then cron has
   nothing to mail.
2. Is there a `MAILTO=""` in that crontab?
3. Does `/etc/aliases` have a `root:` line to a real address?
4. Is it a **systemd timer**? Timers have no mail path. Add `OnFailure=` to
   a mail unit, or a push monitor (playbook 5.1).

**Verify:** make one job fail on purpose and see the mail or the push alert
arrive.

## Gotchas (from the book and the test)

- **Debian 13 has no rsyslog by default**, on the collector *or* the
  clients. A host without it forwards nothing, silently.
- **Clients use the collector's IP address.** A DNS outage is exactly when
  you want the logs.
- **TCP, not UDP, between your own hosts.** UDP drops silently. (Some
  gateways only send UDP; the collector takes both.)
- **The collector doesn't alert.** It's for afterwards.
- **`bsd-mailx` is the difference between a smartd that alerts and one
  that only logs.**
- **An active daemon isn't a delivered alert.**

## Rollback

Remove the client config from each host and restart rsyslog. Disable the
collector's timer and remove the container (the logs go with it).
