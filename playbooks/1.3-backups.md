# Playbook 1.3 — Backups that tell you when they fail

> **For the reader.** Read this whole file, and `1.3/proxmox-backup-sync.sh`,
> before you give them to your AI assistant. You need a Proxmox host, a USB
> drive for backups, and mail to root that arrives (playbook 1.2). Then say:
> *"Follow this playbook on <host>. Ask me before every step marked
> CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 1.3 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Identify drives by model and serial number,
   never by letter (`sdb` today can be `sdc` after a reboot).
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before formatting anything, editing `/etc/fstab`, or
   changing a backup job. Formatting the wrong disk is the one mistake here
   that can't be undone: show the reader the disk's model, serial and size
   and wait for a yes.
4. **Validate before rebooting:** after any `/etc/fstab` edit, run `systemctl
   daemon-reload` and `findmnt --verify`. A bad line can stop a boot.
5. **Verify by effect**, including by breaking it on purpose (step 5).

## Goal: what "done" looks like

- [ ] The backup drive is mounted by UUID with a self-healing automount.
- [ ] Proxmox's backup storage refuses to work when the drive isn't mounted
      (`is_mountpoint`), and shows the **drive's** size, not the root disk's.
- [ ] A nightly backup job names every guest, uses zstd compression, and is
      staggered against any other host's job.
- [ ] Pulling the drive makes the storage inactive and the backup fail
      loudly, with nothing written to the root disk. Reconnecting it brings
      everything back without a human.
- [ ] A second machine copies the backups nightly and refuses when the
      source looks wrong.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The backup drive | Format the right one | `lsblk -o NAME,MODEL,SERIAL,SIZE,ROTA`, with the reader confirming |
| Every guest on the host | The job lists them explicitly | `qm list`, `pct list` |
| Other hosts' backup times | Stagger them | Ask; `pvesh get /cluster/backup` on each |
| Bind mounts in containers | Proxmox's backup skips them | `grep ^mp /etc/pve/lxc/*.conf` |
| The machine that keeps the second copy | Off-host copy | Ask; it needs space for a few nights |

## Steps

### 1. Format and mount by UUID — CONFIRM

Format the confirmed drive (ext4, with a label), make the mount folder
(`/mnt/usb-backups`), and add one `/etc/fstab` line by **UUID** with
`defaults,nofail,x-systemd.automount,x-systemd.device-timeout=10,x-systemd.mount-timeout=30`.
Reload systemd and start the automount (`systemctl restart local-fs.target`
is enough).

**Verify:** `systemctl list-units --type=automount` shows it `active
waiting`; `ls /mnt/usb-backups` mounts the drive; `findmnt` shows the
device under the automount.

### 2. The backup storage — CONFIRM

`pvesm add dir usb-backups --path /mnt/usb-backups --content backup
--prune-backups keep-last=3 --is_mountpoint 1`.

**Verify:** `pvesm status` shows `usb-backups` active with the **drive's**
total size. If its size and usage match `local`, it's writing to the root
disk: stop and fix the mount.

### 3. The backup job — CONFIRM

A scheduled job on this storage (web interface: Datacenter → Backup, or
`pvesh create /cluster/backup`) with:
- **every guest ID listed**. A new guest isn't backed up until it's added,
  and nothing warns you;
- **compression zstd**. The web form defaults to it, but a job created from
  the command line or API without `--compress` writes uncompressed `.tar`
  files: about three times the size, and invisible to the sync script;
- a time staggered against the other host's job (the book: 02:00 and 02:30).

Run one backup now. **Verify:** it finishes, and the archive is listed in
`pvesm list usb-backups` as `.tar.zst`.

### 4. Bind mounts

For each container bind mount found in *Discover first*, tell the reader
it is **not** in this backup and needs its own (playbook 10.1 has one for
Nextcloud's data).

### 5. Prove the guard by breaking it — CONFIRM

1. **Unmount the filesystem** with the drive still attached (`umount
   /mnt/usb-backups`), then run `pvesm status`. It should come back
   mounted by itself.
2. **Make the drive genuinely absent.** Unplug it, or unbind it from USB if
   it's not reachable. Then:
   - `pvesm status` shows `usb-backups` **inactive** ("expected to be a mount
     point but is not mounted");
   - a backup to it fails;
   - `df` shows the root disk didn't grow by an archive's size.
3. **Reconnect it.** Within moments of the next `pvesm status`, it's active
   again and the earlier archives are listed.

### 6. The off-host copy — CONFIRM

On the second machine: an SSH key that the Proxmox host accepts for root
(BatchMode, no passphrase), `rsync` on both ends, and
`1.3/proxmox-backup-sync.sh` installed with the variables at its top set
(Proxmox host **by IP address**, source and destination folders), plus its
one-line cron entry, **without** an output redirect.

**Verify:**
- A first run is silent, exits 0, and the copy has the `.zst` archives.
- Make the guard fire once: with the drive unplugged, the script prints
  "refused: can't reach the Proxmox host, or its backup drive isn't mounted",
  exits 1, and the copy is untouched. Cron then mails that line to root.

### 7. Sweep your other hosts

If there's another Proxmox host, give it the same guard. The book's war
story is this exact failure, fixed on one host and left on the other for
six weeks.

## Gotchas (from the book and the test)

- **`nofail` makes `mount` return success with the device absent.** Don't
  believe a script that says "mount returned 0". Check `findmnt`.
- **With the automount, `mountpoint -q` passes even when the drive is
  gone** (the placeholder is a mount point). Proxmox's `is_mountpoint`
  still works, because activating the automount fails. In scripts, keep an
  `ls` of the folder in the same `&&` chain, as the sync script does.
- **Hidden backups:** if backups ever landed in the empty folder, a later
  mount hides them while they still use space. `mount --bind / /mnt/x` and
  look in `/mnt/x/mnt/usb-backups`.
- **One enclosure is one failure domain.** Two drives in one USB enclosure
  drop together.
- **One job is lost if the drive drops during a backup.** Its failure mail is
  the signal.

## Rollback

Remove the storage (`pvesm remove usb-backups`; archives stay on the drive),
delete the job, remove the fstab line and reload systemd. On the second
machine, remove the cron entry.
