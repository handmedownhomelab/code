# Playbook 2.3 — Claude Code as sysadmin

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need a workstation (Mac or Linux), a command-line or IDE AI
> assistant (the book uses Claude Code; see the Rosetta Stone table in book
> 2.3 for Gemini CLI, Antigravity, OpenAI Codex CLI, Cursor and Aider paths),
> and a few hosts you can already log in to. If you
> built the wiki in 2.1, have its path handy. For this playbook you can run
> the steps yourself, or give it to your assistant once step 1 is done and say:
> *"Follow this playbook. Ask me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* set up what section 2.3 describes: your own rules, reach and
> tools on their lab. Follow the rules below for the whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's hosts, user names and
   addresses. Ask what you can't find.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before writing or editing `~/.claude/CLAUDE.md` or
   `~/.claude/settings.json` (merge, never replace), before installing a
   key on a host, and before changing any host's SSH or sudo configuration.
4. **Never run sudo without a terminal**, and never type or store a
   password. Where sudo needs one, give the reader the `ssh -t` command and
   let them type it.
5. **Install from the vendor's current instructions**, and show the reader
   any script before running it.
6. **Read-only on the hosts** except for the key installation in step 3.
7. **Verify by effect**: a new session, a real SSH login, the skill run
   against a real host.

## Goal: what "done" looks like

- [ ] `claude --version` works and the reader is logged in.
- [ ] `~/.claude/CLAUDE.md` holds the reader's hosts, username, working
      style and the list of things the AI must never do alone, and a new
      session knows them.
- [ ] One SSH key per workstation, installed on every host, one username
      everywhere; `ssh -o BatchMode=yes` reaches every host with no prompt.
- [ ] Hosts that need a sudo password get the `ssh -t` treatment, by rule.
- [ ] A `fleet-update-check` skill that reports pending updates on every
      host and installs nothing.
- [ ] A wiki page (or a note) listing every MCP server and which program's
      configuration it lives in.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Workstation OS and shell | Install method; key type | `uname -a`; `echo $SHELL` |
| Each host: name, address, how you log in today | The rules file, the SSH step and the skill's access map | Ask; the wiki's `system/` pages (2.1) if they exist |
| The username on each host | The book uses one username everywhere; find the exceptions (`root` on Proxmox, an appliance's fixed user) | Ask; `ssh <host> whoami` |
| Which hosts need a password for sudo | Decides the sudo rule | Ask; `ssh -o BatchMode=yes <user>@<host> 'sudo -n true' && echo nopasswd` (safe: `-n` refuses rather than prompts) |
| Containers without SSH of their own | Reached through their hypervisor (`pct exec` on Proxmox) | Ask; the Proxmox host's `pct list` |
| The wiki path, if any | The rules file points at it | Book 2.1 |
| MCP servers already configured anywhere | The inventory in step 6 | `claude mcp list`; the desktop app's settings; other AI tools' configs |

## Steps

### 1. Install Claude Code

Follow the current instructions at code.claude.com/docs/en/setup (the native
installer is one command on macOS and Linux). Show the reader the installer
before running it; it installs into the home folder and refuses to run
under sudo. If it ends with *"~/.local/bin is not in your PATH"*, add the
line it prints to the shell's startup file and open a new terminal. Then
run `claude` once and log in when it asks.

**Verify:** `claude --version` prints a version, and `claude doctor` ends
with `No installation issues found.`

### 2. The global rules file — CONFIRM

Write `~/.claude/CLAUDE.md` from this template (Appendix C.2), with the
reader's values. Keep it short; it grows with the lab.

```
# Claude Code — my rules, every session

## About me
- <Your experience in a line.> Editor: <yours>.
- Direct, technical answers. No padding. Ask only when genuinely unclear.

## Hosts
<N> hosts; details on wiki/system/<host>.md. Read the page when a host comes
up. Username everywhere: <you>. SSH as <you>@<host>.home.arpa.
- <host> — <one line: what it is, what it runs, how to reach it if unusual>

## Working style
- Check the homelab wiki first, before any other lookup.
- Run commands for me (SSH, runbooks, queries). Show the command and output.
- Confirm before anything irreversible: deletes, stopping production
  services, restructuring the wiki.
- Never run sudo without a terminal on hosts that need a password. Give me
  the `ssh -t` command instead.
- Never touch money, financial accounts or credentials.
- After any change, verify the effect by reading it back, not by trusting
  the tool's success message.
- When something doesn't match expectations, say so plainly.

## Wiki
- Every wiki edit gets a log.md entry in the same commit. Commit and push.
- The wiki holds the canonical copy of every script. Edits made directly on
  a host are copied back to the wiki in the same session.
```

Put each host's quirks on its wiki page, not here ("reach the containers
with `pct exec` from the Proxmox host; they have no SSH of their own").

**Verify:** start a new session in any folder and ask *"Which username do
you use on my hosts, and what must you never do without asking?"* It
answers from the file, not generally. `/memory` lists the file.

### 3. SSH: one key, one username — CONFIRM per host

On the workstation: if `~/.ssh/id_ed25519` doesn't exist, create it with
`ssh-keygen -t ed25519 -C "<you>@<workstation>"`. Set a passphrase if the
reader wants one and uses an agent; a key that prompts would stall every
unattended command.

For each host: `ssh-copy-id <you>@<host>` (the reader types the host's
password once). Use the same username everywhere the reader controls the
accounts. For a Proxmox host, which logs in as `root`, use the IP address
if its DNS name points at a reverse proxy (the book's lab does: 6.3).

**Verify**, for every host:
`ssh -o BatchMode=yes -o ConnectTimeout=5 <user>@<host> 'hostname; whoami'`
prints the host's name and the expected user, with no prompt. A host that
fails is either down or missing the key; book 2.5's `audit.sh` tells the two
apart.

### 4. The sudo rule

The rule is already in the rules file (step 2). Don't weaken a host to
satisfy the AI: if sudo needs a password there, leave it that way. A human
typing a password is a good speed bump.

**Verify:** in a new session, ask for something that needs root on a host
where sudo needs a password, for example *"Show me the last 20 lines of the
SSH server's log on <host>."* The AI does not try `sudo` without a
terminal. It hands back a command of the form
`ssh -t <you>@<host> 'sudo journalctl -u ssh -n 20 --no-pager'` for the
reader to run, or asks first. Then the reader runs
`ssh -t <you>@<host> 'sudo journalctl _COMM=sudo --since today --no-pager'`:
the only sudo entries are the reader's own.

### 5. A first skill: the fleet update check

Create `~/.claude/skills/fleet-update-check/SKILL.md` from this template
(Appendix C.4), with one row per host in the access map:

```
---
name: fleet-update-check
description: Read-only sweep of pending updates on every homelab host, with
  simulated upgrades. Use when asked to check for updates or patch status.
---
# Fleet update check
Read-only. Never apply updates unless the user says so afterwards.

## Access map
| Target | Connect as | Mechanism |
|---|---|---|
| <host> | <user>@<host> | apt |
| <container> | pct exec <id> from <proxmox host> | apt |
| Home Assistant | its MCP server | core / OS / add-ons |

## Not tracked by any package manager (check upstream by hand)
| Tool | Where | How it was installed |
|---|---|---|

## Steps
1. For each apt host: check how old /var/lib/apt/lists is. If it is stale
   and refreshing needs sudo with a password, say so and give the ssh -t
   command; otherwise run `apt-get update`. Then `apt-get -s dist-upgrade`
   (no sudo needed); note removals and security updates.
2. Docker: compare running image digests with the registry's.
3. Report one table: host, updates, security, removals, action needed.
4. Hosts needing a sudo password: give the user the ssh -t command.
```

The second table matters more than it looks: everything installed outside
a package manager (an install script, a git checkout, a hand-downloaded
.deb) is invisible to apt. Fill it in as the lab grows.

**Verify:**
- In a new session, `/skills` lists `fleet-update-check`.
- Ask *"Check the fleet for updates."* (or type `/fleet-update-check`).
  The AI reads the skill, SSHes to each host, and answers with one table.
- Nothing was installed: on each apt host,
  `tail -3 /var/log/apt/history.log` shows no new entry, or `zgrep` it for
  today's date.

### 6. MCP: an inventory first

An MCP server gives the AI named tools for a system it can't reach well by
SSH (Home Assistant is book 5.5's playbook; a UniFi controller; a scoped
folder for the desktop app). Before adding any, write down where each
existing one lives: Claude Code keeps its own (`claude mcp list`; user scope
in `~/.claude.json`, project scope in the project's `.mcp.json`), the
desktop app has a separate file, other AI tools have theirs, and some come
from the reader's Claude account and aren't on disk at all.

Add a server only when there's a job for it, with the narrowest access that
does the job (a read-only account or token first), and add it to the
inventory in the same session:

```
claude mcp add --scope user <name> -- <command> <args>
```

**Verify:** `claude mcp list` shows each server with `✔ Connected`;
`claude mcp get <name>` shows its scope; in a session, `/mcp` shows its
tools. The inventory page names every server, the program it belongs to,
and the account it uses.

### 7. Hooks: point at 2.2 and 2.4

The two remaining pieces are hooks (the wiki pulls at session start and
pushes at the end, book 2.2) and memory (2.4). Each has its own playbook.
Do them next.

## Gotchas (from the book and the test)

- **"Check the wiki first" is the most valuable line.** It turns guessing
  into looking up. If a session answers about the lab from general
  knowledge, the rules file isn't being read: check `/memory`.
- **There isn't one MCP configuration.** A server that "works everywhere
  but here" is almost always configured in a different program's file from
  the one you're looking at. That's why the inventory comes first.
- **A process with no output at all has an environment problem, not a code
  problem.** The book's MCP server lived in an iCloud folder; macOS froze it
  before its first line ran, so there were no logs anywhere. Install servers
  and scripts on plain local disk (`~/.mcp/`, `~/bin/`).
- **A DNS name may not be the host.** If a name points at the reverse proxy,
  `ssh` to it reaches the proxy. Use the address for those hosts, and say so
  on the host's wiki page.
- **Different users exist.** Proxmox hosts log in as `root`; Home
  Assistant's SSH add-on is `root` with a minimal shell. Put each exception
  in the access map, not in the AI's head.
- **Empty isn't the same as absent.** Without sudo, `journalctl -u ssh`
  on Debian prints "No entries" for a user outside the `systemd-journal`
  group: an answer that looks like a quiet log. In the test the AI caught
  it and said why; expect that, and question a read that comes back empty.
- **Don't believe "success".** Every change is checked by reading the thing
  that should have changed. The rules file says so; hold the AI to it.
- **What the AI must never do alone** (the book's list): delete things,
  stop production services or restructure the wiki without asking; touch
  money or credentials; run sudo without a terminal; use a generic "remove
  device" call on Zigbee (4.2 explains why); believe a tool's own success.

## Rollback

Delete `~/.claude/skills/fleet-update-check/`, remove `~/.claude/CLAUDE.md`
(or the parts added), and `claude mcp remove <name>` for anything added. To
take the AI's reach away, remove the workstation's key line from each
host's `~/.ssh/authorized_keys`; book 2.5's `audit.sh` will show those hosts
as **NO KEY**, which is how you confirm it.
