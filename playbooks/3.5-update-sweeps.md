# Playbook 3.5 — Update sweeps without breaking things

> **For the reader.** Read this whole file before you give it to your AI
> assistant. It extends the `fleet-update-check` skill from playbook 2.3,
> so build that first. Nothing here installs an update until you say so,
> and then one host at a time. Then say: *"Follow this playbook. Ask me
> before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 3.5 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's hosts, containers and
   access map from the 2.3 skill.
2. **Show each command before you run it**, and say which machine it runs on.
3. **The sweep is read-only.** Simulate (`apt-get -s`), never install,
   during a sweep. Applying is a separate request, per host.
4. **CONFIRM** before writing a file on a host, before any upgrade, and
   before any restart or reboot.
5. **Never `sudo -n`** on a host that needs a sudo password, and never retry
   sudo there in a loop: on some hosts a failed sudo emails a security
   alert. Give the reader an `ssh -t` command instead.
6. **A count from stale lists is unknown, not zero.** Say so in the report.
7. **Verify by effect**: a date that moved, a count of `(deleted)` lines,
   a service answering.

## Goal: what "done" looks like

- [ ] Every Debian, Ubuntu and Proxmox host and container refreshes its
      package lists daily: `apt-config dump` shows
      `Update-Package-Lists "1"`.
- [ ] The sweep checks freshness first and reports a stale host as
      **STALE, counts unknown**.
- [ ] The sweep simulates every pending upgrade and reports removals, held
      packages, "not upgraded" counts (with the reason) and security
      updates.
- [ ] Docker images are compared by digest, not by tag.
- [ ] Everything outside a package manager is listed, with how to check
      it.
- [ ] After an upgrade, nothing runs on deleted libraries: `grep -c
      '(deleted)' /proc/1/maps` prints 0.
- [ ] Hypervisor reboots happen in a planned window, with DNS covered.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The 2.3 skill and its access map | This playbook extends it | `~/.claude/skills/fleet-update-check/SKILL.md` |
| Each host's distribution | Refresh is on by default on Ubuntu (unattended-upgrades) and Proxmox (its own daily update), off on plain Debian | `. /etc/os-release; echo $PRETTY_NAME` |
| Which hosts need a sudo password | Rule 5 | The 2.3 access map |
| Which hosts email on a failed sudo | Rule 5 | Ask |

## Steps

### 1. Is refresh even on?

On every apt host and container (containers through `pct exec <id> --`
from their Proxmox host):

```
apt-config dump | grep Update-Package-Lists
```

**Read it:** `APT::Periodic::Update-Package-Lists "1";` means on. **No
output means off**: that's plain Debian's default, and also the default
inside a Debian container from a Proxmox template. The daily timer still
runs, does nothing, and shows green.

### 2. How old is the data?

```
grep -m1 '^Valid-Until:' /var/lib/apt/lists/*security*_InRelease
```

Debian's security release file expires a week after it's published, so a
`Valid-Until` in the past means stale lists, whatever the timer says.
Ubuntu's security file has no `Valid-Until`; read its `Date:` line instead
(older than about three days is stale). **"No such file"** is stale too:
a container made from the Proxmox Debian 13 template ships with lists for
the main suites but none for security, until the first refresh.

Two signals that look right and aren't:
- `/var/lib/apt/periodic/update-success-stamp` is missing on healthy
  Debian hosts;
- sorting `/var/lib/apt/lists/` by age picks the `partial/` folder.

### 3. Turn refresh on — CONFIRM, per host

Copy `3.5/10periodic` from this repository to `/etc/apt/apt.conf.d/10periodic`
on each host where step 1 printed nothing (mode 644, root). It refreshes
the lists only: nothing is downloaded or installed.

**Verify through the path that failed**, not by running `apt-get update`
yourself (that would refresh the lists whatever the timer does):

```
apt-config dump | grep Update-Package-Lists        # now "1"
grep -m1 '^Valid-Until:' /var/lib/apt/lists/*security*_InRelease
systemctl start apt-daily.service                  # the daily job itself
grep -m1 '^Valid-Until:' /var/lib/apt/lists/*security*_InRelease
```

The second `Valid-Until` is about a week ahead, and later than the first
(or the first was "No such file"). In the test, the daily job run
**without** the file finished "successfully" and fetched nothing; with it,
the same job fetched the security lists.

### 4. Extend the sweep skill

Add to `fleet-update-check/SKILL.md`, in this order:

- **Step 0, freshness gate:** per host, steps 1 and 2 above in one SSH call.
  A stale host is reported **STALE, counts unknown**, never "up to date".
  A Debian host without `"1"` is missing `10periodic`.
- **Simulate every pending upgrade:** `apt-get -s dist-upgrade` (no sudo
  needed). Report:
  - any `Remv` line: something would be removed;
  - anything "kept back" or "held back";
  - the `N not upgraded` in the summary line (`N upgraded, N newly
    installed, N to remove and N not upgraded`, printed before the `Inst`
    lines, not at the end: `grep 'upgraded,'`). **Never explain it away.** Name each
    package behind it, then `apt-get -s install <pkg>` to see why. An
    Ubuntu *phased* update (`apt-cache policy` shows `phased`) lands by
    itself; an unmet dependency needs a decision;
  - security updates (packages from the `-security` suite).
- **Docker by digest:** for each running image, compare the local digest
  with the registry's, without pulling:
  ```
  docker image inspect -f '{{index .RepoDigests 0}}' <image> | sed 's/.*@//'
  docker buildx imagetools inspect <image> --format '{{.Manifest.Digest}}'
  ```
  The first prints `<image>@sha256:…`; the `sed` leaves the `sha256:…`
  part to compare.
  Use `docker image inspect` on the image, not `docker inspect` on the
  container: a container has no `RepoDigests`. **An empty digest on either
  side is not a pass**; the comparison didn't happen.
- **Home Assistant:** Core, OS and add-on updates through its MCP server
  (playbook 5.5), once you have it.
- **macOS:** `softwareupdate -l`.
- **The things no package manager tracks:** keep the 2.3 skill's second
  table current (install-script binaries, git checkouts, source builds,
  hand-installed `.deb` files) and check each against its upstream release
  page. For a `.deb`, `apt-cache policy <pkg>` showing only
  `100 /var/lib/dpkg/status` means no repository: apt will never report an
  update for it. For a configured repository, read `Installed:`, not
  `Candidate:`.

**Verify:** ask *"Check the fleet for updates."* The report starts with
freshness (every host fresh, or STALE named), has one row per host with
pending, security, removals and held, and nothing was installed (`tail -3
/var/log/apt/history.log` on each host has no new entry).

### 5. Apply, one host at a time — CONFIRM each host

Only when the reader asks, and only for a host whose simulation showed no
removals and nothing held. Hosts where the AI has root (Proxmox hosts and
their containers) can be done by the AI; for sudo-password hosts, hand the
reader `ssh -t <user>@<host> 'sudo apt-get dist-upgrade'`.

Then finish the job: **after apt finishes, the upgrade isn't done.**

1. Check PID 1 (needs root):
   ```
   grep -c '(deleted)' /proc/1/maps
   ```
   It must print **0**. If it doesn't, `systemctl daemon-reexec` and check
   again. (Debian's own systemd package re-executes PID 1 when systemd
   itself is upgraded, so after the test's libc6 + systemd upgrade it was
   already 0. A libc6 upgrade without systemd gets no such help.)
2. Check the other processes:
   ```
   for m in /proc/[0-9]*/maps; do grep -q '(deleted)' "$m" 2>/dev/null && echo "$m $(cat ${m%maps}comm)"; done
   ```
   After the test's upgrade this listed cron, dbus-daemon, systemd-logind,
   the gettys, dhclient and the test's own shell (ignore your own shell).
   Restart the services that are safe to restart (`systemctl restart cron
   systemd-logind` cleared those two). dbus, the gettys and the DHCP client
   are simpler to clear with a reboot of the guest, in a quiet moment; in
   the test, a container reboot left the list empty. On a Proxmox
   container, wrap the loop so the glob expands **inside** the container:
   `pct exec <id> -- bash -c '<the loop above>'`. Without `bash -c` the host
   expands it, and the test got an empty answer: a false all-clear.
3. Re-read the installed version (`apt-cache policy <pkg>`): repositories
   move between a sweep and an apply.

**Verify:** `(deleted)` count 0 on PID 1, an empty loop, and the host's
services answering (its Kuma monitors from 3.1 are green).

### 6. Plan the reboots — with the reader

A kernel update needs a reboot, and **a hypervisor reboot is several
reboots**: everything on that host goes down with it. List the guests on
each Proxmox host (`pct list`, `qm list`), write down what each one is
(DNS, the proxy, Home Assistant, the CA), and pick a window. Let the
second Pi-hole (playbook 6.2), on the other host, carry DNS through it.

**Verify:** after the window, `uname -r` matches the newest installed
kernel, and every guest set to start at boot is running.

## Gotchas (from the book and the author's lab)

- **The fix that wasn't** (book 3.5's war story). Five containers showed
  zero updates. The network-wait step was blamed and masked, and a manual
  `apt-get update` "confirmed" the fix: 91 security updates appeared. Five
  weeks later the lists were 24 days old on eight machines. The wait step
  never mattered; refresh was simply off. Prove a fix through the path that
  failed (step 3's `systemctl start apt-daily.service`).
- **Rolling Docker tags lie.** `:latest` and `:main` have the same name
  before and after a new release. Compare digests.
- **"apt is clean" isn't "the library is patched."** Python wheels bundle
  their own copies of libraries such as image codecs, which apt can't see.
  When a library vulnerability is in the news, check every virtual
  environment (`find / -name pyvenv.cfg 2>/dev/null`, not a `*/venv` glob)
  and what running processes have mapped (`/proc/*/maps`). A venv made by
  `uv` may have no `pip`; list it with `uv pip list --python <venv>`.
- **Upgrading a wheel doesn't fix a running process.** It keeps the old
  library mapped until it restarts.
- **Drivers and Docker in one batch.** On a GPU host, an NVIDIA driver
  upgrade plus a Docker restart can leave GPU containers failing until the
  host reboots. Upgrade them in a window, and reboot promptly (book 7.1).
- **A Go binary needs no restart after an OpenSSL update**, and gets none
  from it either: its crypto is built in. Its version is the binary's.

## Rollback

`rm /etc/apt/apt.conf.d/10periodic` turns daily refresh off again. Remove
the added steps from the skill. An applied upgrade can't be rolled back by
apt in general: that's what the backups in playbook 1.4 are for.
