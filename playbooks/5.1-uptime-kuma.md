# Playbook 5.1 — Uptime Kuma: the monitor that watches the watcher

> **For the reader.** Read this whole file before you give it to your AI
> assistant. Then say: *"Follow this playbook. Ask me before every step
> marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 5.1 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's hosts and addresses are the
   author's. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs
   software or deletes anything is a CONFIRM step even if this file forgot
   to mark it.
4. **Get install steps from Uptime Kuma's own wiki** ("How to Install"),
   not from memory.
5. **Secrets:** the reader creates Kuma's admin account and types the SMTP
   password into Kuma themselves. A script that creates monitors must
   prompt for the admin password, never take it as an argument.
6. **Verify by effect**: each monitor shows the state you expect, and a
   test alert actually arrives in the reader's inbox.
7. If the reader keeps a homelab wiki, record the monitor list and the
   dependency tree there.

## Goal: what "done" looks like

- [ ] Kuma runs on **different hardware** from the things it watches most
      (especially Home Assistant), starts at boot, and its admin account
      belongs to the reader.
- [ ] HTTPS checks on `*.<domain>` names pass **without** "ignore TLS
      errors", so Kuma reads real certificate expiry dates.
- [ ] At least one each of: HTTP(S), DNS (each Pi-hole), and a push monitor
      for a scheduled job.
- [ ] Monitors are arranged in groups from the gateway down.
- [ ] A test notification arrives by email, through Kuma's own SMTP
      settings, not through Home Assistant.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Where Kuma will run | Not on the same physical machine as Home Assistant, or one failure silences both | Ask; the book uses a small container on the second Proxmox host |
| Its fixed address and name | The reader opens it, and push URLs point at it | Ask; book 1.4 and 3.1 |
| The reader's CA root, if they built 3.4 | So HTTPS checks verify | From playbook 3.4 (with its fingerprint) |
| What to watch | Services as users reach them (names, through the proxy), not just pings | Ask; list hosts, then services on each |
| An SMTP account for alerts | Kuma sends its own mail | Ask; the reader enters the password in Kuma |

## Steps

### 1. A machine on other hardware — CONFIRM

A small Debian container is enough to run Kuma. Give it 2 cores and 2 GB
for the install (the build fetches a prebuilt web interface and uses
little memory, but npm is happier with room); 1 GB is plenty afterwards.
In an unprivileged Proxmox container, turn on `nesting`: Debian 13's
systemd needs it.

### 2. Install Kuma — CONFIRM

Follow the wiki's **Non-Docker** install: Node.js (Debian's own `nodejs`
and `npm` packages are new enough; check the wiki's minimum), `git`, clone
the repository into `/opt/uptime-kuma`, **check out the newest release tag**
(not the development branch), and `npm run setup`. Create a system user for
it and make it own `/opt/uptime-kuma`. (Docker is the wiki's other option.
The book's lab uses the non-Docker install.)

Run it as a **systemd service** as that user, rather than the wiki's pm2.
That way it starts at boot like everything else, and its logs go to the
journal. `Restart=on-failure`.

**Verify:** the service is active and enabled, and `http://<kuma-ip>:3001/`
answers.

### 3. Claim it now — the reader does this

Until Kuma is set up, **its setup screens need no login**: anyone on the
network who opens port 3001 first chooses the database and creates the
admin account. Ask the reader to open `http://<kuma-ip>:3001` straight
away. Kuma 2 asks for the database first: **SQLite** is right for one small
lab. Then they create their admin account.

**Verify:** opening the address now shows the login page.

### 4. Trust your CA, and allow ping — CONFIRM

- **Root certificate:** add the reader's CA root to the system store (check
  its fingerprint first) and **restart Kuma**. Debian's Node.js reads the
  system store at start. Without this every `*.home.arpa` HTTPS check fails
  with "unable to get local issuer certificate". The tempting fix, "ignore
  TLS errors", throws away the certificate-expiry signal that is a third of
  the reason for this monitor.
- **Ping:** Kuma's service user can't send ICMP in an unprivileged
  container until `net.ipv4.ping_group_range` allows it. Put
  `net.ipv4.ping_group_range = 0 65534` in a file under `/etc/sysctl.d/`
  and apply it. The common value `0 2147483647` is **rejected** with
  "Invalid argument" in an unprivileged container, which maps only 65,536
  group IDs.

**Verify:** after the next check, an HTTPS monitor on a private-CA name is
UP with expiry information, and a ping monitor is UP.

### 5. Alerts by their own path

The reader adds an SMTP notification in Kuma (Settings → Notifications)
with their own account and password, makes it the default, and presses
**Test**. **Verify:** the test email arrives. Don't route Kuma's alerts
through Home Assistant: that's the dependency this monitor exists to avoid.

### 6. Monitors that check what users use — CONFIRM

Create the monitors in the web interface, or with a script. If you script
it, use Kuma's socket.io API with a password prompt, and make it idempotent
(look a monitor up by name before adding it).

- **HTTP(S)** on each service's real name through the proxy, with
  certificate expiry notifications on.
- **DNS** against each Pi-hole for a local name.
- **Push** for each scheduled job: the job calls
  `https://<kuma>/api/push/<token>?status=up&msg=OK` **only when it
  succeeds**, and the monitor's interval is a little longer than the job's
  schedule.
- **Groups:** gateway at the root, then switches, then hosts, then
  services, so one switch reboot doesn't send thirty alerts.
- **Retries:** size them to the longest normal blip, such as a switch
  rebooting for a firmware update. Two retries a minute apart absorb about
  two minutes.

**Verify:**
- Every monitor is UP, except ones you expect down.
- Call one push URL once, then let it go silent past its interval: the
  monitor goes **DOWN** with "No heartbeat in the time window", and an alert
  arrives. Then push again and see it recover.

### 7. Reach it at a name — optional

Add a proxy host for Kuma (playbook 3.3), with **WebSockets on**: Kuma's
interface is live updates over WebSockets.

## Gotchas (from the book and the test)

- **Everything red at once?** Suspect the monitor's own network path first
  (a switch between Kuma and the house rebooting), not a real outage.
- **A 1-millisecond check is probably answering from a cache**, and stays
  green through an outage.
- **Debian's Node.js needs a restart to see a newly trusted root.**
- **The ping range upper bound is 65534 in an unprivileged container.**
- **Kuma 2 starts with a database-choice page** that Kuma 1 didn't have.
  Older guides skip it.
- **Push monitors are only as good as "only on success".** A job that calls
  the push URL unconditionally reports UP while failing.

## Rollback

Stop and disable the service, remove `/opt/uptime-kuma` and the unit file.
Remove the push calls from jobs, or they'll fail quietly against a missing
host.
