# Playbook 3.2 — Two Pi-holes that stay in sync

> **For the reader.** Read this whole file, and `3.2/pihole-sync.sh`, before
> you give them to your AI assistant. Then say: *"Follow this playbook. Ask
> me before every step marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 3.2 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** The book's addresses and names are the
   author's. Use the reader's.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** means stop, ask, and wait for a yes. Anything that installs
   software, changes DNS or DHCP for the house, or deletes anything is a
   CONFIRM step even if this file forgot to mark it.
4. **Secrets never go on a command line, in your output, or in a file you
   write.** The sync needs both admin passwords in a root-only file: you
   create it with placeholders, the reader types the real values in.
5. **Verify by effect**: read back the state a step should have changed.
6. If the reader keeps a homelab wiki (book Chapter 2), record what you
   built there, with the verification results.

## Goal: what "done" looks like

- [ ] A second Pi-hole runs on **different hardware** from the first.
- [ ] A local name added on the primary answers on the secondary after one
      sync, and the secondary's own web address still works.
- [ ] A second sync with no change on the primary does **not** import or
      restart anything (the log says so).
- [ ] With the primary stopped, the secondary still answers.
- [ ] The gateway hands out the secondary as DNS server 2, or the reader has
      decided to do that later.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The primary Pi-hole's address, and whether its web interface uses HTTPS | The sync logs into its API | Ask; book 3.1 built it |
| Where the secondary will run | **Not** on the same physical machine as the primary, or one reboot takes both down | Ask |
| The secondary's fixed address | Clients and the gateway need it | Ask; book 1.4 |
| The secondary's own web host name | The import overwrites it; the script puts it back | Ask, e.g. `pihole2.home.arpa` |
| Whether a local name for the secondary exists on the primary | It should, so the name works from both | Check on the primary |

## Steps

### 1. Install Pi-hole on the second machine — CONFIRM

Follow **playbook 3.1** steps 1–4 on the new machine: small container or
machine, fixed address, Pi-hole installed, admin password set by the reader,
blocking verified with `dig`. Skip 3.1's local names: they'll come from the
primary.

**Use the primary's admin password for the secondary too.** The first sync
copies the primary's password hash anyway, and from then on the secondary
only accepts the primary's password. Starting with the same one avoids the
trap in step 4.

### 2. Prerequisites for the script

The script needs `curl`, `python3`, `unzip`, `sha256sum` and `dig` on the
secondary. Check each with `command -v`, and install what's missing with the
system's package manager (CONFIRM).

### 3. Install the script — CONFIRM

Copy `3.2/pihole-sync.sh` from this repository to the secondary and install
it as the comment at its top says: `/usr/local/bin/pihole-sync`, mode 755.
Show the reader the file's header first.

If the primary's web interface is plain HTTP (no certificate yet; book 3.4
adds one), `PRIMARY_URL` starts `http://`. The script's `curl -k` matters
only for HTTPS.

### 4. The credentials file — the reader types the passwords

Create `/etc/pihole/sync-credentials` as root, mode `600`, containing the
lines from the script's header with **placeholders** for the passwords, the reader's primary address in `PRIMARY_URL`, and the secondary's
host name in `SECONDARY_DOMAIN`. Then ask the reader to open it in an editor
over `ssh -t` and type the passwords in, inside the single quotes. **Both
`PRIMARY_PASS` and `SECONDARY_PASS` are the primary's password.** With the
secondary's own (different) password, the first sync works and every later
one fails with `failed to auth to self`, because the first sync replaced the
secondary's password.

A password containing `'`, `"` or `\` breaks this file or the script's JSON.
If the reader's does, they should change it first.

**Verify:** `stat -c '%a %U' /etc/pihole/sync-credentials` prints
`600 root`, also after the reader has edited it (some editors and `sed -i`
write a new file with looser permissions). Do not display the file.

### 5. First sync, by hand — CONFIRM

This replaces the secondary's whole configuration with the primary's,
including its admin password. Tell the reader before running it.

Run `/usr/local/bin/pihole-sync` as root and read the last lines of
`/var/log/pihole-sync.log`.

**Verify:**
- The script exited 0 and the log's last line reads `OK: sync complete
  (config changed, serving again after Ns)`, with N a few seconds.
- `journalctl -u pihole-FTL --since -5min` has no `Failed with result
  'timeout'`. (If it does, the script is an old version that restarts
  Pi-hole itself; see Gotchas.)
- A local name that exists on the primary answers on the secondary:
  `dig +short <name> @<secondary-ip>` from another machine.
- `pihole-FTL --config webserver.domain` on the secondary prints the
  secondary's own host name, not the primary's.
- `dig +short doubleclick.net @<secondary-ip>` returns `0.0.0.0`.

### 6. Prove the change gate

Run the script a second time **without changing anything** on the primary.

**Verify:** the log says nothing changed, and Pi-hole was not restarted:
`systemctl show pihole-FTL -p ActiveEnterTimestamp` on the secondary is the
same before and after the run. This is the check that would have caught the
book's war story.

Then add a test local name **on the primary**, run the script once more, and
check that the name answers on the secondary. Remove the test name on the
primary afterwards (it will vanish from the secondary on the next sync).

### 7. Schedule it — CONFIRM

Install the cron line from the script's header (`/etc/cron.d/pihole-sync`,
every 15 minutes, as root).

**Verify** after the next quarter hour: a new line in
`/var/log/pihole-sync.log`.

### 8. Test failover — CONFIRM

Stop the primary (stop its container, or `systemctl stop pihole-FTL` on it),
then from another machine `dig +short <a-local-name> @<secondary-ip>`.
Start the primary again and check it answers too.

### 9. Hand both to every client — CONFIRM, usually the reader's job

Set the gateway's DHCP to hand out the primary as DNS server 1 and the
secondary as DNS server 2, on every network. Give the reader the steps for
their gateway model unless you have a tool for it and they ask you to use it.

**Verify:** a client that has renewed its lease lists both servers.

## Gotchas (from the book)

- **Edits on the secondary vanish, but not right away.** Because the sync
  imports only when the primary changes, an edit made only on the secondary
  survives every quiet sync and disappears at the primary's next change,
  maybe weeks later. It looks as if it stuck. Make every change on the
  primary. (Tested: a secondary-only record survived a no-change sync and
  was gone after the next primary change.)
- **A primary change is half applied until the next sync.** Anything that
  must take effect now, such as pausing blocking, has to be done on both.
- **The sync copies blocklist rows, not the built list.** After adding a
  blocklist on the primary, run `pihole -g` on the secondary too, or it
  blocks less for up to a week. Test with a domain that exists only in the
  new list.
- **The sync copies mistakes too**, like a backup file left in
  `/etc/pihole/hosts/` (3.1).
- **Never add `systemctl restart pihole-FTL` after an import.** The import
  makes Pi-hole restart itself, and so does the script's host-name fix. A
  restart on top of those hangs for systemd's 60-second stop timeout and
  Pi-hole is killed: a minute without DNS, while `systemctl` returns 0. That
  is the book's war story, and the test reproduced it on a fresh pair. The
  current script waits for Pi-hole's own restart instead (about 3 seconds
  in testing).
- **If the script can't unpack the export it stops with an error.** Older
  versions carried on, and every later sync was silently skipped as "no
  change". Keep `unzip` installed.

## Rollback

Delete `/etc/cron.d/pihole-sync`, then remove the secondary from the
gateway's DHCP DNS list before removing the machine. The primary is never
changed by the sync.
