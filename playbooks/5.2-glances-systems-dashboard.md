# Playbook 5.2 — Servers, climate and your own data on the dashboard

> **For the reader.** Read this whole file before you give it to your AI
> assistant. You need Home Assistant from playbook 4.1. You create the
> Proxmox user's token yourself (step 1), and Google's Nest setup is yours
> too (step 6). Then say: *"Follow this playbook. Ask me before every step
> marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 5.2 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover, don't assume.** Use the reader's hosts, addresses and
   firewall tools.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before installing anything on a host, before every firewall
   change, and before creating a dashboard.
4. **Secrets stay with the reader.** The Proxmox token and Google's
   credentials are typed by the reader into Home Assistant, never into the
   chat or a command line.
5. **Install Glances at one pinned version** everywhere, and get the install
   method from Glances' own documentation.
6. **Verify from Home Assistant's side**, not from the host: a working agent
   proves nothing about the firewall path.

## Goal: what "done" looks like

- [ ] Every Proxmox host and guest reports CPU, memory and disk in Home
      Assistant through a **read-only** Proxmox user (`PVEAuditor`).
- [ ] Every other machine runs **Glances at one pinned version**, as a
      service, with its API reachable **only from Home Assistant's
      address**, and is added with the Glances integration.
- [ ] A **Systems** dashboard: one row per host, CPU / memory / disk gauges,
      and a note instead of a misleading 0% where a VM's disk can't be read.
- [ ] Optional: thermostats, air quality and weather on a climate
      dashboard; your own pages on webpage or markdown cards.

## Discover first

| What | Why | How to find it |
|---|---|---|
| Home Assistant's address | The firewall rule names it | Settings → System → Network; it must be a DHCP reservation (playbook 1.5) |
| Proxmox hosts | The Proxmox VE integration | From playbook 1.2 |
| The other machines | Each gets Glances | Ask: bare-metal Linux, Pis, Macs |
| Each machine's firewall | ufw, nftables, macOS `pf` | `ufw status`, `nft list ruleset`, `pfctl -s rules` |
| The Glances version to pin | One version everywhere | The newest on [PyPI](https://pypi.org/project/Glances/) that the Glances integration documents as supported; write it down |
| Free port 61208 | Glances' default | `ss -ltn | grep 61208` (Linux), `lsof -iTCP:61208` (Mac) |

## Steps

### 1. A read-only Proxmox user — the reader creates the token

On each Proxmox host, following Home Assistant's
[Proxmox VE](https://www.home-assistant.io/integrations/proxmoxve/) page: a
user in the **PVE** realm (e.g. `hass@pve`), given the **`PVEAuditor`**
role on `/`, and an API token for it. The reader creates the token in
Proxmox's web interface and keeps it for step 2.

**Verify:** in Proxmox, Datacenter → Permissions shows the user with
`PVEAuditor` only.

### 2. The Proxmox VE integration — CONFIRM

Settings → Devices & services → Add integration → **Proxmox VE**: realm
PVE, the host, port 8006, the username, *API token* on; the reader pastes
the token ID and secret.

**Verify:** the integration shows a device per node and per guest, with CPU
and memory sensors that move. Control buttons (start, stop) are expected to
fail: the user can only read, on purpose.

### 3. Glances on one machine — CONFIRM

On the first non-Proxmox machine, from Glances' documentation:
- Install **the pinned version** with its web extra (on Linux,
  `pipx install 'glances[web]==<version>'` as a normal user is the simple
  way).
- Run it as a service that starts at boot: **`glances -w --disable-webui`**
  (the API without the browser interface), bound to the machine's own
  address: a systemd unit on Linux, a launchd job on a Mac.

**Verify (on the machine):** `glances --version` prints the pinned version
and "API version: 4". `curl -s http://<bound-address>:61208/api/4/cpu`
returns JSON with a `total` field (bound to the machine's address, it does
not answer on `127.0.0.1`), and `/` returns 404 because the web interface is
off. If `/api/4/` returns 404, the installed version speaks a different
API: check the pin.

### 4. Firewall the agent to Home Assistant only — CONFIRM

Allow TCP 61208 **from Home Assistant's address only**, and nothing else to
that port. With ufw: `ufw allow from <ha-address> to any port 61208 proto
tcp`, with no wider rule for 61208. Write down, next to the reservation,
that this rule depends on Home Assistant's address.

**Verify from two sides:**
- From Home Assistant (its terminal add-on or SSH): the same `curl` against
  the machine's address returns JSON.
- From any other machine: the connection **times out**. A timeout is the
  correct result here.

### 5. Add it to Home Assistant, then the rest — CONFIRM each

Settings → Devices & services → Add integration → **Glances**: host (the
address), port 61208, no SSL; leave username and password empty unless you
set Glances up with a password. The entities are created as
`sensor.<address_with_underscores>_*`. Rename the device to the machine's
name, and rename its entities to match if you want readable IDs: renaming
the device doesn't rename the entities.

**Verify:** the device has `*_cpu_usage`, `*_memory_usage` and
`*_disk_usage` entities with live values (a Linux host gives a few dozen to
over a hundred). Then repeat steps 3–5 for each machine,
at the **same** pinned version.

### 6. The Systems dashboard — CONFIRM

A new dashboard, "Systems". Per host: a **heading** with its name, then
gauges for CPU, memory and disk (severity green / yellow at 75 / red at
90). For a VM whose guest disk the hypervisor can't see, put a **markdown
card** saying so ("Guest disk not exposed") instead of the disk gauge: the
integration reports 0, which would read as an empty disk.

**Verify:** every host from *Discover first* has a row, every gauge shows a
live value, and no row shows a 0% disk that isn't real.

### 7. Climate and your own data (optional) — the reader drives

- **Nest thermostats** come through Google's cloud: a Google Cloud project,
  OAuth credentials, a Device Access registration (a one-off fee) and a
  Pub/Sub subscription. Follow Home Assistant's
  [Nest](https://www.home-assistant.io/integrations/nest/) page step by step
  with the reader; the credentials are theirs to enter. Expect an evening.
- **Air quality and weather:** add the reader's air sensor's integration and
  a weather integration; put them beside the thermostats.
- **Your own data:** a *webpage* card shows any page Home Assistant's browser
  can reach (it must allow framing), and a *markdown* card shows text or a
  template. Use them for the reader's own projects.

**Verify:** each card shows live content on a phone as well as a desktop.

## Gotchas (from the book and the test)

- **Pin the Glances version.** An unpinned upgrade can change the API so
  the integration finds no entities at all, while the service looks healthy.
- **The firewall rule names Home Assistant's address.** If that address
  changes, every Glances host goes stale. Reserve it, and list the rule
  beside the reservation.
- **A working agent proves nothing about the path.** Test from Home
  Assistant's side; a timeout from anywhere else is correct.
- **Use the address, not a `.local` name**, for the Glances host in Home
  Assistant: mDNS can answer with an IPv6 address the agent isn't
  listening on.
- **Deleting a Glances entry deletes the helpers on its device** (statistics
  sensors, for example). Re-adding a host means recreating them.
- **VM disks read 0 from outside.** Show a note, not a gauge.
- **This is a dashboard, not a monitor.** When Home Assistant is down, so is
  this page; uptime monitoring belongs on other hardware (playbook 3.1).

## Rollback

Remove the integrations (Settings → Devices & services), delete the
dashboard, stop and disable the Glances service, uninstall it
(`pipx uninstall glances`), remove the firewall rule, and delete the Proxmox
user and its token.
