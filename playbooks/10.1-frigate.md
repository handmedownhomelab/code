# Playbook 10.1 — Frigate: detection on top of your recorder

> **For the reader.** Read this whole file, and `10.1/config.yml`, before
> you give them to your AI assistant. You need a machine with Docker and
> room for recordings (the book's is the GPU tower from 7.1), cameras or a
> recorder that serve RTSP, and an MQTT broker (Home Assistant's, from
> playbook 5.1). Then say: *"Follow this playbook. Ask me before every step
> marked CONFIRM."*
>
> **For the AI assistant.** You are helping a reader of *Hand-Me-Down
> Homelab* build what section 10.1 describes. Follow the rules below for the
> whole session.

## Rules for the assistant

1. **Discover before assuming.** Nothing here assumes the book's addresses,
   camera names or channel numbers.
2. **Show each command before you run it**, and say which machine it runs on.
3. **CONFIRM** before installing software, starting containers, or changing
   anything on the recorder or the broker.
4. **Get current commands from Frigate's own documentation**
   (docs.frigate.video), especially the model export, which changes.
5. **Secrets stay out of files you'd share and off command lines.** Camera
   and MQTT passwords go in a `.env` file (mode 600) that Frigate reads as
   `{FRIGATE_…}` placeholders. The reader types passwords; you don't echo
   them.
6. **"No errors" is not "working".** Every detection check compares the
   output with an answer you already know.

## Goal: what "done" looks like

- [ ] A YOLOv9 model built with Frigate's recipe, checked on a known image
      before any camera sees it.
- [ ] Frigate running in Docker, its web interface on port 8971 behind a
      login, and the unauthenticated port 5000 reachable only from the host.
- [ ] Each camera's small stream used for detection and its main stream for
      recording, with the camera passwords in `.env`.
- [ ] A person walking past a camera becomes an event with a clip, a
      snapshot and a message on `frigate/events`.
- [ ] Each camera in Frigate shows the view you expect.

## Discover first

| What | Why | How to find it |
|---|---|---|
| The host, and whether it has an NVIDIA GPU | GPU image or CPU image | `nvidia-smi`; book 7.1 sets up the driver and container toolkit |
| Where recordings will live, and how much space | Retention is sized to the disk | `df -h`; a surveillance-rated drive for all-day writes |
| Each camera's two RTSP URLs | Main stream to record, sub stream to detect | The recorder's or camera's documentation; for a recorder, the **channel number** of each camera |
| The sub stream's resolution and frame rate | `detect:` must match it | The recorder's stream settings; 640 × 360 at 5–10 fps is plenty |
| The MQTT broker's address, and a login for Frigate | Frigate publishes events there | Home Assistant's Mosquitto add-on (playbook 5.1); ask the reader to create a `frigate_mqtt` user |
| The time zone | Timestamps on clips | The host's `/etc/localtime` |

## Steps

### 1. Docker — CONFIRM

Install Docker Engine and the compose plugin from Docker's own repository
(docs.docker.com, the page for this distribution). On a GPU host, the NVIDIA
driver and container toolkit come first (book 7.1).

**Verify:** `docker run --rm hello-world` prints its greeting. On a GPU host,
`docker run --rm --gpus all ubuntu nvidia-smi` lists the card.

### 2. Build the model — CONFIRM

Create the Frigate folder (for example `~/frigate/`, with `config/` and
`media/` inside), then `config/model_cache/onnx/`. In that folder, run the
**YOLOv9 export command from Frigate's documentation** (Object detectors,
YOLOv9). It's a `docker build … --output .` with `MODEL_SIZE` and `IMG_SIZE`
arguments. Use `t` and `320` to match the book. It downloads PyTorch and the
YOLOv9 weights, exports, and leaves `yolov9-t-320.onnx` (about 8 MB) in the
folder. It needs several GB of free disk while it runs.

Don't download a ready-made ONNX file from elsewhere: a badly quantized
model loads and runs without an error and detects nothing (the book's war
story).

**Verify:** run the model on a photo whose contents you know, before any
camera sees it. In a throwaway Python container (`python:3.11-slim`, then
`pip install numpy onnxruntime pillow`), with the model folder mounted at
`/m` and a copy of Ultralytics' `bus.jpg` (ultralytics.com/images/bus.jpg)
placed beside the model:

```python
import numpy as np, onnxruntime
from PIL import Image
sess = onnxruntime.InferenceSession("/m/yolov9-t-320.onnx", providers=["CPUExecutionProvider"])
img = Image.open("/m/bus.jpg").convert("RGB").resize((320, 320))
arr = np.array(img).transpose(2, 0, 1)[None].astype(np.float32) / 255.0
out = sess.run(None, {sess.get_inputs()[0].name: arr})[0]
# This export's output is (1, 84, anchors): 4 box values, then 80 class scores.
cls = out[0, 4:, :].T if out.shape[1] < out.shape[2] else out[0, :, 4:]
best = cls.max(axis=1)
names = {0: "person", 5: "bus"}
found = {names.get(int(c), int(c)) for c in cls.argmax(axis=1)[best > 0.25]}
print(out.shape, round(float(best.max()), 3), int((best > 0.25).sum()), found)
```

**Healthy:** the top score is between 0.6 and 0.95 and the only classes
found are `person` and `bus` (the test: 0.896, both). **Broken:** a top
score of 1.0 on hundreds of anchors. **Misread:** a "score" in the hundreds
means the output was read the wrong way round (box coordinates, not class
scores); check which axis is 84. Delete `bus.jpg` from the model folder
afterwards.

### 3. An MQTT login for Frigate — CONFIRM

On the broker, the reader creates a user for Frigate (with Home Assistant's
Mosquitto add-on, a Home Assistant user or an add-on login, as its
documentation says) and types the password into `.env` in the next step.

**Verify:** from any machine with `mosquitto-clients`, an anonymous
`mosquitto_sub -h <broker> -t 'frigate/#'` is refused ("not authorised").

### 4. Compose and secrets — CONFIRM

In the Frigate folder, create `.env` (mode 600) with
`FRIGATE_MQTT_PASSWORD=` and `FRIGATE_RTSP_PASSWORD=` (the reader types the
values), and a `docker-compose.yml`:

```yaml
services:
  frigate:
    container_name: frigate
    image: ghcr.io/blakeblackshear/frigate:0.18.0    # pin a release; see "Updates"
    restart: unless-stopped
    env_file: [.env]
    shm_size: "256mb"
    volumes:
      - ./config:/config
      - <recordings disk>:/media/frigate
      - /etc/localtime:/etc/localtime:ro
    tmpfs:
      - /tmp/cache:size=1000000000
    ports:
      - "8971:8971"              # web interface and API, with a login
      - "127.0.0.1:5000:5000"    # no login: this host only (watchdogs, scripts)
```

**On an NVIDIA GPU** (the book's setup; not tested here), use the
`-tensorrt` variant of the image (`0.18.0-tensorrt`: it carries the CUDA
runtime the ONNX detector uses on the GPU), and add:

```yaml
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    environment:
      - CUDA_CACHE_PATH=/config/model_cache/cuda_cache
      - CUDA_CACHE_MAXSIZE=536870912
```

The CUDA cache lives on the persistent `/config` mount: without it, every
cold start on a new GPU generation spends about 90 seconds compiling
kernels.

Port 5000 has **no authentication** and controls everything, configuration
included. Publish it to the LAN only if you have a reason, and then behind
the reverse proxy with its own access control. Port 8554 (the RTSP
restream) is left unpublished here for the same reason: publish it only
when another program needs the streams.

### 5. The configuration — CONFIRM

Copy `10.1/config.yml` from this repository to `config/config.yml` and
change, with the reader:

- `mqtt:` the broker's address and the user from step 3.
- `go2rtc: streams:` each camera's main and sub RTSP URLs, with
  `{FRIGATE_RTSP_PASSWORD}` in place of the password.
- `cameras:` one entry per camera; `detect:` width, height and fps to match
  the sub stream.
- `zones:` delete the `street` zone for now (book 10.3 builds it with
  measured distances).
- `ui: unit_system:` metric or imperial.
- `record:` and `snapshots:` retention, sized to the disk.

Leave the `model:` block as it is: every field matters, and adding
`input_pixel_format` has broken detection before. Leave the `version:` line;
Frigate writes it.

**Verify:** `docker compose config` shows no errors, and every line that
`grep -i password config/config.yml` prints holds a `{FRIGATE_…}`
placeholder, never a real password.

### 6. Start it, and take the login — CONFIRM

`docker compose up -d`. On the first start Frigate creates an `admin` user
and prints its password **once** in the log, between rows of asterisks:
the reader reads it with `docker logs frigate 2>&1 | grep -A1 'User: admin'`,
logs in at `https://<host>:8971`, and changes it. The log keeps the old
password until the container is recreated.

**Verify:** from another machine, `curl -sk https://<host>:8971/api/events`
returns `401` and `curl http://<host>:5000/api/version` can't connect. After
logging in, the web interface shows each camera's live view.

### 7. Prove detection

Have someone walk past a camera.

**Verify, on the host:**

- `curl -s localhost:5000/api/stats`: for the camera, `camera_fps` near the
  `detect` fps, `process_fps` the same, `skipped_fps` 0, and the detector's
  `inference_speed` in milliseconds (the book's GPU: about 7; the test's old
  CPU: 81, which skipped half the frames; lower `detect: fps` on a slow
  CPU).
- `curl -s 'localhost:5000/api/events?limit=5'`: a `person` event with a
  score between 0.5 and 0.95, `has_clip` and `has_snapshot` true.
- `mosquitto_sub -h <broker> -u frigate_mqtt -P … -t frigate/events -C 1`
  (the reader types the password): one JSON message for the event.

### 8. Check every camera is the camera you think

Open each camera in Frigate and compare it with the recorder's own view.
A recorder **renumbers channels** when cameras are added or moved, and
Frigate then silently analyzes a different camera. Repeat this after any
change on the recorder.

### 9. Write it down

On the host's wiki page: the image version, where the model came from and
its sanity-check result, the compose file, which channel is which camera,
retention, and the update routine below.

## Updates

Pin a release in the compose file and update on purpose: read the release
notes, change the tag, `docker compose pull && docker compose up -d`, then
repeat step 7. Frigate migrates its own config and database on a minor
version change. Keep a copy of `config/` (and its `frigate.db`) from before.

## Gotchas (from the book and the test)

- **"No errors" isn't working.** A broken model runs without complaint.
  The step 2 check is the only proof.
- **Buses and trucks are "car".** Frigate's label map files COCO's bus and
  truck under `car`, so track `car` to see them.
- **Snapshots are `.webp`** in `media/clips/` (0.18), not `.jpg`.
- **Channel numbers aren't camera names** (step 8).
- **`Did not detect hwaccel`** is a warning, not an error: video decoding
  falls back to the CPU. On an NVIDIA card Frigate finds NVDEC by itself.
- **The first-run password is in the log.** Change it.
- **"Healthy" isn't detecting.** Book 10.2 is a 45-hour outage with the
  container healthy throughout; its watchdog watches `process_fps`.

## Rollback

`docker compose down` in the Frigate folder, then remove the folder and the
recordings, and the MQTT user on the broker. Nothing else depends on Frigate
until Home Assistant's integration is added.
